# 기술 블로그와 TIL 글쓰기 컨벤션

블로그 글은 독자가 **어떤 문제를 왜 해결하려 했고, 무엇을 근거로 선택했는지** 이해하도록 작성합니다. 이 규칙은 `content/posts`와 `content/til`에 새 글을 쓰거나 기존 글을 수정할 때 적용합니다. 시리즈 목차와 표식은 [블로그 목차 컨벤션](./blog-outline-convention.md)을 함께 따릅니다.

아래 네 가지 작성 기준은 사용자가 제공한 [원본 글쓰기 규칙](https://github.com/whizzkid1452/cursor-agent-skills/blob/feature/blog-writing-convention/rules/cursor/blog-writing-convention.mdc)을 블로그에 적용한 것입니다. 원문의 예시 수치나 대안을 실제 경험으로 옮기지 않는 근거 기준도 함께 적용합니다.

## 1. 공개할 내용은 개념과 인터페이스 중심으로 추상화합니다

- 사내 로직, 비공개 제품 요구사항, 실제 변수·클래스·테이블 이름을 그대로 옮기지 않습니다. 이해에 필요한 역할 이름과 가상의 최소 예시로 바꿉니다.
- 서비스에 종속된 이름은 `serviceSpecificAuthToken` → `authToken`처럼 보편적인 이름으로 바꿉니다. 주제와 무관한 에러 처리, 로깅, 방어 로직은 `// ...생략`으로 줄이거나 예시에서 제외해 **핵심 로직**이 드러나게 합니다. 실제 구현에서 이 로직을 제거했다는 뜻으로 쓰지 않습니다.
- 계정 정보, 사용자 데이터, 접근 키, 내부 URL과 로그 원문을 포함하지 않습니다. 코드 공개 여부와 별개로 대화 내용의 공개 가능성을 검토합니다.
- 수백 줄의 구현을 복사하기보다 핵심 **인터페이스와 개념**, 상태의 소유권, 데이터 흐름을 설명합니다. 데이터가 A에서 B로 변환되는 흐름은 **의사코드(Pseudocode)**나 간결한 스니펫으로 표현합니다.
- 아키텍처 변화나 복잡한 비동기 처리 흐름은 장황한 코드와 텍스트보다 **다이어그램**을 우선 사용합니다. 내부 이름은 추상화하고, 도식과 함께 읽을 수 있는 텍스트 설명도 제공합니다.
- 제안 단계의 구조를 그릴 때는 **검토안**이라고 표시합니다. 다이어그램이 실제 구현이나 채택의 증거처럼 보이지 않게 합니다.

## 2. HOW보다 WHY와 검증된 임팩트에 집중합니다

어떤 기술을 사용했는지 나열하는 데 그치지 않습니다. 먼저 프로젝트의 맥락, 실제 요구사항, 관찰한 증상과 제약을 설명하고, **왜 서비스와 사용자에게 중요한 문제였는지** 도입부에서 짚습니다.

이어 실제로 검토한 대안을 같은 기준으로 비교합니다. 팀의 트래픽, 가용 리소스와 제약이 선택에 어떤 영향을 주었는지 설명하고, 선택으로 얻는 점과 감수하는 비용인 **트레이드오프(Trade-off)**를 함께 씁니다. 선택하지 않은 대안이 실제로 없었다면 새로 만들어 넣지 않습니다.

권장 흐름은 **문제와 요구사항 → 고민 → 실제 대안과 트레이드오프 → 선택과 이유 → 검증 결과 → 남은 질문**입니다. 자료에 없는 단계는 생략하거나 미확인으로 밝힙니다. 형식을 채우려고 대안이나 선택 이유를 만들어 내지 않습니다.

결론은 구현을 마쳤다는 설명에서 끝내지 않습니다. **확인된 성능·사용자 경험·개발자 경험(DX)의 변화**를 설명합니다. 측정 자료가 있으면 비교 조건과 함께 임팩트를 수치화하고, 자료가 없으면 확인한 변화와 남은 한계를 적습니다. 원문의 로딩 속도 개선율 같은 예시를 실제 성과로 사용하지 않습니다.

## 3. 친절한 동료와 대화하듯 겸손하게 씁니다

딱딱한 논문이나 보고서보다 동료와 기술 리뷰를 나누는 느낌으로 친절하고 담백하게 씁니다. **~해요, ~했습니다체**를 사용하고, 본문을 `~이다`, `~함` 같은 건조한 어투로 채우지 않습니다.

실패한 시도와 시행착오도 관찰 결과와 한계, 다음 판단에 미친 영향을 투명하게 설명합니다. 완벽함을 과시하기보다 독자와 함께 배울 수 있는 태도를 유지합니다. 실제 실패 기록이 없다면 회고를 극적으로 만들기 위한 실패 사례를 추가하지 않습니다.

독자의 연차나 도메인이 다를 수 있음을 가정합니다. 생소한 사내 용어, 최신 기술 개념과 약어는 처음 등장할 때 **1~2줄의 쉬운 주석이나 부연 설명**을 붙입니다. 설명에 도움이 되지 않는 비유와 수식어는 줄입니다.

## 4. 소제목과 짧은 호흡으로 시각적 피로도를 낮춥니다

모바일 화면이나 바쁜 업무 중에도 글의 흐름을 따라갈 수 있게 작성합니다.

- **두괄식 소제목:** 목차만 읽어도 전체 흐름을 알 수 있도록 요점을 담은 완전한 문장이나 직관적인 구로 씁니다. `렌더링 최적화`보다 `불필요한 리렌더링을 막기 위해 렌더링 페이즈를 분리하다`처럼 무엇을 왜 했는지 보여 줍니다. 단, 실제로 수행한 내용일 때만 이런 표현을 사용합니다.
- **짧은 문장과 문단:** 한 문장에 여러 인과관계를 몰아넣지 않고 끊어 씁니다. 한 문단은 하나의 생각을 담으며, 작성 화면에서 **4~5줄을 넘는 문단은 줄바꿈**하여 나눕니다.
- **볼드체:** 바쁜 독자가 빠르게 훑는 **스키밍(Skimming)**을 하더라도 핵심을 놓치지 않도록 문단에서 가장 중요한 **키워드나 검증된 결과값**을 굵게 표시합니다. 문단 전체를 굵게 만들지는 않습니다.
- 도입부에는 핵심 문제와 결론을 먼저 밝힙니다. 나란히 비교할 정보는 표, 순서나 병렬 항목은 목록으로 표현합니다.

## 5. TIL은 그날의 사고 흐름과 근거 범위를 남깁니다

- 날짜는 **한국 시간(Asia/Seoul)**의 하루를 기준으로 합니다. `content/til/YYYY-MM-DD.md` 파일명과 frontmatter의 `date`를 일치시킵니다.
- `topics`에는 달력에서 읽을 수 있는 짧은 큰 주제를 씁니다. 본문은 대화 나열보다 프로젝트의 요구사항, 고민, 선택 이유와 결론을 중심으로 재구성합니다.
- 접근 가능한 대화만 근거로 사용합니다. 원문 대신 요약만 확인했다면 그렇게 밝히고, 일부 대화를 전체 Work 기록처럼 표현하지 않습니다.
- 확인된 결론이 없으면 미정이라고 씁니다. 후속 질문을 새로 도출했다면 당시의 결정과 구별합니다.
- 공개 초안에서 근거가 충분하지 않으면 `draft: true`로 두거나 미확인 범위를 명시합니다. `visibility: private`와 `draft: true`인 일지는 공개 목록·달력·상세 경로·sitemap에 노출하지 않습니다.

## 6. 사실과 성과는 확인한 근거 안에서 설명합니다

- 수치에는 측정 조건, 비교 기준과 출처를 붙입니다. 측정하지 않은 개선율, 처리 시간, 비용 절감액을 만들지 않습니다.
- 재현, 테스트, 로그 등으로 확인한 결과와 기대 효과를 구분합니다. 테스트 통과를 실제 운영 성능 개선으로 바꾸어 표현하지 않습니다.
- 사용자 결정, 어시스턴트 제안, 구현 상태, 추론을 구별합니다. 질문을 채택으로, 계획을 완료로 바꾸지 않습니다.
- 실제로 겪지 않은 실패, 검토하지 않은 대안, 확인되지 않은 선택 이유와 결론을 경험처럼 쓰지 않습니다. 원본 규칙에 있는 수치·대안·사례도 설명을 위한 예시로만 취급합니다.

## 게시 전 확인

독자가 문제의 이유와 선택 근거를 따라갈 수 있는지, 용어가 설명되었는지 확인합니다. 공개할 수 없는 정보와 근거 없는 수치·대안·결론이 없는지 읽어 봅니다. 검증하지 못한 범위는 솔직하게 남깁니다.
