# 블로그 SEO를 위한 정적 생성 선택 기록

## Goal

Next.js 블로그에서 공개 글 페이지를 어떤 렌더링 방식으로 제공할지 결정하고, 그 선택이 SEO에 어떤 조건을 제공하는지 설명한다.

이 문서에서 사용하는 용어는 다음과 같다.

- **SSR(Server-Side Rendering)**: 요청 시점마다 서버가 HTML을 생성하는 방식
- **SSG(Static Site Generation)**: 빌드 시점에 HTML을 미리 생성하는 방식
- **CSR(Client-Side Rendering)**: 브라우저에서 JavaScript 실행 후 주요 화면을 생성하는 방식
- **SEO(Search Engine Optimization)**: 검색엔진이 페이지를 발견, 크롤링, 색인, 이해하기 쉽게 만드는 기술적·콘텐츠적 최적화

## 문제 정의

블로그 글은 검색엔진이 안정적으로 발견하고 색인해야 한다. 이 프로젝트는 글 본문, 제목, 설명, 태그, 발행일이 Markdown 파일에 있고, 공개 페이지는 글 내용이 사용자별로 달라지지 않는다.

따라서 핵심 문제는 "요청마다 HTML을 새로 만들 필요가 있는가"가 아니라, "검색엔진이 JavaScript 실행에 덜 의존하고도 글의 핵심 정보를 읽을 수 있는가"다.

## 확인된 사실

- 프로젝트는 Next.js App Router 기반이다.
- 글 데이터는 `content/posts`의 Markdown 파일에서 읽는다.
- 글 상세 페이지는 `generateStaticParams()`로 공개 글의 slug 목록을 빌드 시점에 제공한다.
- 글 상세 페이지와 태그 페이지는 `dynamicParams = false`를 사용한다.
- 글별 metadata는 `title`, `description`, canonical URL, Open Graph, Twitter metadata를 생성한다.
- 글 상세 페이지는 `BlogPosting` JSON-LD를 포함한다.
- `sitemap.xml`, `robots.txt`, `feed.xml`이 제공된다.

## 추론

현재 글 데이터는 파일 기반이고, 공개 글 페이지는 요청별 사용자 상태나 쿠키에 의존하지 않는다. 이 조건에서는 SSR보다 SSG가 더 적합하다.

이 추론은 다음 연결에 근거한다.

1. Markdown 파일은 빌드 시점에 읽을 수 있다.
2. 공개 글의 URL 목록은 빌드 시점에 계산할 수 있다.
3. 글 본문과 metadata는 사용자별로 달라지지 않는다.
4. 따라서 요청 시점 서버 렌더링은 필수 조건이 아니다.

## 결정

공개 블로그 페이지는 SSR이 아니라 SSG를 기본 전략으로 둔다.

구현에서는 동적 글 상세 페이지와 태그 페이지에 `generateStaticParams()`를 사용해 빌드 시점에 생성할 경로 목록을 제공한다. `dynamicParams = false`는 이 목록 밖의 동적 경로를 요청 시점에 새로 만들지 않고 404로 처리한다.

별도의 `dynamic = 'error'` 설정은 사용하지 않는다. 현재 구조에서는 이미 파일 기반 데이터와 `generateStaticParams()`만으로 정적 생성이 가능하다. `dynamic = 'error'`는 SEO 점수를 직접 올리는 기능이 아니라, 요청 시점 데이터 의존을 빌드 단계에서 막는 방어적 제약이다. 이 제약은 나중에 미리보기, 요청 헤더 기반 분기, 검색 파라미터 기반 화면이 필요할 때 불필요한 마찰이 될 수 있으므로 현재 변경에서는 제외한다.

## 선택 근거

### 1. 검색엔진이 초기 HTML에서 글을 읽을 수 있다

SSG는 빌드 시점에 글 본문이 포함된 HTML을 만든다. 검색엔진은 JavaScript 실행 결과를 기다리지 않아도 제목, 설명, 본문을 확인할 수 있다.

이것은 검색 순위 상승의 충분조건은 아니다. 다만 크롤링 안정성과 색인 가능성을 높이는 조건과 일치한다.

### 2. canonical URL과 metadata를 페이지별로 고정할 수 있다

글별 metadata가 빌드 결과에 포함되면 검색엔진과 소셜 플랫폼은 각 글의 대표 URL, 제목, 설명, 공유 이미지를 더 일관되게 해석할 수 있다.

이 효과는 metadata가 정확히 생성되고, 배포 환경의 `NEXT_PUBLIC_SITE_URL`이 실제 도메인을 가리킨다는 조건에서 성립한다.

### 3. sitemap과 RSS가 공개 URL 발견을 돕는다

`sitemap.xml`은 검색엔진이 공개 URL 목록을 찾는 데 도움을 준다. `feed.xml`은 구독기와 외부 수집기가 최신 글을 찾는 별도 경로를 제공한다.

이 둘은 색인을 보장하지 않는다. 다만 URL 발견 경로를 명시한다는 점에서 SEO에 유리한 보조 조건이다.

### 4. 블로그의 데이터 변경 주기와 맞다

파일 기반 블로그는 글을 추가하거나 수정할 때 보통 빌드와 배포가 함께 일어난다. 이 흐름에서는 요청마다 HTML을 다시 만들 필요가 작다.

SSG는 이 특성과 맞기 때문에 런타임 서버 부하와 캐시 무효화 복잡도를 줄인다.

## 대안과 트레이드오프

### CSR

CSR은 브라우저에서 JavaScript가 실행된 뒤 주요 콘텐츠가 만들어진다.

장점:

- 서버 렌더링 구성이 단순할 수 있다.
- 사용자 상호작용 중심 앱에는 적합할 수 있다.

단점:

- 초기 HTML에 글 본문이 부족할 수 있다.
- 검색엔진이 JavaScript 렌더링을 완료해야 글을 정확히 읽을 수 있다.
- 블로그처럼 본문 색인이 중요한 페이지에는 불리한 조건이 생긴다.

판단:

이 프로젝트의 공개 글 페이지에는 맞지 않는다. 글 본문은 초기 HTML에 포함되는 편이 더 안정적이다.

### SSR

SSR은 요청마다 서버가 HTML을 생성한다.

장점:

- 요청별 사용자 상태, 지역, 권한, 실시간 데이터 반영에 적합하다.
- 데이터가 자주 바뀌고 빌드 없이 즉시 반영해야 할 때 유리하다.

단점:

- 모든 요청에서 서버 렌더링 비용이 발생한다.
- 캐시 전략, 장애 대응, 서버 부하 관리가 더 중요해진다.
- 이 블로그처럼 파일 기반 공개 글에는 요청 시점 계산의 이점이 작다.

판단:

현재 공개 글에는 필요한 조건이 아니다. 관리자 화면, 미리보기, 사용자별 대시보드가 생긴다면 해당 페이지 단위로 SSR을 검토할 수 있다.

### SSG

SSG는 빌드 시점에 HTML을 만든다.

장점:

- 초기 HTML에 글 본문과 metadata를 포함할 수 있다.
- 요청 시점 렌더링 비용이 작다.
- 빌드 결과가 고정되어 동작을 검증하기 쉽다.
- 파일 기반 블로그의 배포 흐름과 잘 맞는다.

단점:

- 글 수정 후 반영하려면 다시 빌드하고 배포해야 한다.
- 사용자별 콘텐츠나 요청별 데이터에는 적합하지 않다.
- 글 수가 매우 많아지면 빌드 시간이 증가할 수 있다.

판단:

현재 조건에서 가장 적합하다. 단, 글 수 증가나 CMS 도입 이후에는 ISR 또는 서버 렌더링을 다시 검토해야 한다.

### ISR

ISR(Incremental Static Regeneration)은 정적 페이지를 만들되, 일정 조건에서 재생성하는 방식이다.

장점:

- 정적 HTML의 장점을 유지하면서 콘텐츠 갱신을 더 유연하게 처리할 수 있다.
- CMS나 DB에서 글을 가져오는 구조로 바뀌었을 때 유용하다.

단점:

- 재검증 주기, stale 응답, 캐시 무효화 정책을 설계해야 한다.
- 파일 기반 글과 배포가 함께 일어나는 현재 구조에서는 복잡도가 먼저 증가할 수 있다.

판단:

현재는 필요하지 않다. DB나 CMS를 도입해 글 변경과 배포가 분리되면 다시 검토한다.

## 최종 판단

현재 프로젝트의 공개 블로그 페이지에는 SSG가 가장 적합하다.

근거는 다음과 같다.

- 글 데이터가 빌드 시점에 접근 가능한 Markdown 파일이다.
- 공개 글 페이지는 사용자별 요청 상태에 의존하지 않는다.
- SEO에 필요한 본문, metadata, canonical URL, 구조화 데이터를 초기 HTML에 포함할 수 있다.
- 요청 시점 렌더링의 장점보다 정적 생성의 단순성과 안정성이 더 크다.

따라서 이번 변경의 핵심은 "SSR을 적용했다"가 아니라, **블로그 공개 페이지를 정적 생성 대상으로 명확히 고정하고 그 전제를 문서화했다**는 것이다.

## 검증 방법

다음 명령으로 정적 생성 전제가 깨지지 않았는지 확인한다.

```bash
pnpm test
pnpm typecheck
pnpm lint
pnpm build
```

`pnpm build` 결과에서 `/posts/[slug]`와 `/tags/[tag]`가 `SSG`로 표시되어야 한다.

```text
●  (SSG)      prerendered as static HTML (uses generateStaticParams)
```

## 남은 불확실성

다음 내용은 현재 코드만으로 결론을 낼 수 없다.

- 실제 검색 유입 증가 여부
- 검색 순위 변화
- Core Web Vitals의 운영 환경 측정값
- 검색엔진별 크롤링 빈도 변화

이 값들은 배포 후 Search Console, 접근 로그, 성능 측정 도구를 통해 확인해야 한다.
