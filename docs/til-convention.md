# TIL 작성과 달력 표시 컨벤션

TIL은 **그날 사용자가 실제로 한 질문과 그에 대한 답변**을 남기는 개발 공부 일지입니다. 로컬 대화 목록에서 질문을 찾고, 답변에 필요한 맥락과 확인한 결론만 정리합니다.

이 문서는 `content/til`의 일지 작성과 홈 달력, `/til` 게시판, 날짜별 상세 페이지의 표시 기준입니다. 문체·추상화·근거 표시는 [글쓰기 컨벤션](./writing-convention.md)을 함께 따릅니다.

## 1. 대화와 접근 가능한 Work 기록을 날짜별로 모읍니다

- 기본 자료는 사용자와 나눈 대화 및 **접근 가능한 Work 대화**입니다. Work 기록을 포함해 그날의 관련 대화를 가능한 범위에서 확인하되, 접근하지 못한 대화를 읽었다고 표현하지 않습니다.
- 하루는 **한국 시간(Asia/Seoul) 00:00부터 다음 날 00:00 직전까지**입니다. 원본 시각에 시간대가 있으면 한국 시간으로 변환합니다. 날짜를 확인할 수 없는 대화는 특정 날짜의 경험으로 배정하지 않습니다.
- 원문 전체, 일부 메시지, 전달받은 요약 중 무엇을 확인했는지 구분합니다. 여러 대화에 걸친 동일한 고민은 연결하되, 별개 프로젝트의 질문을 하나의 설계 결정으로 합치지 않습니다.
- 대화 생성일이나 마지막 수정일 대신 **실제 질문·답변 메시지의 시각**으로 날짜를 정합니다. 며칠간 이어진 대화는 그날 다룬 질문만 해당 날짜에 넣습니다. 학습과 관계없는 단순 실행·승인 요청과 개인정보는 일지 소재에서 제외합니다.
- 자료가 없거나 접근이 안 되면 **미확인·작성 보류**로 남깁니다. 대화가 조회되지 않았다는 이유로 그날 공부하지 않았다고 단정하거나, 예시 경험으로 빈 기록을 채우지 않습니다.
- 접근 권한을 우회하거나 새 권한을 임의로 확보하지 않습니다. 작성에 필요한 범위와 확인하지 못한 자료를 작업 결과에 알립니다.

## 2. 사용자가 한 질문에 답하는 Q&A로만 작성합니다

- 본문은 **`## Q. 실제 질문`과 `**A.** 답변`**을 반복하는 형식으로만 작성합니다. 질문의 말투는 다듬어도 되지만 원래 의도와 조건을 바꾸거나 묻지 않은 질문을 만들어 넣지 않습니다.
- **관련 개념을 전부 정리하지 않습니다.** 사용자가 한 질문에 먼저 직접 답하고, 이해에 필요한 개념·이유·짧은 예시만 답변 안에 덧붙입니다. 프로젝트 전체 개념집, API 목록, 일반적인 학습 로드맵으로 확장하지 않습니다.
- “개념을 전부 알려 달라”는 과거 요청도 TIL에서는 당시의 핵심 질문과 후속 질문으로 압축합니다. 같은 질문의 반복·정정은 최종 확인된 답변으로 합치고, 서로 다른 날짜의 질문을 한 날짜로 옮기지 않습니다.
- 로컬 실행 질문은 실제로 물은 명령·오류·원인·확인 결과에 답합니다. 실행 환경의 모든 기초 개념을 나열하지 않습니다.
- 별도 회고·일반론·체크리스트로 본문을 채우지 않습니다. 마지막 기록 범위도 `Q. 이 기록은 어떤 대화를 바탕으로 했나요?`와 답변으로 작성합니다.

답변에 필요한 경우에만 아래 내용을 포함합니다. 자료에서 확인되는 단계만 사용하고, 실제 결정이 없으면 미정이라고 씁니다.

| 흐름                   | 남길 내용                                                            |
| ---------------------- | -------------------------------------------------------------------- |
| 프로젝트와 맥락        | 어떤 프로젝트에서 무엇을 하려 했는지                                 |
| 요구사항과 문제의 이유 | 어떤 요건·제약·관찰 때문에 고민이 시작됐는지, 사용자에게 왜 중요한지 |
| 고민과 대안            | 실제로 비교한 접근, 각 대안의 장점·비용·한계                         |
| 선택과 이유            | 사용자가 실제로 선택한 것과 그 판단의 근거                           |
| 결론과 검증            | 확인된 결과·실패·한계, 아직 결정하지 못한 조건                       |
| 후속 질문              | 다음에 확인할 점. 작성 시 새로 도출한 질문은 당시의 결정과 구분      |

**사용자의 질문, 계획, 어시스턴트의 제안, 실제 채택, 구현 완료, 검증된 성과**를 서로 구별합니다. 제안을 받았다는 사실만으로 사용자가 그 구조를 선택했다고 쓰지 않습니다. 비교한 대안이나 선택 이유가 기록에 없으면 만들어 넣지 않습니다.

대화 표현은 읽기 좋은 경어체로 다듬고, 용어는 답변에 필요한 만큼만 쉽게 풀이합니다. 답변 첫 문장에 결론을 쓰되, 결론이 미정이면 그 상태를 먼저 밝힙니다. 마지막 Q&A에는 어떤 자료를 바탕으로 재구성했는지 **기록의 범위**를 남깁니다. 원문 전체를 그대로 공개할 필요는 없습니다.

## 3. 하루의 일지는 날짜 하나와 파일 하나로 연결합니다

- 파일은 `content/til/YYYY-MM-DD.md`에 작성합니다. 파일명과 frontmatter의 `date`를 일치시킵니다.
- 같은 날 여러 프로젝트를 다뤘다면 날짜별 일지 안에서 주제를 구분합니다. 홈·게시판·상세 페이지는 같은 일지 자료를 사용합니다.
- `title`은 하루의 핵심 질문이나 결론, `description`은 확인된 질문과 답변의 짧은 요약입니다. `topics`는 **실제 질문과 연결되는 짧은 키워드**의 목록입니다. 본문에 없는 개념이나 대화에 나오지 않은 기술을 달력 키워드로 넣지 않습니다.

다음은 구조를 설명하는 템플릿입니다. 예시 문구를 실제 경험이나 결정으로 게시하지 않습니다.

```md
---
date: '2026-10-29'
title: '그날 고민한 핵심 질문'
description: '확인된 요구사항과 고민, 선택 또는 미정 상태의 요약'
topics:
  - 큰 주제
draft: true
visibility: public
---

## Q. 그날 실제로 물었던 질문은 무엇인가요?

**A.** 질문에 직접 답합니다. 필요한 이유와 확인한 결과만 이어서 설명합니다.

## Q. 이어서 물었던 질문은 무엇인가요?

**A.** 당시 확인한 답변을 씁니다. 제안만 있었다면 구현 완료로 바꾸지 않습니다.

## Q. 이 기록은 어떤 대화를 바탕으로 했나요?

**A.** 해당 날짜에 확인한 로컬 대화와 자료의 범위를 밝힙니다. 나중에 보완했다면 보완 날짜를 덧붙입니다.
```

## 4. 홈 달력에는 큰 주제를 불릿으로 표시합니다

- 홈에 **월별 달력**을 표시하고, 기록이 있는 날짜에 `topics`를 **크고 읽기 쉬운 불릿**으로 보여 줍니다. 자세한 대화를 작은 날짜 칸에 모두 넣지 않습니다.
- 날짜에 마우스를 올리면 그날의 제목과 요약을 볼 수 있게 합니다. **키보드 포커스에도 같은 요약**을 제공하고, Escape로 닫을 수 있게 합니다. 요약 위로 포인터를 옮겨도 읽을 수 있어야 합니다.
- TIL 공개가 켜져 있을 때 **날짜를 클릭하거나 Enter로 활성화하면 `/til/YYYY-MM-DD`의 해당 일지**로 이동합니다. 상세에는 그날의 질문과 답변을 보여 줍니다.
- 터치 환경에서는 호버에 의존하지 않습니다. 달력 아래에도 큰 주제와 요약을 표시하고, 날짜를 한 번 탭하면 상세로 이동하게 합니다.
- 기록이 없는 날짜는 상세 링크로 만들지 않습니다. 이전 달·다음 달·이번 달 이동을 제공하고, 기록이 없는 달에는 빈 상태를 알립니다.
- 날짜 표에는 요일과 월을 알 수 있는 의미 구조를 유지하고, 링크·버튼의 키보드 포커스를 보이게 합니다. 작은 화면에서도 가로 넘침 없이 읽을 수 있어야 합니다.

## 5. TIL 게시판과 상세 페이지는 같은 공개 기록을 보여 줍니다

`/til` 게시판은 공개 일지를 **날짜 내림차순**으로 모읍니다. 날짜·제목·요약·키워드를 보여 주고, 목록과 달력에서 같은 날짜의 상세 페이지로 이동하게 합니다.

상세 페이지에는 날짜, 키워드, 질문·답변과 기록의 범위를 표시합니다. `draft: true` 또는 `visibility: private`인 일지는 **달력·게시판·상세 경로·sitemap에서 제외**합니다. 공개되지 않은 날짜는 404로 응답합니다.

전체 TIL 공개 여부는 `features/til/config/til-publication.ts`의 `IS_TIL_PUBLISHED`를 따릅니다. `false`이면 Study Stamp에는 날짜와 `topics`만 표시하고, 제목·요약·본문·게시판·상세 경로·sitemap은 숨깁니다. **키워드와 TIL 작성 요청만으로 이 공개 설정을 변경하지 않습니다.** 로컬 실행도 같은 설정을 유지합니다.

## 6. 공개할 수 있는 근거만 추상화해 사용합니다

- 이 블로그는 면접관도 읽는 공개 기술 기록입니다. **면접 준비용 Q&A, 예상 질문, 모범 답변, 답변 전략·키워드와 개인 지원 내용은 게시 소재에서 제외합니다.** 실제 개발 중 생긴 기술 질문과 문제 해결을 중심으로 작성합니다.
- 제외 대상은 본문뿐 아니라 제목·요약·`topics`·Study Stamp 키워드·기록 범위에도 남기지 않습니다. 면접 준비 기록의 이름만 일반 학습 주제로 바꿔 게시하지 않습니다. **같은 날짜에 개발 기록도 있으면 해당 내용은 유지하고 제외 대상만 제거합니다.** 제외한 내용만 있는 날짜는 일지와 달력 기록을 만들지 않고, 다른 경험으로 채우지 않습니다.
- 불필요한 개인정보, 계정 정보, 사내 비공개 요구사항·로직, 내부 URL, 접근 키, 사용자 데이터와 로그 원문을 포함하지 않습니다. 내부 이름은 역할과 개념 중심으로 바꿉니다.
- 대화나 Work 기록에 접근할 수 있다는 사실이 그 내용을 모두 외부에 공개해도 된다는 뜻은 아닙니다. 공개할 수 없는 부분은 생략하거나 충분히 추상화합니다.
- 근거 없는 전문적 주장, 측정하지 않은 수치, 실제로 겪지 않은 실패, 검토하지 않은 대안과 확인되지 않은 결론을 추가하지 않습니다.
- 원문이 비공개라면 계정·대화 링크나 원문 전체를 공개 파일에 옮기지 않고, 확인한 범위를 설명합니다. 검증용 자료도 공개할 필요가 없는 내용은 게시물에 넣지 않습니다.
- `draft`와 `visibility`는 사이트 노출 설정입니다. **공개 저장소의 파일이나 Git 이력을 비공개로 만드는 기능은 아니므로**, 민감한 원문은 애초에 커밋하지 않습니다.

## 7. 매일 작성·원격 푸시는 목표와 실행 상태를 구분합니다

사용자가 요청한 장기 목표는 **매일 그날의 대화를 바탕으로 공부 일지를 작성하고 원격 저장소에 푸시하는 것**입니다. 로컬 대화에서 여러 날짜의 기록을 한 번에 보충하는 작업과 매일 실행되는 자동화는 구분합니다. **대화 자동 수집·매일 작성·정기 푸시 자동화는 아직 설정하지 않았습니다.** 이 문서를 추가했다는 사실만으로 자동화가 실행된다고 설명하지 않습니다.

일지를 추가하거나 수정할 때는 실제 질문과의 연결, Q&A 형식, 확인한 대화 범위와 날짜, 사실·제안·결정의 구분, 공개 범위, 메타데이터와 표시 결과를 점검합니다. 오류를 고칠 때는 뒤늦게 알게 된 내용을 당시의 결정처럼 덮어쓰지 않습니다. 수정 시점과 새로 확인된 내용을 구분합니다.

파일을 검증한 뒤 작업 브랜치에 커밋·푸시하고 결과를 보고합니다. 머지·운영 배포나 정기 자동화 설정은 해당 작업의 승인 범위를 따릅니다. 자동화를 구현하기 전에는 기록에 접근할 수 있는 범위, 실행 환경과 실제 실행 상태를 확인해야 합니다.
