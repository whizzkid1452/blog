# TIL 작성과 달력 표시 컨벤션

TIL은 **그날 내가 어떤 질문을 했고, 무엇을 확인하면서 생각을 바꿨으며, 왜 그 선택을 했는지** 남기는 개발 공부 일지입니다. 완성한 기능이나 전달받은 답변보다 질문에서 배움으로 이어진 과정을 중심으로 씁니다. 작은 질문 하나를 짧게 기록해도 충분합니다.

이 문서는 `content/til`의 일지 작성과 홈 달력, `/til` 게시판, 날짜별 상세 페이지의 표시 기준입니다. 문체·추상화·근거 표시는 [글쓰기 컨벤션](./writing-convention.md)을 함께 따릅니다.

## 1. 대화와 접근 가능한 Work 기록을 날짜별로 모읍니다

- 기본 자료는 사용자와 나눈 대화 및 **접근 가능한 Work 대화**입니다. Work 기록을 포함해 그날의 관련 대화를 가능한 범위에서 확인하되, 접근하지 못한 대화를 읽었다고 표현하지 않습니다.
- 하루는 **한국 시간(Asia/Seoul) 00:00부터 다음 날 00:00 직전까지**입니다. 원본 시각에 시간대가 있으면 한국 시간으로 변환합니다. 날짜를 확인할 수 없는 대화는 특정 날짜의 경험으로 배정하지 않습니다.
- 원문 전체, 일부 메시지, 전달받은 요약 중 무엇을 확인했는지 구분합니다. 여러 대화에 걸친 동일한 고민은 연결하되, 별개 프로젝트의 질문을 하나의 설계 결정으로 합치지 않습니다.
- 자료가 없거나 접근이 안 되면 **미확인·작성 보류**로 남깁니다. 대화가 조회되지 않았다는 이유로 그날 공부하지 않았다고 단정하거나, 예시 경험으로 빈 기록을 채우지 않습니다.
- 접근 권한을 우회하거나 새 권한을 임의로 확보하지 않습니다. 작성에 필요한 범위와 확인하지 못한 자료를 작업 결과에 알립니다.

## 2. 내가 던진 질문을 따라 사고의 변화를 씁니다

### 질문을 고른 뒤 필요한 답변과 결과를 연결합니다

먼저 대화에서 **사용자가 직접 던진 질문, 재질문, 수정 요청과 선택**을 찾습니다. 무엇을 몰랐는지, 어떤 답변으로도 충분하지 않았는지 드러나는 질문을 중심에 둡니다. 어시스턴트가 오래 설명했거나 많은 파일을 수정했다는 이유만으로 주요 주제를 고르지 않습니다.

소제목은 `로컬 검증 완료`보다 `테스트가 통과하면 실제 소리도 확인한 걸까?`처럼 질문의 대상과 고민이 보이게 씁니다. 질문형은 원문 인용이 아니라 의미를 유지한 재구성일 수 있습니다. 원문을 그대로 확인한 문장에만 인용 표시를 사용하고, 요약만 확인했다면 정확한 발언처럼 따옴표로 꾸미지 않습니다.

### 질문, 확인한 근거, 선택 이유를 연결합니다

각 주제는 다음 순서로 읽히게 작성합니다. 모든 항목을 별도 소제목으로 만들거나 같은 틀을 반복할 필요는 없습니다.

1. **어떤 상황에서 무엇이 궁금했는가:** 프로젝트의 목적과 당시의 제약을 짧게 설명하고, 내가 한 질문을 제시합니다.
2. **처음에는 어떻게 생각했는가:** 기존 이해나 가설이 대화에 있다면 씁니다. 첫 질문만으로 당시의 믿음이나 감정을 추정하지 않습니다.
3. **무엇을 확인하거나 다시 물었는가:** 문서·코드·실험에서 확인한 근거와 실제 후속 질문을 연결합니다. 질문이 바뀌었다면 어떤 정보 때문에 바뀌었는지 씁니다.
4. **왜 그 선택을 했는가:** 실제로 비교한 선택지, 중요하게 본 기준, 선택과 감수한 비용을 설명합니다. `유지보수가 쉬워서` 같은 일반론 대신 그 상황의 요건과 연결합니다.
5. **어디까지 알게 됐고 무엇이 남았는가:** 확인한 결과와 한계, 다음에 쓸 판단 기준을 남깁니다. 해결하지 못한 질문도 유효한 TIL입니다.

**질문 → 확인·재질문 → 판단 기준 → 선택 또는 미정 → 배운 점**이 읽혀야 합니다. 코드와 테스트 수치는 판단의 근거가 될 때 필요한 만큼만 둡니다. 긴 검증 목록과 구현 설명은 접이식 영역이나 별도 기술 글로 분리합니다. 하루의 모든 작업을 빠짐없이 보고하거나 답변을 길게 요약하는 것이 목표는 아닙니다.

### 기록에 있는 판단과 글을 쓰면서 얻은 해석을 구분합니다

**사용자의 질문, 계획, 어시스턴트의 제안, 실제 채택, 구현 완료, 검증된 성과**를 서로 구별합니다. 질문을 했다는 사실만으로 답변을 이해·동의·채택했다고 쓰지 않습니다. 후속 요청이 구현 선택을 보여 주더라도 이유까지 자동으로 확인되는 것은 아닙니다.

비교한 대안이나 선택 이유가 기록에 없으면 만들어 넣지 않습니다. `선택은 확인되지만 당시 이유는 기록에 없습니다` 또는 `제안까지 받았고 선택은 미정입니다`처럼 확인 가능한 상태로 남깁니다. 질문 목록만 확인한 경우에는 실행 기록을 덧붙여도 당시의 고민이나 동기가 복원됐다고 표현하지 않습니다.

대화 표현은 읽기 좋은 1인칭 경어체로 다듬고, 용어는 쉽게 풀이합니다. 도입에는 그날의 핵심 질문과 도달한 이해 또는 미정 상태를 짧게 밝힙니다. 뒤늦게 정리한 배움·적용 기준·후속 질문은 **글을 정리하며 얻은 기준**이라고 구분해, 당시부터 알고 선택한 이유처럼 소급하지 않습니다. 본문 끝에는 어떤 자료를 바탕으로 재구성했는지 **기록의 범위**를 남깁니다.

## 3. 하루의 일지는 날짜 하나와 파일 하나로 연결합니다

- 파일은 `content/til/YYYY-MM-DD.md`에 작성합니다. 파일명과 frontmatter의 `date`를 일치시킵니다.
- 같은 날 여러 프로젝트를 다뤘다면 날짜별 일지 안에서 주제를 구분합니다. 홈·게시판·상세 페이지는 같은 일지 자료를 사용합니다.
- `title`은 하루의 핵심 질문이나 결론, `description`은 확인된 고민과 상태의 짧은 요약입니다. `topics`는 **달력에서 크게 읽을 수 있는 짧은 큰 주제**의 목록입니다.

다음은 구조를 설명하는 템플릿입니다. 예시 문구를 실제 경험이나 결정으로 게시하지 않습니다.

```md
---
date: '2026-10-29'
title: '그날 내가 던진 핵심 질문'
description: '질문에서 확인한 내용과 선택 이유, 또는 남아 있는 판단의 요약'
topics:
  - 큰 주제
draft: true
visibility: public
---

그날의 핵심 질문과 확인한 이해, 또는 아직 결정하지 못한 범위를 짧게 설명합니다.

## 실제로 했던 질문의 요지가 드러나는 소제목

어떤 상황에서 질문했는지 씁니다. 처음 생각은 기록에 있을 때만 덧붙입니다.

무엇을 확인하거나 다시 물었고, 그 근거가 판단에 어떤 영향을 줬는지 연결합니다.

실제 선택과 이유, 감수한 비용을 씁니다. 선택하지 않았다면 미정 상태를 남깁니다.

확인한 결과와 한계를 적습니다. 정리하며 얻은 적용 기준은 당시 결정과 구분합니다.

## 기록의 범위

확인한 날짜, 질문 원문·일부 메시지·요약의 범위와 수정 시점을 적습니다.
```

## 4. 홈 달력에는 큰 주제를 불릿으로 표시합니다

- 홈에 **월별 달력**을 표시하고, 기록이 있는 날짜에 `topics`를 **크고 읽기 쉬운 불릿**으로 보여 줍니다. 자세한 대화를 작은 날짜 칸에 모두 넣지 않습니다.
- 날짜에 마우스를 올리면 그날의 제목과 요약을 볼 수 있게 합니다. **키보드 포커스에도 같은 요약**을 제공하고, Escape로 닫을 수 있게 합니다. 요약 위로 포인터를 옮겨도 읽을 수 있어야 합니다.
- **날짜를 클릭하거나 Enter로 활성화하면 `/til/YYYY-MM-DD`의 해당 일지**로 이동합니다. 상세에는 그날의 대화를 사고 흐름으로 재구성한 내용을 보여 줍니다.
- 터치 환경에서는 호버에 의존하지 않습니다. 달력 아래에도 큰 주제와 요약을 표시하고, 날짜를 한 번 탭하면 상세로 이동하게 합니다.
- 기록이 없는 날짜는 상세 링크로 만들지 않습니다. 이전 달·다음 달·이번 달 이동을 제공하고, 기록이 없는 달에는 빈 상태를 알립니다.
- 날짜 표에는 요일과 월을 알 수 있는 의미 구조를 유지하고, 링크·버튼의 키보드 포커스를 보이게 합니다. 작은 화면에서도 가로 넘침 없이 읽을 수 있어야 합니다.

## 5. TIL 게시판과 상세 페이지는 같은 공개 기록을 보여 줍니다

`/til` 게시판은 공개 일지를 **날짜 내림차순**으로 모읍니다. 날짜·제목·요약·큰 주제를 보여 주고, 목록과 달력에서 같은 날짜의 상세 페이지로 이동하게 합니다.

상세 페이지에는 날짜, 큰 주제, 요구사항·고민·대안·선택·결론의 본문과 기록의 범위를 표시합니다. `draft: true` 또는 `visibility: private`인 일지는 **달력·게시판·상세 경로·sitemap에서 제외**합니다. 공개되지 않은 날짜는 404로 응답합니다.

## 6. 공개할 수 있는 근거만 추상화해 사용합니다

- 불필요한 개인정보, 계정 정보, 사내 비공개 요구사항·로직, 내부 URL, 접근 키, 사용자 데이터와 로그 원문을 포함하지 않습니다. 내부 이름은 역할과 개념 중심으로 바꿉니다.
- 대화나 Work 기록에 접근할 수 있다는 사실이 그 내용을 모두 외부에 공개해도 된다는 뜻은 아닙니다. 공개할 수 없는 부분은 생략하거나 충분히 추상화합니다.
- 근거 없는 전문적 주장, 측정하지 않은 수치, 실제로 겪지 않은 실패, 검토하지 않은 대안과 확인되지 않은 결론을 추가하지 않습니다.
- 원문이 비공개라면 계정·대화 링크나 원문 전체를 공개 파일에 옮기지 않고, 확인한 범위를 설명합니다. 검증용 자료도 공개할 필요가 없는 내용은 게시물에 넣지 않습니다.
- `draft`와 `visibility`는 사이트 노출 설정입니다. **공개 저장소의 파일이나 Git 이력을 비공개로 만드는 기능은 아니므로**, 민감한 원문은 애초에 커밋하지 않습니다.

## 7. 매일 작성·원격 푸시는 목표와 실행 상태를 구분합니다

사용자가 요청한 장기 목표는 **매일 그날의 대화를 바탕으로 공부 일지를 작성하고 원격 저장소에 푸시하는 것**입니다. 달력·게시판과 수동으로 작성한 일지가 있다는 사실만으로 자동 수집·매일 작성·정기 푸시가 실행된다고 설명하지 않습니다. 자동화 여부는 실제 설정과 실행 기록으로 확인합니다.

일지를 추가하거나 수정할 때는 확인한 대화 범위와 날짜, 사실·제안·결정의 구분, 공개 범위, 메타데이터와 표시 결과를 점검합니다. 오류를 고칠 때는 뒤늦게 알게 된 내용을 당시의 결정처럼 덮어쓰지 않습니다. 수정 시점과 새로 확인된 내용을 구분합니다.

파일을 검증한 뒤 작업 브랜치에 커밋·푸시하고 결과를 보고합니다. 머지·운영 배포나 정기 자동화 설정은 해당 작업의 승인 범위를 따릅니다. 자동화를 구현하기 전에는 기록에 접근할 수 있는 범위, 실행 환경과 실제 실행 상태를 확인해야 합니다.

## 8. 게시 전에는 질문과 선택의 연결을 확인합니다

- 사용자의 실제 질문·재질문이 글의 중심에 있는가?
- 당시의 상황과 궁금했던 점을 처음 읽는 사람도 이해할 수 있는가?
- 어떤 근거가 판단을 바꿨는지, 또는 아직 판단하지 못했는지 드러나는가?
- 선택 이유가 일반적인 장점 나열이 아니라 실제 요구사항과 연결되는가?
- 답변·제안·구현 결과를 사용자의 생각이나 선택으로 바꾸지 않았는가?
- 대안·실패·동기를 꾸며 넣지 않았고, 뒤늦은 해석과 수정 시점을 구분했는가?
- 구현 목록과 검증 수치가 질문과 배움을 가리지 않는가?

## 9. 참고한 TIL 가이드와 이 블로그의 적용 기준

다음 자료를 2026년 10월 31일에 확인했습니다. 자료의 공통 취지는 참고하되, 질문·재질문과 선택 이유를 중심에 두는 구성은 이 블로그의 목적에 맞춘 기준입니다.
