# TIL 작성과 달력 표시 컨벤션

TIL은 **그날 어떤 요구사항 때문에 무엇을 고민했고, 어떤 선택과 결론에 도달했는지** 남기는 개발 공부 일지입니다. 대화의 시간순 나열보다 사용자의 사고 흐름을 중심으로 재구성합니다.

이 문서는 `content/til`의 일지 작성과 홈 달력, `/til` 게시판, 날짜별 상세 페이지의 표시 기준입니다. 문체·추상화·근거 표시는 [글쓰기 컨벤션](./writing-convention.md)을 함께 따릅니다.

## 1. 대화와 접근 가능한 Work 기록을 날짜별로 모읍니다

- 기본 자료는 날짜가 확인되는 **로컬 대화 기록과 접근 가능한 Work 대화**입니다. Work 기록을 포함해 그날의 관련 대화를 가능한 범위에서 확인하되, 접근하지 못한 대화를 읽었다고 표현하지 않습니다.
- 하루는 **한국 시간(Asia/Seoul) 00:00부터 다음 날 00:00 직전까지**입니다. 원본 시각에 시간대가 있으면 한국 시간으로 변환합니다. 날짜를 확인할 수 없는 대화는 특정 날짜의 경험으로 배정하지 않습니다.
- 원문 전체, 일부 메시지, 전달받은 요약 중 무엇을 확인했는지 구분합니다. 여러 대화에 걸친 동일한 고민은 연결하되, 별개 프로젝트의 질문을 하나의 설계 결정으로 합치지 않습니다.
- 자료가 없거나 접근이 안 되면 **미확인·작성 보류**로 남깁니다. 대화가 조회되지 않았다는 이유로 그날 공부하지 않았다고 단정하거나, 예시 경험으로 빈 기록을 채우지 않습니다.
- 접근 권한을 우회하거나 새 권한을 임의로 확보하지 않습니다. 작성에 필요한 범위와 확인하지 못한 자료를 작업 결과에 알립니다.

## 2. 하루의 대표 주제 하나를 세 부분으로 정리합니다

- 여러 대화가 있어도 근거를 확인할 수 있는 **대표 기술 주제 하나**를 선택합니다. 서로 다른 프로젝트나 질문을 묶지 않습니다.
- 본문은 일기체나 경어체 대신 간결한 **객관적 명사형**(~함, ~임, ~됨, ~필요)으로 작성합니다. 하이픈 불릿 하나에 핵심 하나, 기준·원인·결론은 필요한 곳만 정상적인 마크다운 굵게 표시로 강조합니다.
- 개요 첫 불릿에 **질문 요지**를 적습니다. 사용자가 그날 실제로 물어보거나 요청한 내용을 읽기 쉽게 요약하고, 판단에 영향을 준 후속 질문이 있으면 함께 남깁니다. 이어서 배경과 제약을 2~3줄로 설명합니다.
- 핵심 내용에 **답변에서 고른 방법**과 **고른 이유**를 적습니다. 당시 답변이나 비교 시험에서 실제로 선택한 방법을 밝혀, 어떤 코드, 관찰, 요구사항이나 제약이 그 판단을 뒷받침했는지 연결합니다. 대안과 트레이드오프는 실제 대화에서 비교한 경우에 남깁니다. 이해에 도움이 되면 짧은 코드 예시나 흐름도를 덧붙입니다.
- **질문, 제안, 계획, 채택, 구현 완료, 검증 결과**를 구분합니다. 결과가 없으면 미검증 또는 계획이라고 표시합니다. 적용점에는 핵심 인사이트 1~2개와 필요하면 다음 검증 또는 학습 키워드를 남깁니다.
- **측정 기록이 있으면** 핵심 내용에 **측정 조건**과 **측정 결과**를 함께 적습니다. 조건에는 확인 가능한 환경과 도구, 입력 또는 데이터셋, 절차, 표본 수와 반복 횟수, 비교 기준을 남깁니다. 결과에는 지표명, 단위, 기록의 정밀도, 통계량을 명시하고 같은 조건에서 비교한 변경 전후 값을 함께 보여 줍니다. 원본 실행 로그 없이 요약으로만 확인한 값은 자료 범위와 미확인 조건을 밝힙니다.
- **실측, 추정, 예시, 목표, 계산한 변화량**을 구분합니다. 테스트 통과 수와 호출 횟수는 각각 어떤 동작을 검증했는지 설명하고, 실제로 잰 시간이나 메모리와 구분합니다. 공개할 수 있는 수치만 기록합니다. 측정 기록이 없는 날에는 확인한 동작이나 남은 검증 범위를 적습니다.
- 자료 범위와 검증 한계는 필요한 경우 해당 섹션의 불릿에 명기합니다. 별도의 네 번째 섹션은 두지 않습니다.

## 3. 날짜 하나당 파일 하나와 대표 제목 하나를 사용합니다

- 파일은 `content/til/YYYY-MM-DD.md`에 작성합니다. 파일명과 frontmatter의 `date`를 일치시킵니다.
- `title`은 대표 기술 주제, `description`은 색인용 짧은 요약입니다. `topics`에는 그날 본문에서 다룬 API, 도구, 패턴, 기술 개념을 짧은 키워드로 적습니다. 예를 들어 `메모리 잔류`를 다룬 글이라면 `FFmpeg`와 `Blob URL`처럼 측정 대상을 적습니다. 기존 공개·초안 상태는 명시적 요청 없이 변경하지 않습니다.
- 독립 Markdown에서 쓰는 `## 제목`의 역할은 블로그에서는 frontmatter `title`이 담당합니다. 상세 화면이 이를 H1으로 출력하므로 **본문에 제목을 반복하지 않습니다**.
- 아래 세 개의 섹션 제목과 순서를 그대로 지킵니다. 예시 문구를 실제 경험으로 게시하지 않습니다.

```md
---
date: '2026-10-29'
title: '핵심 기술 주제가 드러나는 제목'
description: '대표 주제와 실제 확인 범위의 요약'
topics:
  - FFmpeg
  - Blob URL
draft: true
visibility: public
---

### 1. 개요 및 배경 (Context)

- **질문 요지** 그날 실제로 물어보거나 요청한 내용을 요약함
- 질문이 나온 문제 상황과 제약을 적음

### 2. 핵심 내용 / 문제 해결 과정 (Core / Troubleshooting)

- **답변에서 고른 방법** 당시 선택한 방법과 그 판단의 근거를 적음
- 실제로 비교한 대안과 트레이드오프, 확인한 결과와 남은 검증 범위를 적음
- **측정 조건** 측정 기록이 있을 때 환경, 도구, 입력, 절차와 표본 수를 적음
- **측정 결과** 지표, 단위와 통계량을 밝히고 비교 가능한 전후 값을 적음

### 3. 인사이트 및 적용점 (Takeaway & Next Action)

- 적용 조건과 **다음 검증 항목** 확인 필요
```

## 4. 홈 달력에는 기술 키워드를 불릿으로 표시합니다

- 홈의 월별 달력은 6주 격자와 일정한 날짜 칸 높이를 유지합니다. 달을 바꾸거나 주제가 많아져도 달력 높이는 변하지 않습니다.
- 기록이 있는 날짜의 `topics`는 세로 불릿 목록으로 표시하고, 각 주제의 긴 문구는 한 줄 말줄임표로 줄입니다. 목록에 마우스를 올리면 툴팁으로 그날의 전체 주제를 보여 줍니다. 일지 링크가 없는 모드에서는 목록의 키보드 포커스로도 툴팁을 열 수 있습니다. 목록이 칸을 넘으면 날짜 칸에 마우스를 올렸을 때 아래쪽 주제가 차례로 나타나고, 마지막 주제 뒤에는 처음부터 반복합니다. 키보드로 목록을 읽을 때는 자동 롤링을 멈춥니다. 모션 감소 설정에서도 자동 롤링을 끄고 직접 스크롤할 수 있게 합니다.
- 운영과 로컬 개발 미리보기에서 날짜에 마우스를 올리면 그날의 제목과 요약을 볼 수 있습니다. **키보드 포커스에도 같은 요약**을 제공하고, Escape로 닫을 수 있게 합니다. 요약 위로 포인터를 옮겨도 읽을 수 있어야 합니다.
- **날짜를 클릭하거나 Enter로 활성화하면 `/til/YYYY-MM-DD`의 해당 일지**로 이동합니다. 상세에는 그날의 대화를 사고 흐름으로 재구성한 내용을 보여 줍니다.
- 640px 이하의 화면에서 홈 달력은 날짜 격자를 표시합니다. 기록이 있는 날짜를 탭하면 상세로 이동합니다.
- 처음에는 한국 시간 기준 이번 달을 엽니다. 달력 상단에는 선택한 달의 연월을 표시하고 좌우 화살표로 월을 이동합니다. 기록이 없는 날짜는 상세 링크로 만들지 않으며, 기록이 없는 달에는 빈 상태를 알립니다.
- 날짜 표에는 요일과 월을 알 수 있는 의미 구조를 유지하고, 링크·버튼의 키보드 포커스를 보이게 합니다. 작은 화면에서도 가로 넘침 없이 읽을 수 있어야 합니다.

## 5. TIL 게시판과 상세 페이지는 같은 공개 기록을 보여 줍니다

운영과 로컬 개발 미리보기의 `/til` 게시판은 공개 일지를 **날짜 내림차순**으로 모읍니다. 날짜, 제목, 요약, 기술 키워드를 보여 주고, 목록과 달력에서 같은 날짜의 상세 페이지로 이동하게 합니다.

640px 이하에서는 게시판 달력 아래에 선택한 달의 날짜별 기술 키워드와 요약을 카드로 표시합니다.

운영 홈 달력과 로컬 개발 미리보기에서 상세 페이지를 열 수 있습니다. 상세 페이지에는 날짜, 대표 기술 주제, 개요·핵심 내용·적용점의 본문을 표시합니다. `draft: true` 또는 `visibility: private`인 일지는 **달력·게시판·상세 경로·sitemap에서 제외**합니다. 공개되지 않은 날짜는 404로 응답합니다.

## 6. 공개할 수 있는 근거만 추상화해 사용합니다

- 불필요한 개인정보, 계정 정보, 사내 비공개 요구사항·로직, 내부 URL, 접근 키, 사용자 데이터와 로그 원문을 포함하지 않습니다. 내부 이름은 역할과 개념 중심으로 바꿉니다.
- 대화나 Work 기록에 접근할 수 있다는 사실이 그 내용을 모두 외부에 공개해도 된다는 뜻은 아닙니다. 공개할 수 없는 부분은 생략하거나 충분히 추상화합니다.
- 근거 없는 전문적 주장, 측정하지 않은 수치, 실제로 겪지 않은 실패, 검토하지 않은 대안과 확인되지 않은 결론을 추가하지 않습니다.
- 원문이 비공개라면 계정·대화 링크나 원문 전체를 공개 파일에 옮기지 않고, 확인한 범위를 설명합니다. 검증용 자료도 공개할 필요가 없는 내용은 게시물에 넣지 않습니다.
- `draft`와 `visibility`는 사이트 노출 설정입니다. **공개 저장소의 파일이나 Git 이력을 비공개로 만드는 기능은 아니므로**, 민감한 원문은 애초에 커밋하지 않습니다.

## 7. 검증과 게시를 구분합니다

- 질문 요지가 그날 대화에 근거하는지, 선택한 방법과 이유가 연결되는지, 제안과 실제 적용이 구분되는지 확인합니다. 측정이 있다면 조건, 결과, 출처 범위가 함께 적혔는지 확인합니다. 날짜와 대표 주제를 대조하고 각 내용을 공개할 수 있는지 확인합니다. 뒤늦게 확인한 사실은 확인한 시점과 함께 기록합니다.
- `pnpm lint:content`와 목록·상세 미리보기에서 제목, 세 섹션, 강조가 정상적으로 표시되는지 확인합니다.
- 작업 브랜치 커밋 및 푸시, 머지·운영 배포, 정기 자동화 설정은 각각 해당 요청의 승인 범위를 따릅니다. 작성 규칙을 추가했다는 사실을 자동화가 실행 중이라는 근거로 쓰지 않습니다.
