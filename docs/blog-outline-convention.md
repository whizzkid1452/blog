# 블로그 목차 컨벤션

## 1. 목적

이 문서는 복잡한 프론트엔드 설계 과정을 기술 블로그와 시리즈 글의 목차로 바꾸는 규칙을 정의한다.

목차는 구현 파일을 나열하는 목록이 아니다. 독자가 다음 흐름을 따라가도록 설계한다.

> 문제 환경 → 관찰된 증상 → 제약 조건 → 선택지 비교 → 설계 판단 → 트레이드오프 → 검증 → 인사이트

## 2. 기본 원칙

### 2-1. 한 글은 한 질문에 답한다

각 글은 하나의 핵심 질문만 다룬다.

- 좋은 예: `왜 ProjectDocument의 SSOT를 Main Process에 두었는가`
- 나쁜 예: `Main Store 구현, PR 분리, 테스트, 배포 과정`

질문이 두 개 이상이면 시리즈 글을 나눈다. 파일 수나 코드 수정량이 아니라 독자가 이해해야 하는 판단 단위를 기준으로 나눈다.

### 2-2. 결론을 먼저 밝힌다

도입부에서 다음 내용을 짧게 제시한다.

1. 어떤 문제가 있었는가
2. 이 글에서 내린 결론은 무엇인가
3. 결론이 아직 조건부라면 무엇을 검증해야 하는가

측정하지 않은 성능 개선이나 데이터 손실 감소율은 주장하지 않는다.

### 2-3. 사실과 판단을 분리한다

본문은 다음 세 종류의 내용을 구분한다.

| 구분      | 의미                                     | 표현 예시                                      |
| --------- | ---------------------------------------- | ---------------------------------------------- |
| 확인 사실 | 코드, 재현 결과, 공식 문서로 확인한 내용 | `각 BrowserWindow는 별도 Renderer에서 열린다.` |
| 설계 판단 | 확인 사실을 바탕으로 선택한 구조         | `이 프로젝트에서는 Main을 SSOT로 선택했다.`    |
| 미정 조건 | 제품 정책이나 측정값이 필요한 내용       | `자동저장의 허용 손실 시간은 아직 미정이다.`   |

근거가 일부뿐이면 `원인이다` 대신 `원인과 일치한다`, `가능성을 좁힌다`처럼 쓴다.

## 3. 제목과 번호 규칙

### 3-1. 글 제목

시리즈 글은 다음 형식을 사용한다.

```text
[Part N.] 핵심 질문 또는 결론
```

예시:

- `[Part 0.] Main Process SSOT 시리즈를 시작하며`
- `[Part 2.] Main Process에 ProjectDocument SSOT를 둔 이유`
- `[Part 6.] Main SSOT 설계를 검증하고 선택의 비용 정리하기`

### 3-2. 섹션 번호

- 상위 섹션: `1.`, `2.`, `3.`
- 하위 섹션: `3-1.`, `3-2.`
- 하위 단계는 두 단계까지만 사용한다.
- 본문에는 frontmatter의 제목과 중복되는 `h1`을 작성하지 않는다.
- 상위 섹션 번호는 `1`부터, 하위 섹션 번호는 각 상위 섹션의 `1`부터 순서대로 작성한다.

```md
## [sort1] 3. Renderer 상태 동기화

### [sort2] 3-1. 읽기 전용 ProjectSnapshot

### [sort2] 3-2. version gap 복구
```

목차가 세 단계 이상 필요하면 글을 나누거나 상위 개념을 다시 묶는다.

## 4. 글 상단 구성

frontmatter 다음에는 글의 문제와 결론을 설명하는 도입부를 둔다. 본문 제목을 다시 쓰거나 수동 목차를 추가하지 않는다.

화면의 사이드 목차와 모바일 목차는 Markdown 제목의 표식을 기준으로 자동 생성한다.

- `## [sort1] N. 제목`: 사이드 목차의 상위 항목
- `### [sort2] N-N. 제목`: 사이드 목차의 하위 항목 (하위 항목을 목차에 넣을 때만)
- `### N-N. 제목`: 본문 하위 제목이지만 사이드 목차에서는 제외
- `## 참고`: 사이드 목차에서 제외하는 참고 자료 영역

```md
## [sort1] 1. 들어가며

## [sort1] 2. 문제 정의

### [sort2] 2-1. 관찰된 증상

### [sort2] 2-2. 구조적 조건

## [sort1] 3. 설계 판단

## 참고
```

시리즈 글은 frontmatter의 `series.name`과 `series.order`로 묶는다. 같은 시리즈의 링크 목록을 각 글 본문에 반복하지 않는다.

## 5. 시리즈 목차 설계

복잡한 설계 주제는 다음 역할로 나눈다.

| Part | 글의 역할           | 핵심 질문                                               |
| ---- | ------------------- | ------------------------------------------------------- |
| 0    | 시리즈 안내와 맥락  | 어떤 제품과 환경에서 문제가 발생했는가                  |
| 1    | 문제와 원인 범위    | 관찰된 증상과 구조적 조건은 무엇인가                    |
| 2    | 상태 소유권 결정    | 최종 상태를 어느 위치에서 확정할 것인가                 |
| 3    | 화면 동기화         | 확정 상태를 각 Renderer가 어떻게 표시할 것인가          |
| 4    | Undo/Redo           | 문서 History와 실행 객체를 어떻게 분리할 것인가         |
| 5    | 자동저장과 복구     | memory 반영과 disk 저장을 어떻게 구분할 것인가          |
| 6    | 검증과 트레이드오프 | 무엇을 검증하고 어떤 조건에서 설계를 다시 판단할 것인가 |

Part 수는 주제에 따라 바꿀 수 있다. 다만 마지막 글은 단순 요약이 아니라 검증 기준, 선택 비용, 재검토 조건으로 마무리한다.

## 6. 한 글의 표준 흐름

### 6-1. 들어가며

- 이전 글과의 연결
- 이 글이 답할 질문
- 먼저 밝히는 결론
- 아직 측정하거나 결정하지 못한 범위

### 6-2. 문제와 제약

- 사용자가 관찰한 증상
- 기존 상태 구조
- Electron, React, 브라우저 환경에서 확인한 제약
- 증상, 직접 원인, 구조적 조건의 구분

### 6-3. 선택지 비교

선택지는 장점만 설명하지 않는다. 각 선택의 적용 조건과 비용을 같은 기준으로 비교한다.

```md
| 선택지 | 얻는 점 | 비용과 한계 |
| ------ | ------- | ----------- |
```

### 6-4. 설계 판단

- 선택한 구조
- 선택 근거
- 상태의 위치와 변경 권한
- 선택하지 않은 대안이 다시 필요해지는 조건

### 6-5. 트레이드오프와 검증

- 줄이려는 위험
- 새로 생기는 복잡성
- 실제로 확인해야 하는 시나리오
- 성능과 복구의 측정 항목

### 6-6. 마치며

기능을 다시 나열하지 않는다. 이번 판단에서 얻은 인사이트와 다음 글의 질문으로 마무리한다.

## 7. 포함할 내용과 제외할 내용

### 7-1. 포함할 내용

- 상태의 소유 위치와 변경 권한
- Renderer 간 동기화 규칙
- version, 중복, event 누락 복구
- Undo/Redo와 자동저장이 같은 문서를 보는 이유
- 선택 근거와 트레이드오프
- 측정해야 할 항목과 미정 조건
- 공식 문서 링크와 실제 관찰 근거

### 7-2. 기본적으로 제외할 내용

- PR 분리 순서
- 브랜치와 커밋 전략
- 파일별 이관 체크리스트
- 클래스의 private method 목록
- 전체 타입 정의와 긴 최소 구현 코드
- 독자의 판단에 영향을 주지 않는 내부 이름

구현 코드가 글의 핵심 증거라면 필요한 최소 범위만 포함한다. 구현 튜토리얼이 목적이라면 별도 글로 분리한다.

## 8. 용어 규칙

프론트엔드와 Electron에서 실제로 사용하는 좁은 용어를 우선한다.

- `원본 복제 Store` 대신 `읽기 전용 ProjectSnapshot`
- `직렬화` 대신 의도에 따라 `data serialization` 또는 `queued sequential execution`
- `실시간 저장` 대신 `memory 즉시 반영`, `disk write 완료`, `device sync`를 구분
- `동기화` 대신 필요한 경우 `event 발행`, `cache 갱신`, `version gap 복구`로 구체화

`SSOT`는 값이 한 벌만 존재한다는 뜻이 아니라 최종 상태의 변경 권한이 한 곳에 있다는 의미로 정의한다.

## 9. 다이어그램 규칙

- 하나의 다이어그램은 하나의 관계만 설명한다.
- 노드 이름은 클래스 이름보다 역할을 우선한다.
- 화살표에는 `변경 요청`, `확정 결과`, `자동저장`처럼 전달 의미를 쓴다.
- 저장 상태와 UI state를 같은 노드에 섞지 않는다.
- 밝은 화면과 어두운 화면을 모두 고려해 글자색과 배경색을 직접 고정하지 않는다.
- 세부 구현보다 Main, Renderer, cache, local file 사이의 흐름을 보여준다.

## 10. 작성 템플릿

```md
---
title: '[Part N.] 제목'
description: '문제와 결론이 드러나는 한 문장'
date: 'YYYY-MM-DD'
tags: ['electron', 'state-management']
series:
  name: '시리즈 이름'
  order: N
draft: false
---

## [sort1] 1. 들어가며

문제, 글의 질문, 결론, 미정 범위를 적는다.

## [sort1] 2. 문제와 제약

관찰 사실과 환경 제약을 적는다.

## [sort1] 3. 선택지 비교

같은 기준으로 대안을 비교한다.

## [sort1] 4. 설계 판단

선택과 근거를 적는다.

## [sort1] 5. 트레이드오프와 검증

비용, 검증 시나리오, 재검토 조건을 적는다.

## [sort1] 6. 마치며

핵심 인사이트와 다음 질문을 적는다.

## 참고
```

## 11. 확인 목록

- [ ] 제목이 한 가지 질문이나 결론을 나타내는가
- [ ] 사이드 목차에 넣을 `h2`에는 `[sort1]` 표식이 있는가
- [ ] 사이드 목차에 넣을 `h3`에만 `[sort2]` 표식이 있는가 (대목차만 노출할 글은 `h3`에 sort 태그를 두지 않는다)
- [ ] `h2`, `h3` 번호가 빠짐없이 순서대로 이어지는가
- [ ] 본문에 frontmatter 제목과 중복되는 `h1`이 없는가
- [ ] `참고` 섹션이 사이드 목차에서 제외됐는가
- [ ] 확인 사실, 설계 판단, 미정 조건을 구분했는가
- [ ] 선택지의 장점과 비용을 같은 기준으로 비교했는가
- [ ] PR, 커밋, 파일 단위 작업 절차가 핵심 흐름을 가리지 않는가
- [ ] 측정하지 않은 효과를 정량적으로 주장하지 않았는가
- [ ] 다이어그램이 역할과 데이터 흐름만 보여 주는가
- [ ] 결론이 인사이트와 재검토 조건으로 수렴하는가
