비디오를 가져온 뒤 썸네일 전체가 준비될 때까지 타임라인이 비어 보였다. 화면 밖 구간까지 같은 우선순위로 생성하고 있어, 사용자가 먼저 볼 이미지도 파일 읽기와 디코딩을 기다려야 했다.

[1편](/posts/thumbnail-optimization-web-worker)에서는 첫 한 장을 먼저 보여주고 대량 생성을 Web Worker에 맡기는 방식을 비교했다. 이번에는 이 원리를 제품의 타임라인에 적용하면서 **첫 표시, 현재 화면, 화면 밖 작업의 우선순위와 정확도 기준**을 나눈 과정을 정리한다.

## [sort1] 1. 전체 영상의 균등 분포보다 현재 화면이 중요했다

기존에는 영상 길이에 따라 일정 개수의 썸네일을 만들었다. 구현은 단순했지만, 그 시점들이 사용자의 첫 화면에 필요한 시점과 같지는 않았다.

긴 영상일수록 전체 구간을 미리 채우는 비용이 커진다. 반대로 장수에 상한만 두면 현재 화면이 충분히 채워진다는 보장이 없다. 그래서 생성 기준을 전체 영상 길이에서 화면에 보이는 시간 범위인 viewport로 옮겼다.

## [sort1] 2. poster와 timestamp 썸네일을 구분했다

poster는 영상이 등록되었다는 사실을 먼저 보여주는 대표 이미지다. 타임라인의 각 시점에 정확히 대응하는 썸네일이 준비되기 전까지 대체 이미지로 사용할 수 있다.

실제 썸네일은 특정 원본 timestamp의 프레임이다. poster를 같은 캐시에 넣으면 요청한 시점의 이미지가 이미 있다고 잘못 판단할 수 있어, 대표 이미지와 timestamp 기반 캐시를 구분했다.

여기서 tile은 타임라인 Region 안에서 썸네일 한 장이 표시되는 칸을 뜻한다. 현재 화면에 tile이 몇 개 보이는지와 각 tile이 어느 원본 시점에 대응하는지를 먼저 계산한다.

## [sort1] 3. 첫 화면은 대표 이미지 한 장으로 먼저 채웠다

업로드 직후에는 약 0.1초 시점의 영상 프레임을 먼저 준비하고 `createImageBitmap()`으로 캡처해 대표 이미지로 사용했다. **0.1초는 영상 안에서 캡처할 위치이며 생성 소요 시간이 아니다.**

이 이미지는 Source 목록과 미리보기, 타임라인에서 실제 썸네일이 없는 구간의 대체 이미지로 사용한다. 정확한 timestamp 썸네일이 도착하면 해당 칸을 교체한다.

```text
영상 가져오기
→ 대표 프레임 준비와 캡처
→ poster 표시
→ 현재 화면의 실제 썸네일로 순차 교체
```

첫 화면을 채우는 일과 요청한 모든 썸네일을 만드는 일을 분리한 것이다.

## [sort1] 4. 현재 화면에는 요청 시점의 프레임을 만들었다

현재 보이는 tile에는 `HTMLVideoElement`의 재생 위치를 원본 timestamp로 이동하는 seek 경로를 적용했다. seek 완료 후 프레임을 캡처하고 캐시에 넣어 해당 화면을 다시 그린다.

```text
현재 viewport의 tile timestamp 계산
→ 캐시에 없는 timestamp만 요청
→ video.currentTime 변경 후 seek 완료 대기
→ 프레임 캡처와 캐시 등록
→ 해당 tile 갱신
```

하나의 video 요소에 여러 seek를 동시에 요청하면 완료 이벤트와 요청 시점을 연결하기 어렵다. 소스별 순차 큐를 두고, 스크롤이나 줌으로 화면 범위가 바뀌면 새 요청을 우선한다. 이전 화면에서 시작한 결과가 늦게 도착했는지도 확인해야 한다.

이 경로를 적용한 이유는 현재 화면의 정확도와 초기 준비 비용을 우선했기 때문이다. 모든 파일과 요청 장수에서 seek가 Worker보다 빠르다는 뜻은 아니다. [3편의 비교 측정](/posts/thumbnail-optimization-worker-verification)에서는 이 성능 판단의 범위를 다시 확인한다.

## [sort1] 5. 화면 밖은 Worker의 키프레임 경로로 미리 채웠다

화면 밖 썸네일은 당장 표시할 필요가 없다. 이 작업은 낮은 우선순위의 background prefetch로 두고 Web Worker에서 처리한다. 이전 글에서 backfill이라고 부르던 작업이다.

Worker에서는 파일의 영상 데이터를 분리하는 demux와 디코딩을 수행한다. 요청 시점에 가까운 키프레임을 사용하면, 정확한 timestamp 프레임과 결과가 다를 수 있다. 키프레임은 다른 프레임 없이 독립적으로 디코딩할 수 있는 프레임이다.

따라서 현재 화면에는 시점 정확도를 우선하고, 화면 밖에는 근사 이미지와 처리 효율을 허용했다. Worker 결과를 정확한 요청 시점의 이미지처럼 취급하지 않는 캐시 정책도 함께 필요하다.

긴 영상의 모든 구간을 무제한으로 생성하지 않도록 파일당 장수와 batch 크기, 캐시 수에 상한을 둔다. 사용자가 보고 있는 구간의 요청이 들어오면 화면 밖 작업보다 먼저 처리해야 한다.

## [sort1] 6. 실행 위치를 나눠도 요청 수명 관리는 남는다

Worker는 계산을 메인 스레드에서 분리할 수 있지만, 오래된 결과나 메모리 관리까지 해결하지는 않는다. 다음 조건을 요청과 캐시 양쪽에서 관리해야 한다.

- 같은 소스와 timestamp의 진행 중 요청을 중복 실행하지 않는다.
- 파일 교체나 프로젝트 전환 뒤 이전 결과를 새 캐시에 넣지 않는다.
- 스크롤·줌 이후에도 유효한 요청인지 확인한다.
- 결과를 작은 batch로 전달하고 캐시의 상한을 유지한다.
- 사용하지 않는 `ImageBitmap`은 `close()`로 정리한다.

미디어 취소와 Undo도 요청 수명에 포함된다. 화면에서 Region을 지웠는데 뒤늦은 Worker 결과가 리소스를 다시 붙이는 일이 없어야 한다.

## [sort1] 7. 결과는 지표별로 나누어 보았다

최초 썸네일 노출은 초 단위 요약 기준으로 `6.2초 → 2.8초`, 약 54.8% 단축됐다. [1편의 원 로그](/posts/thumbnail-optimization-web-worker)는 `6,262.2ms → 2,815.8ms`이며, 원 로그로 계산하면 약 55.0%다. 표시 단위와 반올림 후 계산에 따른 차이다.

대량 생성 시간 47.5% 단축은 같은 파일에서 60장을 만드는 seek와 Worker 비교 결과다. 첫 노출 개선과는 비교군이 다르다. 이 둘을 같은 지표의 중복 성과로 합산하지 않았다.

처리 로직은 `video-thumbnail` 공통 라이브러리로 패키징했다. 제품에서 필요한 우선순위와 캐시·취소 정책을 라이브러리의 실행 경계와 연결할 수 있도록 한 것이다.

## [sort1] 8. 적용해보기

- [ ] 첫 대표 이미지와 timestamp별 썸네일의 역할을 구분한다.
- [ ] 현재 화면의 누락 이미지부터 생성한다.
- [ ] 키프레임 근사값과 정확한 timestamp 결과를 같은 의미로 캐시하지 않는다.
- [ ] Worker 작업량과 결과 캐시에 상한을 둔다.
- [ ] 첫 노출, 전체 생성 시간, UI 루프 지연을 따로 측정한다.

이번 변경의 기준은 사용자가 언제 어떤 정확도의 이미지를 필요로 하는가였다. 같은 썸네일 생성 작업이어도 첫 표시와 현재 화면, 화면 밖에 서로 다른 실행 정책을 적용해야 했다.
