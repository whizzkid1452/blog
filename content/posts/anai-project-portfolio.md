## [sort1] 1. AnAI Media Editor

**GitHub**

### 개요

웹 브라우저와 Electron에서 실행되는 멀티미디어 편집 서비스입니다. 평균 1시간 분량, 15개 트랙, 약 700MB 규모의 프로젝트를 처리합니다.

### 역할

프론트엔드 2인 팀에서 웹 버전 개발을 리드했습니다. Electron 버전은 프론트엔드 2명, 백엔드 3명과 협업했습니다.

### Skills

React, Electron, Zustand, TanStack Query, IndexedDB

Web Worker, WebCodecs, Web Audio API, FFmpeg

### 주요 기여

#### 여러 편집 창의 상태와 Undo/Redo 통합

**AS-IS**

Electron의 기본 창과 보조 창이 프로젝트 상태를 각각 관리했습니다. 같은 프로젝트가 창마다 다르게 보였습니다. 저장 중 발생한 편집이 저장 완료로 잘못 표시되는 문제도 있었습니다.

클립 이동, 삭제, 분할 기능도 서로 다른 방식으로 상태를 변경했습니다. 여러 클립을 함께 수정하면 전체 작업을 한 번에 되돌리기 어려웠습니다.

**TO-BE**

모든 창이 같은 상태를 사용하고 저장 중 발생한 편집도 유지해야 했습니다. 창끼리 상태를 직접 맞추면 동기화 경로가 늘어나므로, 모든 창이 접근할 수 있는 Electron Main Process에서 프로젝트 상태를 관리했습니다. 각 화면은 IPC(Inter-Process Communication)로 상태 변경을 요청했습니다.

클립 이동, 삭제, 분할은 실행과 되돌리기 정보를 가진 Command로 만들었습니다. 여러 변경은 하나의 Command로 묶어 한 번에 되돌릴 수 있게 했습니다. 저장을 시작한 버전과 완료 시점의 버전도 비교했습니다. 그 결과 여러 창과 타임라인, 미리보기, 내보내기가 같은 상태를 사용했고, 오래된 저장 결과가 최신 편집을 덮어쓰지 않게 됐습니다.

[-- 구조도: Main Process와 여러 편집 창의 상태 동기화 흐름]

#### Local-first 저장과 비동기 결과 검증

**AS-IS**

서버 업로드가 끝나야 저장이 완료됐습니다. 네트워크가 끊기거나 미디어 업로드가 실패하면 로컬 편집 내용도 저장되지 않았습니다.

프로젝트를 바꾼 뒤 이전 프로젝트의 저장이나 미디어 처리가 끝나면 그 결과가 현재 프로젝트에 반영됐습니다.

**TO-BE**

네트워크 연결 없이 저장하려면 프로젝트 문서와 대용량 미디어를 로컬에 먼저 보관해야 했습니다. 브라우저에서 문서와 미디어 파일을 함께 저장할 수 있는 IndexedDB를 사용하고, 클라우드 동기화(Cloud Sync)는 로컬 저장이 끝난 뒤 실행하는 별도 작업으로 분리했습니다.

프로젝트 문서에는 파일 대신 로컬·서버 식별자를 기록했습니다. 파일 해시를 비교해 필요한 파일만 업로드했습니다. 비동기 작업이 끝나면 작업을 시작한 세션과 현재 세션을 비교하고, 두 세션이 다르면 결과를 버렸습니다. 이를 통해 오프라인에서도 편집 내용을 저장·복원하고, 이전 프로젝트의 늦은 작업 결과가 현재 프로젝트를 덮어쓰지 않게 했습니다.

[-- 구조도: IndexedDB 로컬 저장과 Cloud Sync 처리 흐름]

#### 썸네일과 드래그 렌더링 성능 개선

**AS-IS**

긴 영상의 프레임을 메인 스레드(Main Thread)에서 반복해서 추출했습니다. 첫 썸네일 표시에는 최대 6.26초가 걸렸습니다. 측정 구간의 Main Thread busy 비율은 66%였습니다.

클립을 드래그할 때는 모든 Pointer 이벤트마다 위치를 계산하고 React 상태를 바꿨습니다. 같은 화면 갱신 주기 안에서 계산과 렌더링이 반복됐습니다.

**TO-BE**

영상 처리가 UI를 막지 않도록 Web Worker와 WebCodecs를 사용해 디코딩을 Main Thread 밖으로 옮겼습니다. 전체 영상을 한 번에 처리하지 않고 현재 화면에 보이는 구간만 디코딩했습니다. 준비된 썸네일부터 `ImageBitmap`으로 전달해 순서대로 표시했습니다.

드래그 위치는 메모리에 저장하고 `requestAnimationFrame`에 맞춰 화면 갱신마다 최대 한 번 계산했습니다. 드래그 중에는 Overlay만 바꾸고, 끝날 때 최종 위치를 편집 상태에 반영했습니다. 첫 썸네일 표시 시간은 `6.26초 → 2.82초`, Main Thread busy 비율은 `66% → 11%`로 줄었습니다. React Profiler의 렌더링 시간인 `actualDuration`도 `2.87ms → 1.98ms`로 줄었습니다. 단, `actualDuration`은 Pointer 처리와 화면 그리기를 포함한 전체 응답 시간은 아닙니다.

[-- 이미지: 썸네일 표시 시간과 Main Thread busy 비율 전후 비교 그래프]

[-- 구조도: Web Worker 썸네일 처리와 requestAnimationFrame 드래그 처리 흐름]

#### 브라우저별 미디어 가져오기 개선

**AS-IS**

브라우저와 운영체제마다 지원하는 미디어 형식이 달랐습니다. MOV 파일에서 오디오를 읽지 못하는 문제가 발생했습니다.

모든 파일을 FFmpeg로 변환하면 이미 지원되는 파일에도 초기화와 변환 시간이 추가됐습니다.

**TO-BE**

일반적인 파일의 처리 속도를 유지하면서 브라우저별 형식 차이도 지원해야 했습니다. Web Audio API는 브라우저가 지원하는 파일을 바로 디코딩할 수 있지만, FFmpeg는 초기화와 변환 시간이 필요합니다. 따라서 Web Audio API를 기본 경로로 사용하고 FFmpeg를 대체 경로로 선택했습니다.

Web Audio API 디코딩이 8초 안에 끝나지 않거나 파일 형식을 지원하지 않으면 FFmpeg로 PCM WAV를 만들었습니다. Safari와 알려진 비호환 형식은 FFmpeg 경로를 먼저 사용했습니다. 이를 통해 일반적인 파일의 처리 속도를 유지하면서 기본 디코더가 처리하지 못하는 MOV 파일도 가져올 수 있게 됐습니다.

[-- 흐름도: Web Audio API 우선 처리와 FFmpeg 대체 경로]

#### WAV와 macOS AAF 내보내기 안정화

**AS-IS**

장시간 오디오를 WAV로 만들 때 전체 출력 크기의 `ArrayBuffer`를 한 번에 할당했습니다. 저사양 PC에서는 `RangeError: Array buffer allocation failed` 오류가 발생했습니다.

AAF(Advanced Authoring Format) 내보내기는 개발 PC에서는 동작했지만 macOS 사용자 PC에서 중단됐습니다. Native Runtime과 Library의 누락, 실행 경로, 서명 상태가 개발 환경과 달랐습니다.

**TO-BE**

WAV는 큰 연속 메모리를 할당하지 않아야 했습니다. 오디오를 16,384 Frame씩 인코딩해 `BlobPart`로 보관한 뒤 하나의 WAV `Blob`으로 합쳤습니다. WAV의 4GB 한계도 메모리를 할당하기 전에 검사했습니다. 그 결과 WAV 생성에 필요한 연속 메모리를 전체 파일 크기에서 조각 크기로 줄였습니다.

AAF는 사용자 PC에 설치된 Library에 의존하지 않도록 실행 파일과 Library를 앱에 포함했습니다. Mac CPU 종류별로 Runtime을 빌드하고 macOS Code Signing을 적용했습니다. Production Build 전에는 작은 오디오로 실제 AAF 파일을 만드는 Smoke Test를 실행했습니다. 이를 통해 Runtime 누락, 실행 경로, 서명 문제를 배포 전에 확인할 수 있게 됐습니다.

[-- 구조도: WAV 조각 인코딩과 AAF Runtime 패키징·검증 과정]

#### 화면 오류 격리와 서버 요청 복구

**AS-IS**

관리 화면처럼 편집과 관계없는 화면에서 오류가 발생해도 앱 전체가 오류 화면으로 바뀌었습니다.

서버 요청이 실패한 뒤 화면만 초기화하면 TanStack Query의 실패 상태가 남았습니다. 사용자가 다시 시도해도 같은 오류가 바로 표시됐습니다.

**TO-BE**

한 화면의 오류가 다른 기능으로 번지지 않아야 했습니다. React Error Boundary를 편집, 관리, 프로젝트 선택 화면에 각각 적용해 렌더링 오류를 화면별로 분리했습니다.

서버 요청 오류는 TanStack Query에 별도로 남기 때문에 다시 시도할 때 Error Boundary와 요청 오류 상태를 함께 초기화했습니다. 입력 오류와 권한 오류는 전체 화면 오류로 바꾸지 않고 현재 화면에서 안내했습니다. 이를 통해 한 화면의 오류가 앱 전체로 번지는 범위를 줄이고, 일시적인 서버 요청 오류는 앱을 다시 실행하지 않고 복구할 수 있게 했습니다.

[-- 구조도: 화면별 Error Boundary 범위와 서버 요청 오류 복구 흐름]

#### 생성 상태와 중복 조회 통합

**AS-IS**

미리 듣기 오디오와 최종 결과의 완료 조건을 화면마다 다르게 관리했습니다. 미리 듣기가 준비됐다는 이유로 전체 작업이 완료된 것처럼 표시됐습니다.

여러 화면이 같은 작업 상태를 반복해서 조회해 중복 요청도 발생했습니다.

**TO-BE**

미리 듣기와 최종 결과의 완료 조건을 구분하면서 화면 상태도 서버와 맞춰야 했습니다. 화면마다 상태를 관리하는 대신 두 결과를 하나의 생성 작업으로 묶고, 작업 단계를 준비, 미리 듣기 완료, 최종 결과 생성, 전체 완료, 실패로 나눴습니다.

서버 상태는 작업이 처리 중일 때만 폴링(Polling)했습니다. 이전 조회가 끝난 뒤 다음 조회를 시작하고, 생성 중에는 같은 화면의 추가 요청도 막았습니다. 미리 듣기는 준비되는 즉시 제공하고, 최종 결과는 필요한 파일이 모두 준비된 뒤 완료로 표시했습니다. 이를 통해 중복 생성 요청과 상태 조회를 줄였습니다.

[-- 상태도: 준비부터 미리 듣기·최종 결과·실패까지의 생성 상태 변화]

#### 미디어 재생과 리소스 정리 통합

**AS-IS**

오디오와 영상이 재생 상태와 위치를 각각 관리했습니다. 한쪽만 재생되거나 화면을 이동한 뒤 재생 위치가 처음으로 돌아갔습니다.

파일을 바꾸거나 화면을 이동한 뒤에도 이전 미디어 객체, 객체 URL(Object URL), 이벤트, 타이머가 남는 경로가 있었습니다.

**TO-BE**

오디오와 영상이 같은 재생 위치를 사용하도록 재생, 일시 정지, 위치 이동을 하나의 관리 영역에서 처리했습니다. 같은 미디어는 화면을 이동해도 재생 위치를 복원했습니다. 모바일에서는 브라우저의 자동 재생 정책에 맞춰 사용자가 누른 시점에 재생하고, 성공한 뒤 UI 상태를 바꿨습니다.

재생 제어와 리소스 정리를 같은 영역에 두어 정리 누락도 줄였습니다. 파일을 바꾸거나 화면을 닫으면 요청, 타이머, 이벤트, Object URL을 정리했습니다. 그 결과 오디오와 영상의 재생 위치가 달라지는 문제와 미디어 리소스가 남는 경로를 줄였습니다.

[-- 구조도: 미디어 재생 상태와 Object URL·이벤트·타이머 생명주기]

#### 공유와 다운로드 호환성 개선

**AS-IS**

Web Share API의 지원 범위와 파일 크기 제한이 브라우저와 기기마다 달랐습니다. 파일 공유를 지원하지 않는 환경에서는 결과물을 공유하거나 저장하기 어려웠습니다.

공유 버튼을 빠르게 여러 번 누르면 공유창과 파일 요청이 중복됐습니다. 잘못된 MIME 타입 때문에 모바일 공유가 실패하기도 했습니다.

**TO-BE**

브라우저가 지원하는 가장 편한 공유 방법을 먼저 제공하고, 지원하지 않는 환경에도 저장 경로를 남겨야 했습니다. Web Share API의 지원 범위와 파일 조건을 확인해 파일 공유, 링크 공유, 다운로드 순서로 처리했습니다. 실제 파일 형식에 맞게 MIME 타입도 고쳤습니다.

받은 파일은 결과 식별자별로 임시 저장해 다시 사용했습니다. 공유 중에는 같은 파일 요청을 새로 시작하지 않고 진행 중인 요청을 사용했습니다. 이를 통해 모바일과 데스크톱에 공유 또는 다운로드 경로를 제공하고, 중복 요청과 파일 형식 불일치로 발생하는 공유 실패를 줄였습니다.

[-- 흐름도: 파일 공유에서 링크 공유·다운로드로 이어지는 대체 경로]

#### GA4와 Sentry 기반 미디어 오류 추적

**AS-IS**

콘솔 로그만으로는 이미지와 영상 오류가 발생한 단계를 찾기 어려웠습니다. 오류가 발생한 브라우저 환경과 발생량도 함께 확인할 수 없었습니다.

**TO-BE**

오류 발생량과 개별 오류의 실행 정보를 함께 확인해야 했습니다. Google Analytics 4(GA4)에는 사용자 흐름과 미디어 실패 이벤트를 기록하고, Sentry에는 오류 위치, 브라우저 환경, 화면 경로를 기록했습니다. 두 기록에는 같은 작업 식별자를 사용했습니다.

사용자 입력 문장, 미디어 파일, 인증 정보, 결제 정보는 기록하지 않았습니다. 이를 통해 민감한 정보를 제외하면서 이미지와 영상 오류가 발생한 단계와 환경을 확인하고, 오류 원인을 조사할 범위를 좁혔습니다.

#### 다국어 뉴스 SEO 구조 구축

**AS-IS**

한국어와 영어 페이지의 주소와 검색 정보를 일관되게 관리하기 어려웠습니다. 검색엔진이 두 언어의 페이지를 구분하는 데 필요한 정보도 부족했습니다.

뉴스 주소를 바꾸면 기존 검색 결과, 북마크, 공유 링크가 끊겼습니다. Sitemap과 검색 접근 규칙도 직접 관리해 새 기사 등록을 빠뜨릴 수 있었습니다.

**TO-BE**

검색엔진이 언어별 페이지를 구분하고, 뉴스 주소를 바꿔도 기존 유입 경로를 유지해야 했습니다. Next.js Metadata로 언어별 제목, 설명, 공유 이미지, Canonical URL, 대체 언어 URL을 한곳에서 관리했습니다.

기사 제목과 고유 식별자로 새 주소를 만들고 기존 주소는 Redirect로 연결했습니다. 공개된 콘텐츠를 기준으로 Sitemap과 Robots 규칙을 만들었습니다. Schema.org 기반 JSON-LD로 회사와 기사 정보도 연결했습니다. 이를 통해 검색엔진에 언어별 페이지와 뉴스 구조를 구분할 정보를 제공하고, 기존 링크의 단절과 새 기사 등록 누락 위험을 줄였습니다.

[-- 구조도: 다국어 URL·Metadata·Redirect·JSON-LD 연결 관계]

#### CMS 장애 격리와 뉴스 대체 데이터 제공

**AS-IS**

사이트를 빌드할 때 CMS 조회가 실패하면 뉴스와 관계없는 브랜드 페이지도 배포되지 않았습니다. 서비스 실행 중 CMS에 일시적인 오류가 발생하면 뉴스 화면 전체가 오류 상태가 됐습니다.

화면마다 데이터 요청, 응답 변환, 임시 저장 코드를 따로 작성했습니다. 같은 조회 규칙이 여러 화면과 검색 정보 생성 코드에 반복됐습니다.

**TO-BE**

CMS 오류가 기본 브랜드 페이지의 배포를 막지 않아야 했습니다. 빌드 중 CMS 조회가 실패하면 뉴스 관련 작업만 건너뛰고 기본 페이지는 계속 빌드했습니다.

서비스 실행 중 최신 뉴스 조회가 실패하면 최근 조회 데이터와 서버 임시 데이터를 차례로 사용했습니다. 다만 실제로 존재하지 않는 기사는 이전 데이터로 바꾸지 않았습니다. 요청, 응답 변환, 임시 저장, 검색 정보 생성은 공통 데이터 계층으로 분리했습니다. 이를 통해 CMS의 일시적인 오류가 전체 배포 실패나 빈 뉴스 화면으로 이어지는 범위와 중복된 조회 로직을 줄였습니다.

[-- 흐름도: CMS 조회 실패 시 최근 데이터와 서버 임시 데이터 대체 순서]

#### Docker와 AWS ECR 배포 자동화

**AS-IS**

개발자가 직접 AWS에 로그인해 이미지를 만들고 전송했습니다. 배포 절차가 개발자의 로컬 환경에 따라 달라졌습니다. 일부 단계를 빠뜨리거나 잘못된 환경에 이미지를 전송할 수도 있었습니다.

운영과 개발이 같은 이미지 저장 위치를 사용하면 개발 이미지가 운영 이미지를 덮어쓸 수 있었습니다.

**TO-BE**

같은 코드를 같은 환경에서 빌드하고, 브랜치마다 이미지를 전송할 대상을 고정해야 했습니다. Docker로 설치, 빌드, 실행 환경을 고정하고 Next.js 실행에 필요한 파일만 이미지에 포함했습니다.

운영·개발 브랜치에 코드가 반영되면 GitHub Actions가 AWS 인증, 이미지 생성, 환경별 Amazon Elastic Container Registry(AWS ECR) 전송을 실행했습니다. AWS 인증 정보는 GitHub Secrets에 저장하고, 운영과 개발의 이미지 저장소는 분리했습니다. 그 결과 이미지 생성부터 ECR 전송까지의 수동 작업을 자동화하고 두 환경의 이미지가 서로 덮어쓰는 경로를 없앴습니다. 실제 서버 교체는 자동화 범위에 포함하지 않았습니다.

[-- 구조도: 브랜치별 GitHub Actions·Docker·AWS ECR 배포 파이프라인]
