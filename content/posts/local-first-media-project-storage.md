고객용 웹 멀티미디어 에디터인 VOIX STUDIO를 설계하면서, 네트워크 장애가 편집 내용의 유실로 이어지는 저장 흐름을 바꾸었다. 기존에는 로컬 저장과 클라우드 전송이 결합되어 서버 응답 여부가 저장 성공 전체를 결정했다.

나는 웹 에디터의 초기 아키텍처와 타임라인, 저장, 내보내기 흐름을 개발했다. 저장에서는 **편집 내용을 로컬에 보존하는 일과 서버에 전달하는 일을 분리**하는 데 집중했다. 로컬 저장과 Outbox 등록을 한 트랜잭션으로 묶고, 전송은 별도 동기화 서비스가 맡도록 했다.

![IndexedDB에 로컬 데이터와 Outbox를 저장하고 동기화 서비스가 클라우드로 비동기 전송하는 Local-first 저장 구조](/images/local-first-media-project-storage/local-first-outbox-sync.png)

## [sort1] 1. 로컬 저장 완료와 클라우드 동기화 완료를 구분했다

사용자가 편집을 끝냈을 때 먼저 필요한 것은 현재 작업을 이 브라우저에 남기는 일이다. 서버 전송에 실패했다는 이유로 이 로컬 저장까지 실패로 취급하면, 네트워크 상태가 작업 보존 여부를 결정하게 된다.

그래서 저장 완료의 기준을 나누었다.

- 로컬 저장 완료: IndexedDB에 프로젝트 문서와 전송 대기 항목을 기록한 트랜잭션이 완료된 상태다.
- 클라우드 동기화 완료: 서버가 특정 revision의 저장을 확인한 상태다.

화면도 두 상태를 구분해서 표시한다. 네트워크가 끊기면 동기화 상태를 `offline`으로 표시하고 로컬 편집은 이어갈 수 있게 했다. 저장 시간을 고정된 수치로 보장하는 구조는 아니다. 로컬 쓰기 시간은 문서 크기와 장치, 브라우저 환경에 따라 달라진다.

## [sort1] 2. 문서 저장과 Outbox 등록을 한 트랜잭션으로 묶었다

Outbox는 서버로 보낼 작업을 로컬에 기록한 전송 대기열이다. 프로젝트만 저장하고 Outbox를 기록하지 못하면 서버로 보낼 작업이 누락된다. 반대로 Outbox만 남으면 아직 저장되지 않은 문서를 전송하려 할 수 있다.

이 두 쓰기를 하나의 IndexedDB 트랜잭션에 넣었다. 둘 다 반영되거나 함께 취소되도록 묶는 **Transactional Outbox** 방식이다.

```text
편집 상태로 스냅샷과 revisionId 생성
→ 하나의 IndexedDB 트랜잭션 시작
  → 프로젝트 문서 저장
  → 같은 revisionId의 Outbox 항목 등록
→ 트랜잭션 완료 후 로컬 저장 완료 표시

동기화 서비스
→ Outbox 조회
→ 해당 revision 전송
→ 서버가 저장을 확인한 revisionId의 항목만 정리
```

트랜잭션 안에서 네트워크 요청까지 기다리지는 않는다. 로컬 기록을 먼저 끝내고 동기화 서비스가 전송을 담당한다. 이 서비스가 별도 Web Worker 스레드에서 실행되어야 하는 것은 아니다. 여기서 중요한 경계는 저장 책임과 전송 책임이다.

서버 응답이 도착했을 때 Outbox 전체를 비우지 않는 것도 중요하다. 전송 중 사용자가 새로 편집했다면 더 최신 revision이 대기열에 있을 수 있다. 서버가 확인한 `revisionId`에 해당하는 항목만 정리해야 나머지 미전송 작업이 남는다.

## [sort1] 3. 미디어 원본과 프로젝트 문서를 분리했다

영상과 오디오 원본을 타임라인 문서에 함께 넣으면, 클립 위치만 바꿔도 큰 데이터를 다시 저장하게 된다. 프로젝트 문서에는 편집 지시와 미디어 참조를 남기고 원본은 별도 영역에서 관리했다.

- Files 영역에는 영상·오디오·이미지 원본을 저장한다.
- Projects 영역에는 트랙, 클립 위치, 이펙트와 미디어 참조를 저장한다.

같은 원본에서 클립을 여러 개 만들더라도 각 클립은 원본을 복사하는 대신 참조한다. 미디어를 교체하거나 삭제할 때는 문서의 참조와 파일의 수명을 함께 관리해야 한다. 두 영역을 나누었다고 저장 공간 관리가 자동으로 끝나는 것은 아니다.

## [sort1] 4. 통신 실패를 종류별로 처리했다

네트워크 실패는 편집을 중단하는 예외 대신 동기화 상태로 다뤘다. 다만 모든 실패를 같은 방식으로 재시도하면 안 된다.

일시적인 통신 실패에는 재시도 간격을 점차 늘리는 지수 백오프를 적용한다. 인증이 필요한 경우에는 로그인 회복을 기다리고, 서버와 로컬 버전이 충돌하면 자동 전송을 계속하지 않고 사용자 해결을 기다린다. 전송에 실패한 항목은 Outbox에 남긴다.

같은 프로젝트의 동기화가 이미 진행 중이면 요청을 겹쳐 실행하지 않도록 single-flight로 제어했다. 그동안 생긴 새 revision은 로컬에 보존하고 후속 전송 대상으로 남긴다. 이는 동시 요청을 제한하는 규칙이며, 문서 버전 검증이나 응답 유효성 확인까지 대신하지는 않는다.

## [sort1] 5. 늦은 응답과 문서 충돌을 별도로 막았다

프로젝트 A의 동기화가 끝나기 전에 B를 열 수 있다. 이때 A의 응답이 성공했다고 B의 화면 상태를 갱신하면 안 된다. 결과를 현재 화면에 반영하기 전에 프로젝트 식별자와 실행 세션이 여전히 유효한지 확인했다.

같은 프로젝트를 다시 여는 경우에는 프로젝트 ID만으로 이전 작업을 구분하기 어렵다. 실행 세대까지 확인하는 원리는 [Runtime Scope로 프로젝트 전환 Race Condition 정리하기](/posts/runtime-scope-project-race-condition)에서 설명했다.

문서 충돌은 또 다른 문제다. 로컬 작업의 기준 버전과 서버 버전이 맞지 않으면 최신 응답이라는 이유만으로 덮어쓰지 않는다. 로컬 변경을 보존하고 사용자에게 충돌 해결을 맡기는 경계를 둔다. 이 구조만으로 여러 기기의 오프라인 편집을 자동 병합한다고 주장할 수는 없다.

## [sort1] 6. 달라진 동작과 검증할 경계

이번 변경으로 서버 응답을 기다리던 저장 경로가 로컬 기록과 후속 전송으로 나뉘었다. 전송 실패가 곧바로 로컬 저장 실패를 뜻하지 않으며, 확인되지 않은 revision은 재시도 대상으로 남는다. 저장 시간이나 데이터 유실 감소율은 별도로 정량 측정한 값이 없어 제시하지 않는다.

회귀 검증에서는 다음 경계가 중요하다.

- 문서와 Outbox 중 하나의 쓰기가 실패했을 때 트랜잭션이 함께 취소되는가.
- 이전 revision의 확인 응답이 최신 Outbox 항목을 지우지 않는가.
- 오프라인 전환 후에도 로컬 저장과 재열기가 가능한가.
- 로그인 대기와 버전 충돌이 무한 재시도로 이어지지 않는가.
- 프로젝트 전환 뒤 이전 응답이 현재 화면을 바꾸지 않는가.

IndexedDB 저장은 해당 브라우저의 로컬 보관이다. 사용자의 사이트 데이터 삭제, 저장 공간 제한, 디스크 장애까지 막는 백업과는 범위가 다르다. 그래서 로컬 보존과 클라우드 동기화 상태를 모두 보여줄 필요가 있다.

## [sort1] 7. 적용해보기

- [ ] 로컬 저장 완료와 서버 동기화 완료의 기준을 구분한다.
- [ ] 문서 저장과 전송 대기 등록을 같은 트랜잭션에 넣는다.
- [ ] 서버가 확인한 revision만 대기열에서 정리한다.
- [ ] 일시적 오류, 인증 대기, 충돌에 서로 다른 후속 동작을 둔다.
- [ ] 늦은 응답의 프로젝트와 실행 세대를 확인한다.

Local-first를 적용하며 가장 크게 바뀐 것은 저장 책임의 경계였다. 현재 작업을 보존하는 경로를 먼저 확보한 뒤, 외부 네트워크와 합의하는 과정을 별도로 설계해야 했다.
