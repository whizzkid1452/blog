자동 저장이 실행됐는데도 수정한 SRT 자막과 프로젝트 상태가 과거 값으로 돌아가는 문제가 있었다. 파일 쓰기 실패를 찾는 것만으로는 설명되지 않았다. 어느 창에 남아 있던 오래된 스냅샷이 정상적인 저장 경로를 타고 최신 프로젝트를 덮어쓰고 있었다.

사내용 Electron 에디터인 DYNA STUDIO는 여러 창에서 같은 프로젝트를 편집한다. 나는 이 제품의 레거시 상태 구조를 개선하면서 **프로젝트 상태의 최종 확정 권한을 Main Process로 옮겼다.** 각 창은 변경 요청만 보내고, Main이 확정한 결과를 받아 화면에 반영하도록 바꾸었다.

여기서 단일 진실 공급원(SSOT, Single Source of Truth)은 데이터 복사본이 하나뿐이라는 뜻이 아니다. 같은 값을 여러 창에 보관하더라도, 최종 상태를 변경할 권한은 한 곳에 둔다는 의미다.

## [sort1] 1. 오래된 화면 상태가 저장 원본으로 쓰였다

기존에는 자막 패널과 에디터 등 여러 Renderer가 각자의 Zustand Store를 가졌다. Renderer는 Electron 창의 웹 화면이 실행되는 프로세스다. 창 사이에서는 IPC 이벤트로 변경을 전달하고, 각 창의 로컬 상태를 바탕으로 자동 저장을 수행했다.

![오래된 Renderer Snapshot이 최신 SRT 자막을 덮어쓰는 순서](/images/electron-multi-window-shared-data-ssot/stale-snapshot-overwrite-sequence.png)

_변경을 받지 못한 창의 스냅샷이 프로젝트 파일에 기록되는 흐름_

어떤 창에 이전 값이 남으면 그 창도 자신의 상태를 저장 원본으로 사용할 수 있었다. 그 결과 파일뿐 아니라 다른 창의 화면까지 과거 상태로 돌아갈 수 있었다. 각 창의 값을 맞추는 규칙과 저장을 허용하는 규칙이 같은 기준을 사용하지 않은 것이다.

<p style="width: 100%; max-width: 400px; margin-inline: auto;"><img src="/images/electron-multi-window-shared-data-ssot/temporary-fix-meme.jpg" alt="코드의 오류를 손바닥으로 막는 임시방편을 표현한 밈" /></p>

동기화 이벤트를 추가하면 누락된 경로를 보완할 수는 있다. 그러나 여러 창이 전체 프로젝트를 확정하고 저장할 수 있는 한, 오래된 값이 다시 원본으로 쓰이는 경계는 남는다. 먼저 누가 최신 상태를 확정할지 정해야 했다.

## [sort1] 2. 창 사이 동기화와 파일 중심 갱신을 비교했다

Renderer끼리 상태를 맞추는 방식은 각 창의 변경 경로와 이벤트 순서를 함께 관리해야 한다. 창을 새로 열었을 때의 초기값과 메시지를 놓쳤을 때의 복구 규칙도 필요하다. Store 라이브러리를 같게 맞추는 것만으로 이 권한 문제가 해결되지는 않았다.

로컬 프로젝트 파일을 읽고 쓰며 화면을 맞추는 방법도 생각했다. 파일은 앱을 다시 열 때 상태를 복원하는 데 필요하다. 하지만 매 편집의 화면 반영을 파일 쓰기 완료에 연결하면 메모리 변경과 디스크 기록이 한 흐름에 묶인다. 파일에 쓰기 전에 어떤 값을 확정할지도 여전히 정해야 한다.

그래서 실행 중 상태 확정, 화면 전달, 파일 영속화를 나누었다. Main은 창들의 공통 실행 경계이고 특정 편집 창을 닫아도 프로젝트 상태를 관리할 수 있어 이 제품의 확정 주체로 적합했다.

## [sort1] 3. Main에서 Command를 검증하고 변경을 확정했다

Main Process의 프로젝트 세션이 문서 상태를 소유하도록 바꾸었다. Renderer는 저장할 전체 스냅샷을 보내는 대신, 수행할 변경을 나타내는 Command를 전달한다.

![Main Process의 ProjectSession이 변경을 확정하고 Renderer와 저장 경로에 전달하는 구조](/images/electron-multi-window-shared-data-ssot/to-be-project-document-service.png)

_Main이 확정한 프로젝트 상태를 화면과 자동 저장이 함께 사용하는 구조_

```text
Renderer의 편집 동작
→ Command 전달
→ Main에서 검증 후 프로젝트 상태 확정
→ 확정 이벤트와 변경 내용 전달
  → Renderer의 읽기 전용 캐시에 patch 반영
  → 확정 상태를 기준으로 자동 저장
```

화면에는 Main이 확정한 변경을 반영하고, 초기 화면이나 전체 상태가 필요한 경우 스냅샷을 사용한다. 각 창의 오래된 캐시를 다시 전체 프로젝트로 저장하는 권한은 제거했다.

메모리에서 변경을 확정한 시점과 파일 쓰기가 완료된 시점은 다르다. Command가 성공했다고 디스크 기록까지 끝났다고 표시하면 안 된다. 자동 저장도 화면 상태를 다시 조립하지 않고 Main이 확정한 문서를 입력으로 사용해야 한다.

## [sort1] 4. 문서 상태와 화면 상태에 다른 도구를 썼다

### [sort2] 4-1. Main에는 변경 진입점을 제한하는 클래스를 두었다

당시 Main에서 필요했던 것은 React 구독 모델보다 프로젝트 상태를 외부에서 직접 수정하지 못하게 하는 경계였다. 클래스의 private field와 정해진 변경 메서드로 접근을 제한했다.

Zustand로도 변경 진입점을 설계할 수 있다. 이 선택의 핵심은 클래스 자체의 우월성이 아니라, 문서를 확정하는 경로가 하나임을 드러내는 것이었다.

### [sort2] 4-2. Renderer에서는 TanStack Query를 읽기 전용 캐시로 사용했다

Renderer에도 화면을 그리기 위한 데이터는 필요하다. 기존에 사용하던 TanStack Query 캐시에 Main의 확정 결과를 반영했다. 여기서 읽기 전용은 캐시 API를 호출하지 않는다는 뜻이 아니라, 화면이 프로젝트의 최종값을 독자적으로 확정하지 않는다는 의미다.

Command 전송, Main의 확정 이벤트 수신, 캐시 갱신을 연결하는 책임은 애플리케이션에 남는다. TanStack Query를 사용한다고 Electron IPC 동기화가 자동으로 이루어지지는 않는다.

### [sort2] 4-3. 스크롤과 하이라이트는 Renderer에 남겼다

자막 클릭 후 스크롤, 하이라이트, 메뉴 열림 같은 UI 상태는 프로젝트 문서로 저장할 필요가 없다. 이 상태까지 문서 변경으로 처리하면 불필요한 확정 이벤트가 늘어난다.

저장할 편집 데이터만 Main의 확정 경로를 사용하고, 화면 상태와 일회성 UI 이벤트는 별도로 처리했다. 오디오 버퍼나 디코더 같은 실행 리소스도 저장 문서와 구분해야 한다.

## [sort1] 5. 저장 문제의 재발을 어떤 경계에서 확인할 것인가

이 변경으로 Renderer의 과거 스냅샷이 전체 프로젝트를 덮어쓰던 저장 경로를 제거했다. 같은 문제의 회귀를 추적하기 위해 Playwright E2E와 Vitest 단위 테스트를 도입했다. 데이터 유실 감소율이나 IPC 지연의 정량 수치는 별도로 제시하지 않는다.

회귀 검증에서 살펴볼 경계는 다음과 같다.

- 한 창의 수정이 다른 창의 캐시와 자동 저장 문서에 같은 값으로 반영되는가.
- 오래된 창이 전체 스냅샷을 저장 원본으로 제출할 수 없는가.
- Undo/Redo와 자동 저장이 같은 확정 문서를 기준으로 동작하는가.
- 창을 다시 열거나 이벤트를 놓쳤을 때 최신 상태를 다시 받을 수 있는가.
- 파일 쓰기 실패를 메모리 변경 성공과 구분해서 표시하는가.

Main에 권한을 모으면 IPC 계약과 이벤트 순서, 재연결 복구를 관리할 책임이 생긴다. Main에서 큰 미디어 처리까지 한꺼번에 수행하면 다른 병목이 될 수 있으므로, 문서 확정과 미디어 처리의 경계도 유지해야 한다.

## [sort1] 6. 적용해보기

- [ ] 같은 프로젝트를 확정할 수 있는 진입점이 몇 개인지 확인한다.
- [ ] 화면 캐시가 전체 프로젝트의 저장 원본으로 다시 쓰이지 않는지 확인한다.
- [ ] 메모리 확정과 디스크 저장 완료를 구분한다.
- [ ] UI 상태와 실행 리소스를 저장 문서에서 분리한다.
- [ ] 새 창 초기화와 이벤트 누락 후 복구 경로를 둔다.

이번 문제를 해결하며 상태 관리 도구보다 먼저 결정해야 할 기준을 배웠다. 값이 충돌했을 때 최종 상태를 확정하는 주체와, 그 결과를 화면과 저장에 전달하는 경로가 분명해야 했다.
