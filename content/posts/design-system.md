버튼 하나를 만들 때마다 이런 질문이 반복되곤 했어요.

> "이 버튼, `disabled` 상태에서 `hover` 처리는 어떻게 하죠?"
>
> "텍스트 필드 상태 이름은 뭘로 맞춰야 하나요?"

심지어 Figma의 Variant 이름과 코드의 Prop 이름이 달라서, 매번 어느 쪽이 진짜 기준인지 물어봐야 하는 일도 잦았어요. 빠르게 만들고 배포하는 마이크로 SaaS 프로젝트가 늘어날수록 UI 파편화는 점점 심해졌고, 결국 우리 팀만의 공통 기준인 디자인 시스템이 필요하다는 결론에 도달했어요.

이 글에서는 디자인 시스템을 기획하면서 당연하게 여겼던 npm 패키지 배포 방식을 과감히 버리고 shadcn 스타일의 Registry 방식을 선택한 이유와, 프론트엔드 API 설계 및 운영 리스크를 어떻게 풀어냈는지 공유해 볼게요.

---

## [sort1] 1. 왜 익숙한 npm 패키지를 포기했을까요?

처음에는 당연히 npm 패키지 형태로 배포해야 한다고 생각했어요. 중앙에서 일관성을 통제하고, 패키지 버전만 올리면 모든 프로젝트가 한 번에 업데이트되는 편리한 방식이니까요.

하지만 우리 조직의 현실을 들여다보니 이야기가 달랐어요. 빠르게 런칭했다가 사라지기도 하는 마이크로 SaaS 생태계에서는 중앙 집중적인 통제보다 각 프로젝트 상황에 맞는 빠른 시작과 유연한 커스터마이징이 훨씬 중요했거든요.

만약 패키지 방식을 고수했다면 어땠을까요? 프로젝트마다 쏟아지는 예외적인 디자인 요구를 수용하느라 컴포넌트의 Prop이 끝도 없이 늘어나는 병목이 생겼을 거예요.

그래서 우리는 CLI를 통해 컴포넌트 소스 코드를 프로젝트 내부로 직접 복사해 오는 Registry 방식(shadcn 스타일)을 선택했어요.

- 코드가 복사되는 순간, 컴포넌트의 소유권은 각 프로젝트가 가져요.
- 공통 컴포넌트를 기반으로 프로젝트 입맛에 맞게 코드를 바로 수정할 수 있어 개발 속도와 유연성이 크게 높아져요.

우리의 목표는 모든 프로젝트를 완벽하게 통제하는 게 아니라, 마이크로 SaaS가 빠르게 출발할 수 있는 훌륭한 초기값을 제공하는 것이었으니까요.

## [sort1] 2. Flat vs Compound: 두 마리 토끼를 잡는 하이브리드 API

Registry 방식으로 수정의 자유를 얻었지만, 컴포넌트 API 자체의 확장성도 고민해야 했어요. 보통 컴포넌트 API는 두 가지 패턴으로 나뉘어요.

- Flat 패턴: 내부 구조를 숨기고 모든 변형을 Prop으로 제어해요. `<Card actionLabel="다운로드" title="리포트"/>`처럼 직관적이지만, 예상치 못한 요구사항이 생길 때마다 Prop이 기형적으로 늘어나요.
- Compound 패턴: 하위 컴포넌트를 조합해 써요. `<Card><Card.Title>리포트</Card.Title></Card>`처럼 구조를 직접 제어할 수 있어 확장에 유리하지만, 단순한 기능만 필요할 때도 보일러플레이트가 길어져요.

### [sort2] 2-1. 그래서 내린 결정: Primitive 기반의 Flat API

우리는 두 패턴의 장점만 모은 하이브리드 전략을 택했어요. 내부적으로는 Radix UI와 결합된 Compound 패턴(Primitive)으로 유연한 조각들을 만들고, 외부로 노출할 때는 이 조각들을 미리 조립한 Flat 패턴의 API를 기본으로 제공하는 거예요.

```tsx
// 1. 내부 구조: 확장에 유연한 Compound 패턴(Primitive)으로 구성
const CardRoot = ({ children }) => <div className="card">{children}</div>;
const CardTitle = ({ children }) => <h2 className="title">{children}</h2>;

// 2. 외부 제공: 프로젝트에서 가져다 쓸 때는 직관적인 Flat API로 조립하여 제공
export function Card({ title, content }) {
  return (
    <CardRoot>
      <CardTitle>{title}</CardTitle>
      <p>{content}</p>
    </CardRoot>
  );
}
```

평소에는 Flat API로 빠르게 화면을 조립하다가, 특정 프로젝트에서 `CardTitle` 옆에 아이콘을 넣는 등 특수한 구조 변경이 필요해지면 어떡할까요? Registry로 복사해 온 코드를 열어 내부의 Compound 구조를 직접 수정하면 끝이에요.

## [sort1] 3. 기술 스택과 토큰 파이프라인: 자동화보다 안정성을 택한 이유

Registry 배포 방식과 하이브리드 API를 뒷받침하기 위해, 기존 조직의 주력 환경을 고려해 기술 스택을 꾸렸어요.

- Vite: 컴포넌트를 빠르게 띄워보고 검증하기 위한 개발 및 문서화 환경이에요.
- CLI 배포 + Emotion: shadcn의 훌륭한 CLI 복사 구조는 그대로 가져오되, Tailwind 대신 기존 앱들이 쓰고 있는 Emotion을 유지해 팀 내 혼선을 줄였어요.
- Radix UI: Dialog, DropdownMenu처럼 복잡한 WAI-ARIA 상호작용은 직접 구현하지 않고 Radix UI Primitive에 위임해 접근성과 안정성을 챙겼어요.

### [sort2] 3-1. CSS 변수와 Tokens Studio, 그리고 '수동 동기화'

시각적 일관성의 핵심인 색상, 간격, 모서리 반경 같은 디자인 토큰은 Emotion theme에 가두지 않고 순수 CSS 변수로 추출했어요. 다크모드 전환을 유연하게 처리하고, 앞으로 다른 프레임워크에서도 토큰을 재사용할 수 있도록 기반을 다져둔 거죠.

디자이너와 개발자 간의 싱크는 Figma의 Tokens Studio 플러그인과 GitHub 연동 기능으로 맞췄어요. 처음에는 디자이너가 토큰 JSON을 Push하면 GitHub Actions가 이를 감지해 CSS 변수로 자동 변환하는 완전 자동화 CI 파이프라인을 구상했어요.

하지만 실제 운영을 떠올려 보니 리스크가 너무 컸어요. 극단적인 자동화 과정에서 예기치 않은 토큰 변경이 들어가면, 제품 전체의 UI가 의도치 않게 망가질 수 있거든요.

> 결국 자동화의 편리함 대신 프로덕트의 안정성을 선택했어요.

현재는 수동 동기화(Manual Sync) 방식으로 운영하고 있어요. 디자이너가 GitHub에 토큰 JSON을 Push해 PR을 올리면, 프론트엔드 개발자가 UI에 미칠 영향을 직접 리뷰하고 스크립트를 돌려 CSS 변수로 변환한 뒤 머지해요.

## [sort1] 4. 자유에는 책임이 따르죠: 제공 단위와 리스크 방어 전략

Registry를 통해 복사해 갈 수 있는 단위는 두 가지로 나눴어요.

1. Component: Button, TextField 같은 범용적인 UI 요소예요.
2. Block: Login Page, Dashboard Shell처럼 여러 컴포넌트가 조합된 완성형 화면이에요. 도메인 의존성이 높아 재사용성은 떨어질 수 있지만, 마이크로 SaaS가 당장 화면을 그려내는 데는 이만한 무기가 없어요.

물론 Registry가 주는 '수정의 자유'는 양날의 검이에요. 자유가 무질서로 번지지 않도록 두 가지 방어 장치를 마련했어요.

### [sort2] 4-1. 파편화라는 빚 방어하기

각 프로젝트에서 코드를 마음대로 고치다 보면 1년 뒤에는 전혀 다른 컴포넌트가 되어 있을 수 있어요. 이를 막기 위해 사내 문서에 '절대 수정하면 안 되는 Core 영역'과 '자유롭게 수정해도 되는 Style 영역'을 명확히 구분해 두었어요. 반대로, 특정 프로젝트에서 만든 커스텀 컴포넌트가 범용적으로 훌륭하다면 디자인 시스템 표준으로 역반영해 별도 패키지로 분리하는 프로세스도 갖췄어요.

### [sort2] 4-2. 디자인 토큰 네이밍 변경 방어하기

Figma에서 디자이너가 토큰 이름을 바꾸면 프론트엔드 코드는 곧바로 에러를 뱉으며 무너져요. 코드가 Figma 네이밍을 맹목적으로 따라가지 않도록 번역 계층(Mapping Layer)을 두었어요.

- 디자이너와 협의해 Semantic Name을 엄격하게 유지하는 규칙(WEB Syntax 룰)을 세웠어요.
- 피치 못하게 변수명이 바뀔 때는 코드상에서 기존 이름과 새 이름을 연결하는 Alias를 두어, 기존 코드가 즉시 깨지지 않도록 유예 기간을 확보해요.

## [sort1] 5. 마치며: 완벽한 통제보다 든든한 베이스캠프로

이번 디자인 시스템을 구축하면서 '완벽한 추상화'와 '중앙 통제'라는 전통적인 미덕을 과감히 내려놓았어요. 대신 속도, 프로젝트별 소유권, 유연한 커스터마이징이라는 마이크로 SaaS 생태계에 가장 현실적인 무기를 선택했죠.

치열하게 고민하고 결정한 이 구조가, 앞으로 탄생할 수많은 프로젝트의 든든한 베이스캠프가 되어주길 기대해 봅니다.
