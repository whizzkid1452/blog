1,500개가 넘는 오디오 클립이 놓인 타임라인에서 스크롤과 선택이 늦게 반응했다. 화면에 보이는 클립은 일부였지만, 스크롤할 때마다 전체 데이터를 검사하고 React 컴포넌트까지 다시 실행하고 있었다.

나는 사내용 Electron 에디터인 DYNA STUDIO의 레거시 구조와 타임라인 성능을 개선했다. DYNA는 평균 2시간 길이, 1,500개 이상의 오디오 클립과 약 2GB 규모의 프로젝트를 다룬다. 고객용 웹 에디터인 VOIX STUDIO의 초기 아키텍처와는 실행 환경을 구분해서 볼 필요가 있다.

![영상 미리보기와 자막·오디오 클립이 배치된 멀티트랙 타임라인 에디터 화면](/images/timeline-performance-region-index-decision/editor-multitrack-timeline.png)

결론부터 말하면, **이진 탐색으로 조회 후보를 줄이는 작업과 React를 거치지 않고 Canvas를 갱신하는 작업을 함께 적용했다.** 18개 트랙, 1,518개 Region을 사용한 비교에서 Long Task 누적 시간이 `4,418ms → 1,154ms`로 약 73.9% 감소했다. Region은 타임라인에 놓인 클립의 위치와 길이를 나타내는 편집 단위다.

## [sort1] 1. 화면에 보이는 클립을 찾는 데 전체 순회가 필요했다

기존에는 스크롤 위치가 달라질 때마다 전체 Region을 순회해 화면과 겹치는지 검사했다. 동시에 스크롤 위치가 React prop으로 전달되어 TrackRow와 하위 컴포넌트도 다시 실행됐다.

두 비용을 구분해야 했다. 조회만 줄여도 React 실행은 남고, React 실행만 줄여도 전체 Region 검사는 남는다. 그래서 조회 자료구조와 화면 갱신 경로를 각각 바꾸었다.

일반 목록의 가상화는 항목 높이를 누적해 위치를 찾을 수 있다. 타임라인에는 빈 시간과 길이가 다른 클립, 서로 겹치는 구간이 있으므로 시간 범위의 교차 조건이 필요했다. 세로 트랙 가상화와 가로 시간 구간 조회도 별개의 문제로 다뤘다.

## [sort1] 2. 두 번의 이진 탐색으로 후보 범위를 좁혔다

화면과 겹치는 조건은 다음과 같다. 아래 코드는 설명을 위해 단순화한 예제다.

```ts
const overlaps = region.end >= viewport.start && region.start <= viewport.end;
```

먼저 Region을 시작 시간순으로 정렬했다. 화면 종료 시간보다 늦게 시작하는 첫 위치를 이진 탐색하면 오른쪽 경계를 찾을 수 있다.

왼쪽 경계에는 개별 종료 시간을 그대로 쓸 수 없었다. 시작 시간순으로 정렬해도 종료 시간까지 정렬되지는 않기 때문이다. 일찍 시작한 긴 배경음악이 뒤에 시작한 짧은 효과음보다 늦게 끝날 수 있다.

그래서 각 위치까지의 **누적 최대 종료 시간**을 함께 저장했다.

```text
시작 시간순 Region의 종료 시간: [4, 100, 12, 30]
누적 최대 종료 시간:           [4, 100, 100, 100]
```

누적 최댓값은 감소하지 않는다. 화면 시작 시간 이상인 첫 위치를 이진 탐색하면, 그 앞의 Region은 모두 제외할 수 있다. 두 경계 사이에 남은 후보만 실제 교차 조건으로 검사하고 기존 렌더링 순서를 복원했다.

이 구조는 계층적 구간 트리가 아닌 **정렬 배열과 누적 최댓값 배열**이다. [구현 글](/posts/timeline-performance-region-index-implementation)에서는 두 배열을 만들고 조회하는 코드를 다룬다.

## [sort1] 3. 조회 비용과 인덱스 갱신 비용을 함께 보았다

이진 탐색 두 번이 조회 전체를 `O(log N)`으로 만들어 주지는 않는다. 후보 수를 `C`, 실제 반환 수를 `V`라고 하면 예제의 조회 비용은 `O(log N + C + V log V)`다. 인덱스 생성에는 정렬 비용 `O(N log N)`이 든다.

긴 Region 하나가 앞쪽에 있으면 누적 최대 종료 시간이 크게 유지되어 후보가 많이 남을 수 있다. 모든 배치에서 같은 감소율을 보장하는 구조는 아니다. 이 프로젝트에서는 데이터 변경보다 스크롤 조회가 자주 발생한다는 조건을 기준으로 선택했다.

드래그 중 임시 위치는 별도 시각 레이어에 표시하고, 드래그가 끝날 때 편집 데이터를 확정하는 방식으로 갱신을 나눴다. 인덱스도 확정된 Region 목록이 바뀔 때 다시 만들도록 경계를 두었다. 임시 피드백과 문서 변경을 분리한 과정은 [드래그 최적화 글](/posts/drag-optimization-overlay-rerender)에서 다룬다.

## [sort1] 4. 스크롤 위치를 React prop에서 분리했다

Canvas를 다시 그리는 데 필요한 스크롤 값은 Ref에 보관했다. Signal은 이 값이 바뀌었음을 구독자에게 알리는 통로다. TrackRow의 React prop을 갱신하는 대신, Canvas draw 함수가 Signal을 구독하게 했다.

여기에 `requestAnimationFrame`을 결합해 같은 프레임 안의 갱신 요청을 한 번으로 합쳤다.

```text
스크롤 이벤트 → Ref의 최신 위치 갱신 → rAF 예약
→ Signal 알림 → 필요한 Canvas draw
```

이 경로에서는 스크롤만으로 TrackRow를 다시 실행할 필요가 없다. 선택 상태나 메뉴처럼 React가 표시해야 하는 UI 상태는 기존 React 경로에 남겼다. rAF는 연산 자체를 없애는 도구가 아니므로, 한 번의 draw 비용은 별도로 관리해야 한다.

## [sort1] 5. 무엇이 줄었고 무엇이 남았는가

18개 트랙, 1,518개 Region을 사용한 비교에서 화면 갱신 시 검사 후보 수가 약 98.5% 줄었다. 시간 인덱스와 rAF Signal을 함께 적용한 뒤 Long Task 누적 시간은 `4,418ms → 1,154ms`로 약 73.9% 감소했다.

Long Task는 메인 스레드의 한 작업이 50ms를 넘는 경우를 말한다. 누적 시간 감소는 긴 작업의 부담이 줄었다는 근거다. 총 JavaScript 연산량이나 모든 입력의 응답 시간이 같은 비율로 줄었다는 뜻은 아니다. 두 변경을 함께 적용했으므로 73.9%를 이진 탐색 하나의 효과로 돌리지 않았다.

측정 결과는 위 데이터와 비교 구간에 한정된다. 다른 장치와 클립 분포에서의 결과, 세로 트랙 가상화, 장거리 드래그 중 자동 스크롤은 별도로 확인할 과제다.

## [sort1] 6. 적용해보기

- [ ] 전체 순회 비용과 React 실행 비용을 나누어 측정한다.
- [ ] 화면보다 먼저 시작한 긴 Region도 조회 결과에 포함되는지 확인한다.
- [ ] 스크롤 중 인덱스를 새로 만들고 있지 않은지 확인한다.
- [ ] 프레임마다 바뀌는 값이 React 렌더 결과에 필요한지 구분한다.
- [ ] Long Task, 전체 처리 시간, 실제 입력 지연을 서로 다른 지표로 본다.

이번 작업에서 얻은 기준은 데이터의 변경 빈도와 소비 위치였다. 조회에 쓰는 자료구조와 화면을 갱신하는 경로를 함께 설계해야, 어느 단계의 비용을 줄였는지 설명할 수 있었다.
