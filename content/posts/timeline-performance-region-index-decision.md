18개 Track과 1,518개 Region이 배치된 타임라인에서 가로 스크롤과 편집 입력이 늦게 반영되는 문제가 있었습니다. 코드를 확인해 보니 스크롤할 때마다 다음 두 작업이 반복되고 있었습니다.

- 현재 화면에 보이는 Region을 찾기 위해 전체 Region을 조회
- Canvas를 다시 그리기 위해 모든 TrackRow의 React 컴포넌트를 실행

이 두 경로를 줄이기 위해 다음 구조를 적용했습니다.

- **이진 탐색 기반 시간 인덱스**로 Viewport와 겹칠 가능성이 있는 Region만 조회
- **requestAnimationFrame 기반 Signal 구독 구조**로 React 실행과 Canvas 갱신을 분리

같은 조건으로 측정한 결과 Long Task 누적 시간은 **4,418ms에서 1,154ms로 73.9% 감소**했습니다. 다만 메인 스레드 CPU 비율과 React 작업량은 감소하지 않았습니다. 이 글에서는 결과를 좋게 포장하기보다, 어떤 문제를 확인했고 왜 두 구조를 선택했으며 측정 결과가 어디까지 결론을 지지하는지 정리합니다.

## [sort1] 1. Region이 500개를 넘으면 화면이 늦게 반응했다

> “다중 트랙에서 Region이 500개를 넘으면 화면이 너무 버벅여서 편집하기 어려워요.”

이 제보가 문제의 시작이었습니다. Region은 타임라인에 배치된 시작 시간과 종료 시간을 가진 편집 단위입니다. 음성 생성과 오디오 겹침 처리를 반복하면 하나의 프로젝트에 수백 개에서 1,500개 이상의 Region이 생성될 수 있었습니다. 사용자가 말한 버벅임은 단순히 애니메이션이 매끄럽지 않다는 수준이 아니었습니다.

- 가로 스크롤이 입력을 바로 따라오지 않음
- Region을 클릭해도 선택 상태가 늦게 표시됨
- 편집 도중 화면이 순간적으로 멈춘 것처럼 느껴짐

실제 프로젝트 데이터를 이용해 18개 Track과 1,518개 Region을 배치한 뒤 동일한 가로 스크롤을 반복했습니다. 테스트 환경에서도 입력이 화면에 늦게 반영되는 현상을 재현할 수 있었습니다.

![불타는 방에서도 괜찮다고 말하는 This is fine 밈](/images/timeline-performance-region-index-decision/this-is-fine.jpg)

_Region이 500개를 넘었지만 스크롤이 아주 조금은 움직이니까 아직 괜찮다고 믿고 있는 개발자의 모습. ([이미지 출처](https://imgflip.com/memetemplate/This-Is-Fine))_

처음에는 화면 밖의 TrackRow를 제거하는 세로 Track 가상화를 먼저 떠올렸습니다. 화면에 보이지 않는 컴포넌트를 제거하면 당연히 빨라질 것처럼 보였습니다. 하지만 많은 컴포넌트가 마운트돼 있다는 사실만으로 입력 지연의 원인을 특정할 수는 없었습니다. 하나의 느린 프레임 안에는 여러 작업이 함께 들어갈 수 있습니다.

- JavaScript 계산
- React 컴포넌트 실행과 Commit
- Canvas draw
- 브라우저 Layout과 Paint
- Garbage Collection

따라서 최적화 방법부터 정하기보다, 스크롤할 때 실제로 어떤 작업이 반복되고 있는지 먼저 확인하기로 했습니다. 이번 작업의 목표도 다음 범위로 제한했습니다.

> 스크롤 경로에서 확인한 반복 비용을 줄이고, 같은 조건에서 Long Task와 입력 지표가 어떻게 변하는지 확인한다.

## [sort1] 2. FPS보다 입력을 오래 막는 작업을 확인했다

사용자 제보의 핵심은 평균 FPS가 낮다는 것이 아니었습니다. 화면이 몇 프레임으로 갱신되는지보다, 사용자의 스크롤과 클릭이 늦게 처리돼 편집하기 어렵다는 점이 중요했습니다. 그래서 변경 전후를 비교하는 중심 지표로 **Long Task**를 선택했습니다. Long Task는 메인 스레드를 50ms 이상 점유한 작업입니다. Long Task가 실행되는 동안에는 뒤에서 기다리고 있는 입력 이벤트와 화면 갱신도 함께 늦어질 수 있습니다. 다만 Long Task만으로 전체 성능을 판단할 수는 없습니다. 긴 작업 하나가 여러 개의 짧은 작업으로 나뉘면 Long Task 지표는 좋아질 수 있지만, 전체 CPU 사용량은 그대로일 수 있습니다. 이 한계를 확인하기 위해 다음 보조 지표도 함께 기록했습니다.

| 지표                        | 확인할 내용                                            |
| --------------------------- | ------------------------------------------------------ |
| Long Task 횟수·누적 시간    | 메인 스레드를 50ms 이상 점유한 작업의 발생량           |
| 입력 후 다음 Frame p95      | DOM이 입력을 받은 뒤 다음 화면 갱신 기회까지 걸린 시간 |
| DOM wheel 입력 수신율       | 전송한 wheel 입력 중 DOM에서 실제로 관찰한 비율        |
| 메인 스레드 CPU 비율        | 측정 구간에서 Renderer 작업이 실행된 시간의 비율       |
| React Commit·actualDuration | React Commit 횟수와 Profiler가 기록한 작업 시간        |

비교 조건은 실제 프로젝트 JSON을 고정 Fixture로 저장해 통제했습니다.

| 조건        |                  값 |
| ----------- | ------------------: |
| Track       |                18개 |
| Region      |             1,518개 |
| 측정 시간   |                10초 |
| wheel 입력  |               303회 |
| 입력 간격   |                33ms |
| 스크롤 거리 |               480px |
| 반복 횟수   | 변경 전·후 각각 3회 |
| 대표값      |   3회 측정의 중앙값 |

Electron Renderer에는 Playwright의 `connectOverCDP`를 이용해 연결했습니다. 처음에는 Chrome Trace를 켜고 모든 수치를 측정하려 했습니다. 하지만 Trace를 활성화하면 이벤트 수집 작업 자체가 측정 대상에 추가됐습니다. 실제 측정에서도 Trace 사용 여부에 따라 절대값과 변화 방향이 달라졌습니다. 따라서 측정 목적을 분리했습니다.

- 변경 전후 비교는 Trace를 끄고 각각 3회 실행
- 함수 호출 흐름은 Trace를 켠 별도 실행에서 분석
- CPU 비율은 CDP Performance의 Runtime Metric으로 수집

측정 도구가 성능 측정에 영향을 주는 상황에서 모든 정보를 하나의 실행으로 얻으려 하면, 분석을 위해 추가한 도구가 비교 결과까지 바꿀 수 있었습니다.

## [sort1] 3. 화면 범위를 계산한 뒤에도 Region 전체를 조회하고 있었다

코드에서 처음 확인한 반복 경로는 Region 조회였습니다. 기존 가로 Virtualizer는 현재 화면과 Overscan에 해당하는 시간 범위를 정상적으로 계산하고 있었습니다.

```text
가로 Virtualizer
└─ 현재 화면의 시간 범위 계산
```

문제는 그다음이었습니다. 각 Track에서 해당 시간 범위와 겹치는 Region을 찾을 때는 전체 Region 목록을 처음부터 끝까지 순회하고 있었습니다.

```text
가로 Virtualizer
└─ 현재 화면의 시간 범위 계산

Region 조회
└─ 전체 목록에서 화면과 겹치는 Region 검사
```

Viewport를 계산했으니 화면에 필요한 데이터만 처리하고 있을 것이라고 생각했지만, 실제로는 **화면의 범위만 계산한 뒤 데이터는 여전히 전체 조회**하고 있었습니다.

화면 범위를 계산하는 것과 그 범위에 속한 데이터를 빠르게 찾는 것은 서로 다른 문제였습니다. 확인한 프로젝트에서 Track은 주로 10개에서 15개였고, 측정 프로젝트에는 18개가 있었습니다. 반면 Region은 음성 생성과 겹침 처리 이후 1,518개까지 증가했습니다. 현재 데이터에서 더 크게 증가하는 축은 Track보다 Region이었습니다. 따라서 세로 Track 가상화보다 먼저, 스크롤할 때 반복되는 Region 전체 조회를 줄이는 편이 현재 문제와 더 직접적으로 연결돼 있었습니다.

## [sort1] 4. `React.memo`가 있었지만 모든 TrackRow가 실행됐다

두 번째 반복 경로는 Canvas 갱신 값의 전달 방식이었습니다. 부모 컴포넌트는 Canvas를 현재 스크롤 위치에 맞춰 다시 그리기 위해, 스크롤할 때마다 변경되는 값을 모든 TrackRow에 Prop으로 전달하고 있었습니다.

```text
scroll event
→ scroll prop 변경
→ 모든 TrackRow 실행
→ Canvas 갱신 요청
```

TrackRow에는 이미 `React.memo`가 적용돼 있었습니다. 하지만 스크롤할 때마다 Prop 값이 변경됐기 때문에, 이전 Props와 현재 Props가 같을 때 컴포넌트 실행을 건너뛰는 조건이 성립하지 않았습니다. `React.memo`가 동작하지 않은 것이 아니라, 매번 다른 값을 전달하면서 `React.memo`가 실행을 건너뛰기를 기대하고 있었던 것입니다.

> **`React.memo`를 추가한 나:** 이제 빨라지겠지.
>
> **매 스크롤마다 변경되는 Prop:** 이번에도 실행할게.

스크롤할 때 실제로 필요한 작업은 TrackRow의 JSX를 다시 계산하는 일이 아니었습니다. 최신 가로 위치를 이용해 각 Track의 Canvas를 다시 그리는 일이었습니다.

- Track 데이터는 변경되지 않음
- JSX 구조도 변경되지 않음
- Canvas가 참고할 스크롤 위치만 변경됨

React UI 계산과 Canvas draw의 실행 조건이 달랐지만, 기존 구조에서는 두 작업이 같은 Prop 경로에 묶여 있었습니다. 따라서 다음 두 질문을 분리할 필요가 있었습니다.

1. React가 다시 계산해야 하는 상태인가?
2. Canvas가 다음 Frame에 다시 그려야 한다는 알림인가?

## [sort1] 5. 이진 탐색 기반 시간 인덱스를 선택했다

### 5.1 Region 변경보다 Viewport 조회가 더 자주 실행됐다

Region 추가, 삭제, 시작 시간 변경은 사용자가 편집할 때 발생했습니다. 반면 Viewport 조회는 사용자가 가로로 스크롤하는 동안 계속 반복됐습니다.

```text
Region 목록 변경
└─ 정렬 배열과 조회용 보조 데이터 생성

가로 스크롤
└─ 기존 인덱스에서 Viewport 범위 조회
```

현재 사용 패턴에서는 Region 목록을 변경하는 횟수보다, 같은 Region 목록에서 Viewport를 조회하는 횟수가 훨씬 많았습니다. 따라서 Region 목록이 변경될 때 인덱스를 만드는 비용을 한 번 지불하고, 스크롤 중 반복되는 조회 비용을 줄이는 구조가 적합하다고 판단했습니다. 다만 이 판단은 다음 조건에 의존합니다.

> Region 목록 변경보다 Viewport 조회가 더 자주 실행된다.

Region이 스크롤보다 더 자주 추가되고 이동하는 환경이라면 인덱스를 계속 다시 만드는 비용이 커질 수 있습니다. 그런 환경에서는 같은 자료구조가 적합한지 다시 측정해야 합니다.

---

### 5.2 시작 시간만 정렬하면 긴 Region을 놓칠 수 있었다

처음에는 Region을 시작 시간순으로 정렬한 뒤, Viewport 범위에 해당하는 구간만 이진 탐색하면 될 것처럼 보였습니다. 시작 시간 정렬은 오른쪽 경계를 찾는 데 사용할 수 있습니다.

```text
Region.start > Viewport.end
```

Viewport 종료 시간보다 늦게 시작하는 Region부터는 현재 화면과 겹칠 수 없기 때문입니다. 하지만 왼쪽 경계는 시작 시간만으로 결정할 수 없었습니다. Viewport보다 훨씬 전에 시작했지만 재생 시간이 길어 현재 화면까지 이어지는 Region이 있을 수 있기 때문입니다.

```text
Region
|--------------------------------------|

Viewport
                    |---------|
```

시작 시간이 Viewport보다 앞이라는 이유로 제외하면, 현재 화면과 실제로 겹치는 긴 Region을 놓칠 수 있었습니다. 그래서 시작 시간순 배열과 함께 **누적 최대 종료 시간인 `prefixMaxEnd`**를 저장했습니다.

- 오른쪽 경계: `Region.start > Viewport.end`인 첫 위치
- 왼쪽 경계: `prefixMaxEnd >= Viewport.start`인 첫 위치
- 두 경계 사이의 후보에 실제 겹침 조건 적용
- 결과는 기존 렌더링 순서로 복원

```text
시작 시간순 Region 배열
+
각 위치까지의 최대 종료 시간

        ↓ 이진 탐색

Viewport와 겹칠 가능성이 있는 후보 범위

        ↓ 실제 겹침 검사

렌더링할 Region
```

이 구조를 이용하면 긴 Region을 놓치지 않으면서, 매번 전체 목록을 검사하지 않아도 됩니다.

### 5.3 Interval Tree보다 정렬 배열을 선택했다

Region의 시간 구간을 조회하는 방법으로 다음 선택지를 비교했습니다.

| 선택지                          | 얻는 점                               | 비용과 한계                                     |
| ------------------------------- | ------------------------------------- | ----------------------------------------------- |
| 선형 조회                       | 인덱스 생성 비용이 없음               | Viewport가 바뀔 때마다 모든 Region 검사         |
| 시작 시간만 정렬                | 오른쪽 경계를 빠르게 찾을 수 있음     | 먼저 시작한 긴 Region의 왼쪽 경계를 찾기 어려움 |
| 동적 Interval Tree              | 삽입·삭제와 구간 조회를 함께 지원     | 구현과 경계 조건 테스트 범위가 커짐             |
| 정렬 배열과 누적 최대 종료 시간 | 양쪽 경계를 이진 탐색하고 후보만 검사 | 목록 변경 시 인덱스 재생성과 추가 메모리 필요   |

현재 요구사항에서는 Region을 한 건씩 매우 자주 삽입하고 삭제하기보다, 목록이 변경되면 새로운 배열을 만들고 스크롤 중 읽기 조회를 반복했습니다. 이 조건에서는 동적 Interval Tree보다 정렬 배열과 누적 최대 종료 시간이 필요한 기능을 더 작은 구현 범위로 충족했습니다. 인덱스 생성에는 정렬이 포함되므로 `O(N log N)`의 비용이 발생합니다. 조회도 후보 검사와 결과 순서 복원이 필요하므로 단순히 `O(log N)`이라고 표현할 수는 없습니다. 이 구조의 목적은 계산을 없애는 것이 아니라, 반복 조회에서 확인해야 하는 후보의 수를 줄이는 것입니다. 700개 Region과 2,000개의 Viewport 범위를 사용한 합성 Benchmark에서는 다음 결과가 나왔습니다.

| 방식             | 검사한 Region 수 |
| ---------------- | ---------------: |
| 선형 조회        |      1,400,000개 |
| 시간 인덱스 조회 |         20,798개 |

알고리즘이 검사한 후보 수는 약 **98.5% 감소**했습니다. 다만 이 수치는 사용자가 체감한 속도나 Long Task 감소율이 아닙니다. 자료구조가 실제로 확인한 데이터 수가 줄었다는 의미로만 사용했습니다.

## [sort1] 6. React 실행과 Canvas draw를 Signal로 분리했다

### 6.1 스크롤 위치는 React UI보다 Canvas에 필요했다

스크롤하는 동안 Track 데이터와 JSX 구조는 변경되지 않았습니다. 최신 스크롤 위치가 필요한 곳은 Canvas draw 함수였습니다. 기존처럼 스크롤 위치를 React State와 Prop으로 전달하면 모든 TrackRow의 Prop이 변경됩니다.

```text
변경 전

scroll state 변경
→ 모든 TrackRow의 prop 변경
→ TrackRow React 실행
→ Canvas draw
```

반면 참조가 유지되는 Signal 객체를 TrackRow에 전달하면, TrackRow의 Prop은 그대로 유지하면서 Canvas 갱신 시점만 구독 함수로 전달할 수 있습니다.

```text
변경 후

scroll 위치를 ref에 기록
→ rAF에서 Signal 발행
→ TrackRow의 구독 함수 실행
→ Canvas draw
```

Signal은 스크롤 위치 자체를 저장하는 새로운 전역 Store가 아닙니다. 상태는 Ref에 보관하고, Signal은 구독자에게 **Canvas를 다시 그릴 시점이 됐다는 사실만 전달**합니다. 이 구조를 통해 React가 관리할 UI 상태와 Canvas 갱신 명령을 서로 다른 경로로 분리했습니다.

---

### 6.2 같은 Frame의 갱신 요청을 한 번으로 합쳤다

Wheel 이벤트는 짧은 시간 안에 여러 번 발생할 수 있습니다. Signal을 Wheel 이벤트마다 바로 발행하면 TrackRow의 React 실행은 피할 수 있지만, Canvas 갱신 요청은 이벤트 횟수만큼 그대로 남습니다. 그래서 `requestAnimationFrame`을 이용해 같은 Frame에 들어온 요청을 한 번으로 합쳤습니다.

```text
wheel event 1 ─┐
wheel event 2 ─┼─ 다음 rAF에서 Signal 한 번 발행
wheel event 3 ─┘
```

이미 rAF Callback이 예약돼 있다면 새로운 Callback을 추가하지 않았습니다. 다음 Repaint 전에 최신 스크롤 위치를 읽고 Signal을 한 번만 발행했습니다. 이 선택이 Wheel 이벤트 자체를 줄여 주는 것은 아닙니다. 또한 마운트된 모든 Track Canvas의 draw 비용을 제거하지도 않습니다. 같은 Frame 안에서 중복된 Canvas 갱신 예약을 하나로 합치는 역할만 합니다.

---

### 6.3 `React.memo`의 비교 조건만 바꾸지 않은 이유

스크롤 Prop을 `React.memo` 비교 대상에서 제외하는 방법도 검토했습니다. 하지만 Prop을 무시하면 React 실행은 건너뛸 수 있어도, Canvas가 최신 스크롤 위치를 사용해야 하는 시점을 전달할 방법이 사라집니다.

| 선택지                      | 얻는 점                                 | 비용과 한계                                     |
| --------------------------- | --------------------------------------- | ----------------------------------------------- |
| 스크롤 State·Prop 전달      | React 데이터 흐름 안에서 최신 위치 전달 | 스크롤마다 모든 TrackRow의 Prop 변경            |
| `React.memo` 비교 조건 변경 | 일부 TrackRow 실행을 건너뜀             | 무시한 Prop 대신 Canvas 갱신을 전달할 경로 필요 |
| rAF 기반 Signal 구독        | React 실행 없이 Frame당 한 번 갱신 요청 | 구독 해제와 최신 draw 함수 관리 필요            |

따라서 비교 조건을 억지로 우회하기보다, Canvas 갱신을 위한 별도 경로를 만들었습니다. 이 구조가 모든 React 렌더링을 제거하는 것은 아닙니다. TrackRow의 다른 Prop이나 State, Context가 변경되면 컴포넌트는 다시 실행됩니다. 이번 구조에서 분리한 것은 **스크롤 알림 때문에 발생하던 TrackRow 실행**입니다. 세로 Track 가상화는 별도의 최적화 축으로 남겨 두었습니다. 화면 밖 TrackRow의 작업을 줄일 수 있다는 장점은 있지만, Region 전체 조회 문제는 그대로 남습니다. 또한 드래그 좌표계와 Canvas 생명주기를 함께 변경해야 해 적용 범위가 더 컸습니다.

## [sort1] 7. Long Task는 줄었지만 전체 작업량이 줄었다고 말할 수는 없었다

두 최적화를 함께 적용한 뒤, Trace를 끈 상태에서 변경 전후를 각각 세 번 측정했습니다. 대표값으로 중앙값을 사용했습니다.

| 지표                      | 변경 전 | 변경 후 |        변화 |
| ------------------------- | ------: | ------: | ----------: |
| Long Task 횟수            |    74회 |    19회 |  74.3% 감소 |
| Long Task 누적 시간       | 4,418ms | 1,154ms |  73.9% 감소 |
| Long Task p95             |    82ms |    88ms |   7.3% 증가 |
| DOM wheel 입력 수신율     |   83.8% |   91.7% |  7.9%p 향상 |
| 입력 후 다음 Frame p95    |  75.1ms |  71.2ms |   5.2% 단축 |
| 메인 스레드 CPU 비율      |   82.7% |   84.3% |  1.6%p 증가 |
| React Commit              | 2,581회 | 2,950회 |  14.3% 증가 |
| React actualDuration 누적 | 2,875ms | 3,741ms |  30.1% 증가 |
| Animation Frame Gap p95   | 100.2ms | 100.1ms | 사실상 동일 |

Long Task 횟수와 누적 시간은 감소했습니다. DOM에서 실제로 관찰된 Wheel 입력도 증가했고, 입력 이후 다음 Frame까지 걸리는 p95 시간은 소폭 줄었습니다. 이 결과는 메인 스레드를 50ms 이상 연속으로 점유한 작업이 줄었다는 해석과 일치합니다. 하지만 모든 지표가 좋아진 것은 아니었습니다.

- 메인 스레드 CPU 비율은 감소하지 않음
- React Commit 횟수는 증가
- React actualDuration 누적 시간도 증가
- Animation Frame Gap은 사실상 동일

처음에는 Long Task가 크게 줄었으니 전체 렌더링 비용도 감소했다고 정리하고 싶었습니다. 하지만 측정값은 그 결론을 지지하지 않았습니다. 긴 Task가 여러 개의 짧은 Task로 분산됐을 가능성이 있으며, 전체 CPU 작업량은 그대로이거나 오히려 증가했을 수도 있습니다. 두 변경을 동시에 적용했기 때문에 시간 인덱스와 Signal 구조가 각각 어느 정도 기여했는지도 분리할 수 없었습니다. 그래서 결과를 다음 문장으로 제한했습니다.

> 전체 CPU와 React 작업량은 줄지 않았지만, 두 변경을 함께 적용한 뒤 메인 스레드를 50ms 이상 연속으로 점유한 Task의 횟수와 누적 시간이 감소했다.

성능 수치는 구현을 칭찬하기 위한 점수가 아니라, 무엇을 주장할 수 있고 무엇은 아직 주장할 수 없는지 구분하기 위한 근거였습니다.

## [sort1] 8. 아직 확인해야 할 병목이 남아 있다

이번 변경으로 Region 후보 검사와 스크롤로 발생하던 TrackRow 실행 경로를 줄였습니다. 하지만 다음 비용은 여전히 남아 있습니다.

다음 순서로 남은 병목을 확인할 예정입니다.

5. 화면 밖 Track Canvas의 갱신 요청을 차단한 결과 비교

## [sort1] 9. 최적화는 기법보다 실행 조건을 구분하는 일이었다

처음에는 Virtual Scroll, `React.memo`, Interval Tree처럼 익숙한 최적화 기법의 이름부터 떠올렸습니다. 하지만 코드를 따라가 보니 문제는 특정 기술이 없어서 발생한 것이 아니었습니다. Viewport는 이미 계산하고 있었지만 실제 데이터 조회는 전체 순회하고 있었습니다. `React.memo`도 이미 적용돼 있었지만, Canvas를 갱신하기 위한 값을 React Prop으로 전달하면서 매번 비교 조건을 무효화하고 있었습니다. 결국 중요한 질문은 다음과 같았습니다.

- 어떤 데이터가 자주 변경되는가?
- 변경될 때마다 어떤 작업이 반복되는가?
- 그 변화가 React UI에 필요한가, Canvas draw에 필요한가?
- 업데이트 비용을 언제 지불하고 조회 비용을 언제 줄일 것인가?

이 질문을 기준으로 Region 변경보다 Viewport 조회가 더 자주 발생하는 구조에서는 시간 인덱스를 선택했습니다. 스크롤 위치가 React UI보다 Canvas draw에 필요한 구조에서는 Signal 구독 경로를 선택했습니다.

두 방법이 모든 타임라인에 적용할 수 있는 정답이라고 생각하지는 않습니다. Region 변경 빈도가 높아지면 인덱스 생성 비용이 문제가 될 수 있습니다. Track 수가 크게 늘어나면 화면 밖 Canvas draw와 세로 가상화가 더 중요한 병목이 될 수 있습니다. 이번 작업을 하며 최적화는 유명한 기법을 적용하는 일이 아니라, 현재 실행 경로에서 반복되는 비용을 찾아 변화의 성격에 맞게 분리하는 일이라는 점을 다시 확인했습니다. 그리고 측정 결과가 기대와 다를 때 결과를 억지로 성공으로 정리하지 않는 것도 설계만큼 중요했습니다. 모든 선택에 “왜?”라고 물었을 때 현재의 데이터와 실행 조건으로 답할 수 있는 구조를 만들고 싶습니다. 아직 확인해야 할 병목은 남아 있지만, 확인하지 않은 부분을 이미 해결된 것처럼 말하지 않고 하나씩 측정해 나가는 것이 가장 빠른 길이라고 생각합니다.
