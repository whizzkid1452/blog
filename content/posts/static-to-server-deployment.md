처음에는 SEO를 중요하게 생각해 블로그를 정적 배포로 만들었다. 모든 공개 글을 빌드할 때 HTML로 생성하면 검색 엔진과 사용자가 완성된 문서를 바로 받을 수 있기 때문이다.

하지만 댓글과 비공개 글을 추가하면서 요구사항이 달라졌다. 특히 Markdown으로 관리하는 비공개 글은 로그인 화면만으로 보호할 수 없었다. 결국 공개 글의 정적 생성은 유지하되, 배포 방식은 Next.js 서버가 실행되는 구조로 바꾸었다.

> 이번 결정의 핵심은 로그인을 추가하는 일이 아니라, 비공개 글의 본문을 서버의 인가 결과에 따라 제공하는 일이었다.

## [sort1] 1. 왜 처음에는 정적 배포를 선택했는가

처음 선택한 방식은 Next.js의 `output: 'export'`였다. 빌드 시 공개 글을 HTML 파일로 만들고, 정적 파일 호스팅에서 그대로 제공하는 구조다.

이 방식은 블로그의 초기 조건과 잘 맞았다.

- 글이 Markdown 파일로 관리되고 자주 바뀌지 않았다.
- 요청마다 실행할 서버 로직이 없었다.
- CDN에 정적 파일을 배포하는 구조가 단순했다.
- 공개 글의 완성된 HTML을 검색 엔진에 제공할 수 있었다.

다만 당시에는 **정적 생성(Static Site Generation, SSG)**과 **정적 호스팅**을 사실상 같은 선택으로 생각했다. 둘은 다른 개념이다. SSG는 HTML을 언제 생성하는지에 관한 렌더링 방식이고, 정적 호스팅은 생성된 파일을 어떤 실행 환경에서 제공하는지에 관한 배포 방식이다.

따라서 서버에 배포하더라도 공개 글을 빌드 시점에 생성할 수 있다. 이 구분이 이후 판단을 바꾸는 출발점이 되었다.

## [sort1] 2. 무엇이 문제였는가

### [sort2] 2-1. 로그인과 인가는 다른 문제였다

정적 사이트에서도 Supabase Auth를 이용한 클라이언트 로그인을 구현할 수 있다. 브라우저가 로그인하고 Session을 얻은 뒤 화면을 바꾸는 것까지는 가능하다.

하지만 로그인 여부에 따라 화면만 가리는 것은 비공개 글의 **인가(Authorization)**가 아니다. 인증(Authentication)은 사용자가 누구인지 확인하는 절차이고, 인가는 확인된 사용자에게 특정 자원 접근을 허용할지 결정하는 절차다.

비공개 Markdown을 빌드 시 공개 정적 HTML에 포함하면 파일 자체는 이미 배포되어 있다. 로그인하지 않은 사용자도 HTML 파일의 직접 경로나 네트워크 응답을 통해 본문에 접근할 가능성이 있다. 클라이언트 화면은 이 파일의 접근 권한을 통제하지 못한다.

즉, 클라이언트 로그인은 가능했지만 비공개 본문을 보호하는 보안 경계로는 충분하지 않았다.

### [sort2] 2-2. 댓글은 서버 전환의 필요조건이 아니었다

댓글은 브라우저가 Supabase를 직접 호출하는 구조로도 구현할 수 있다. Publishable key와 Row Level Security(RLS)를 사용하면 정적 배포를 유지하면서 댓글을 읽고 쓸 수 있다.

따라서 댓글 기능만으로 서버 배포가 반드시 필요했다고 말할 수는 없다. 이 프로젝트에서는 입력 검증, 글 존재 여부 확인, 오류 응답 형식을 한곳에서 관리하기 위해 Next.js API Route를 사용했다. 관리자 삭제, 신고, 요청 횟수 제한 같은 기능을 추가할 때도 이 경계가 유용하다고 판단했다.

서버 전환의 직접적인 판단 근거는 **현재 Markdown 구조를 유지하면서 비공개 본문을 요청 시점에 인가해야 한다는 요구사항**이었다.

## [sort1] 3. 어떤 선택지를 비교했는가

두 가지 구조를 같은 기준으로 비교했다.

| 선택지                                                    | 얻는 점                                                                           | 비용과 한계                                                 |
| --------------------------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Next.js 서버 배포 + Markdown 유지                         | 기존 글 작성 흐름 유지, 요청 시점의 Session 검사, API Route와 서버 환경 변수 사용 | 서버 실행 환경, 배포·모니터링·장애 대응 필요                |
| 정적 배포 유지 + 비공개 본문을 Supabase DB/Storage로 이동 | 정적 호스팅의 단순성 유지, Auth와 RLS로 데이터 접근 제한                          | 기존 Markdown 이전, 글 조회 계층 재작성, 저장소 의존성 증가 |

두 번째 방식도 안전하게 설계할 수 있다. 비공개 본문을 공개 HTML에 넣지 않고, 인증된 사용자가 Supabase에서 읽도록 RLS 정책을 적용하면 된다.

다만 현재 글은 모두 Markdown 파일로 관리하고 있었다. 이 방식을 선택하면 비공개 글만 별도의 저장소와 편집 흐름으로 옮겨야 했다. 공개 글과 비공개 글의 조회 경로도 달라진다.

## [sort1] 4. 왜 서버 배포를 선택했는가

이 프로젝트에서는 첫 번째 선택지를 택했다. 이유는 세 가지였다.

첫째, 기존 Markdown 작성 방식을 유지할 수 있다. 글의 저장 위치와 편집 도구를 바꾸지 않고, 서버가 Session을 확인한 뒤에만 비공개 본문을 반환하면 된다.

둘째, 공개 글의 SSG를 유지할 수 있다. 서버 배포는 모든 페이지를 요청마다 렌더링한다는 뜻이 아니다. 공개 글은 빌드 시 생성하고, 인증이 필요한 경로와 API만 요청 시점에 처리할 수 있다.

셋째, 댓글과 이후의 운영 기능에 공통 서버 경계를 둘 수 있다. 현재 댓글 API는 요청 형식과 글 존재 여부를 확인한 뒤 Supabase Repository를 호출한다. 이후 관리자 삭제나 신고 처리가 필요해지면 같은 경계에서 사용자 권한과 서버 전용 자격 증명을 다룰 수 있다.

이 선택이 모든 프로젝트에 더 낫다는 뜻은 아니다. 비공개 콘텐츠를 처음부터 Supabase에 저장했다면 정적 배포와 RLS 조합이 더 단순할 수 있다. 이번 결정은 기존 Markdown 구조를 유지한다는 조건에 따른 설계 판단이다.

## [sort1] 5. 어떻게 구조를 변경했는가

Next.js 설정을 `output: 'export'`에서 `output: 'standalone'`으로 바꿨다.

```ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  output: 'standalone',
};

export default nextConfig;
```

`standalone`은 실행에 필요한 서버 파일과 의존성을 별도 산출물로 만든다. 이 산출물을 실행하기 위해 Node.js 22 기반의 다단계 Dockerfile을 추가했다. 런타임 컨테이너는 root가 아닌 `nextjs` 사용자로 실행하고, 정적 자산과 Markdown 원본을 함께 포함한다.

배포 환경이 현재 서버 프로세스의 상태를 확인할 수 있도록 `/api/health`도 추가했다. 이 응답은 `force-dynamic`과 `Cache-Control: no-store`를 사용해 CDN cache가 아닌 실행 중인 서버의 응답을 확인하도록 했다.

댓글 요청 흐름은 다음과 같이 구성했다.

```text
브라우저
  → Next.js API Route
  → CommentRepository
  → Supabase PostgreSQL
```

Supabase에서는 `anon` 역할에 댓글 조회와 작성만 허용하고, PostgreSQL 테이블 권한과 RLS 정책을 함께 적용했다. API Route는 입력 검증과 HTTP 응답을 담당하지만 데이터베이스 권한을 대신하지 않는다.

비공개 글은 `visibility: authenticated`로 구분한다. 공개 목록, sitemap, RSS에서 제외하고, 상세 페이지에서는 서버가
Google 로그인 Session과 `GOOGLE_AUTHORIZED_EMAIL`을 확인한 뒤 본문을 반환한다. 이 글도 같은 설정을 사용한다.

## [sort1] 6. SEO에는 어떤 영향이 있는가

서버 배포로 바꿨다고 SEO가 자동으로 좋아지거나 나빠지는 것은 아니다. 검색 엔진 최적화에는 완성된 HTML, metadata, canonical URL, sitemap, 구조화 데이터, 응답 속도 같은 여러 조건이 영향을 준다.

이번 변경에서는 공개 글의 정적 생성을 유지했다. 즉, 배포 환경에는 Node.js 서버가 존재하지만 공개 글은 계속 빌드 시점의 HTML을 제공한다. 서버가 필요한 경로만 요청 시점에 처리한다.

비공개 글은 검색 대상이 아니므로 공개 목록, sitemap, RSS에서 제외하고 `noindex` metadata를 사용한다. 공개 글의 SEO와 비공개 글의 접근 통제를 같은 기준으로 해결하려 하지 않았다.

> SEO를 위해 필요한 것은 정적 호스팅 자체가 아니라, 검색 엔진이 안정적으로 읽을 수 있는 공개 문서다.

## [sort1] 7. 어떤 비용을 감수했는가

서버 배포로 다음 기능을 얻었다.

- 요청 시점의 인증과 인가
- 서버 전용 환경 변수 사용
- API Route에서의 입력 검증과 일관된 오류 응답
- 관리자 기능, 신고, 요청 횟수 제한을 추가할 수 있는 경계
- 서버 로그와 health check를 통한 운영 상태 확인

반대로 다음 비용이 생겼다.

- Node.js 서버 또는 컨테이너를 계속 실행해야 한다.
- 서버 장애가 동적 경로와 API의 가용성에 영향을 준다.
- 배포 설정, secret 관리, health check와 로그 확인이 필요하다.
- 인증 응답이 공유 cache에 저장되지 않도록 cache 정책을 관리해야 한다.
- Node.js와 의존성의 보안 업데이트를 지속해야 한다.

정적 파일만 배포할 때보다 운영할 대상이 늘어난 것은 분명한 비용이다. 이번에는 비공개 Markdown을 별도 저장소로 이전하는 비용보다 서버 운영 비용을 감수하는 편이 현재 구조에 맞다고 판단했다.

## [sort1] 8. 무엇을 검증했고 무엇이 남았는가

서버 배포 변경에서는 Next.js production build, 설정 테스트, health route 테스트를 통과했다. 빌드 결과에서 공개 글 경로가 정적으로 생성되는 것도 확인했다. 댓글 기능은 단위 테스트, typecheck, lint, production build를 통과했고, 실제 Supabase의 댓글 조회와 transaction rollback을 이용한 익명 작성 권한을 확인했다.

다만 이 결과가 운영 환경 전체를 증명하지는 않는다. 작업 환경에 Docker 실행 파일이 없어 컨테이너 image build 자체는 직접 확인하지 못했다. 실제 배포 환경에서는 다음 항목을 추가로 확인해야 한다.

- 컨테이너 build와 기동
- 인증되지 않은 비공개 글 직접 접근 차단
- 로그인 후 원래 글로 돌아오는 redirect
- 비공개 응답의 cache 방지
- 서버 재시작과 Supabase 장애 시 동작

서버 런타임은 비공개 Markdown 보호의 필요조건이지만 충분조건은 아니다. 모든 비공개 경로에서 Session을 검사하고, 본문을 공개 build 산출물과 sitemap, RSS에 포함하지 않아야 한다. cache와 로그에 민감한 본문이 남지 않는지도 별도로 확인해야 한다.

## [sort1] 9. 이번 결정에서 배운 점

처음에는 “SEO가 중요하니 정적 배포가 맞다”라고 생각했다. 이 판단은 공개 글만 있을 때는 합리적이었다. 하지만 로그인과 비공개 글이 추가된 뒤에도 같은 결론을 유지하려면 정적 생성, 정적 호스팅, 인증, 인가를 구분해야 했다.

댓글은 서버 없이도 만들 수 있었고, 로그인도 정적 사이트에서 가능했다. 문제는 이미 공개 파일로 배포된 Markdown 본문을 클라이언트 화면만으로 보호할 수 없다는 점이었다.

> 배포 방식은 기술의 선호가 아니라, 어느 시점에 누가 콘텐츠 접근을 결정해야 하는지에 따라 선택해야 한다.

이번 구조는 공개 글의 SSG와 비공개 글의 서버 측 인가를 함께 사용한다. 정적 방식과 서버 방식을 하나만 고르는 대신, 각 경로의 요구사항에 맞게 렌더링과 권한 경계를 나누었다. 앞으로 비공개 콘텐츠가 DB 중심으로 바뀌거나 서버 운영 비용이 더 커지면 정적 배포와 Supabase RLS 조합을 다시 비교할 수 있다.
