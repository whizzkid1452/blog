[1편](/posts/browser-multieditor-architecture-design)에서는 UI, 제품 흐름, 편집 코어를 나누는 초기 기준을 정했다. 실제 타임라인 기능을 붙이자 영상·오디오·이미지·텍스트를 각각 분리하는 것만으로 설명되지 않는 작업이 보였다.

재생, 선택, Undo/Redo, 내보내기는 여러 미디어를 함께 다룬다. 나는 VOIX STUDIO의 웹 아키텍처를 구현하면서 이 조율 책임을 제품의 Session 계층으로 드러내고, 공통 편집 규칙은 `daw-engine`에 남겼다. 이 글에서 Session 계층은 제품의 작업 조율 영역이며, 엔진 내부의 Session 모델이나 Electron Main의 프로젝트 세션과 구분한다.

## [sort1] 1. Facade라는 이름만으로 계층이 정해지지는 않았다

처음에는 Page, Component, Hook, Facade, Store, Service를 나누어 설명했다. 하지만 Hook은 React에서 로직을 연결하는 방식이고, Facade는 여러 기능을 하나의 진입점 뒤에 감추는 패턴이다. 이 이름들만으로 시스템의 책임이 나뉘지는 않았다.

중요한 질문은 파일의 종류가 아니라 누가 무엇을 결정하는가였다. 사용자 요청을 해석하는 제품 흐름, 여러 미디어를 조율하는 작업, 편집 규칙을 실행하는 코어를 기준으로 다시 설명했다.

도메인 폴더 분리는 계속 사용하되, 프로젝트 전체를 조율하는 흐름을 각 도메인 Store 사이의 간접 호출에 숨기지 않기로 했다.

## [sort1] 2. 타임라인에는 미디어를 횡단하는 조율이 필요했다

영상 디코딩과 오디오 파형 계산은 각 미디어의 고유 작업이다. 반면 한 타임라인에서 재생 위치를 맞추거나 영상 가져오기를 되돌리는 작업은 여러 영역의 정보를 함께 사용한다.

제품의 Session 계층에는 이런 조율 책임을 둔다.

- 재생에서는 코어의 시간을 기준으로 미디어 출력을 맞춘다.
- 선택에서는 여러 화면이 참조할 선택 대상을 관리한다.
- 가져오기에서는 파일 준비와 트랙·Region 등록을 연결한다.
- 내보내기에서는 확정된 편집 상태와 미디어를 수집해 처리 파이프라인에 전달한다.

편집 규칙과 이력 자체를 이 계층에서 다시 구현하지는 않는다. 코어의 Command와 Transaction을 호출하고 제품 상태를 연결한다. 여러 Command로 이루어진 편집은 하나의 Undo/Redo 단위로 묶을 수 있다.

## [sort1] 3. 제품 Adapter가 코어와 화면을 연결한다

엔진이 제품 Store를 직접 읽게 하면 당장은 연결 코드가 짧아진다. 대신 엔진을 다른 UI나 실행 환경에서 사용할 때 제품 상태까지 함께 가져와야 한다.

그래서 제품의 Adapter가 코어에 전달할 입력과 변경 결과의 반영을 맡도록 했다. 오디오 재생은 AudioProvider 계약으로 런타임에 위임한다.

```text
제품 UI
→ 사용자 동작 처리·Session 조율
→ 제품 Adapter
→ daw-engine의 Command·편집 모델
→ AudioProvider를 통한 재생·렌더링
```

이 그림은 책임 경계를 요약한 것이다. 모든 동작이 매번 모든 계층을 통과한다는 뜻은 아니다. 메뉴 열림처럼 UI 안에서 끝나는 변경과 프로젝트 문서를 바꾸는 편집 요청을 구분한다.

## [sort1] 4. Store 구독과 rAF는 역할이 다르다

초기에는 Store를 구독하면 의존성이 복잡해지고, rAF 루프가 값을 읽으면 단방향 흐름이 유지된다고 생각했다. 하지만 구독과 폴링 중 어느 방식을 쓰는지만으로 상태의 소유권이 정해지지는 않는다.

프로젝트 문서를 바꾸는 요청은 명시적인 편집 경로를 사용한다. 재생 위치나 드래그 임시 좌표처럼 자주 변하는 값은 소비하는 화면에 맞춰 전달한다. Canvas에만 필요한 값까지 React state로 전달하면 컴포넌트를 불필요하게 다시 실행할 수 있다.

이후 타임라인에서는 Ref와 Signal, rAF로 Canvas 갱신 경로를 나누었다. 관련 결과는 [시간 인덱스와 rAF Signal 최적화 글](/posts/timeline-performance-region-index-decision)에서 다룬다. UI 갱신 주기를 조정하는 일과 편집 데이터를 확정하는 일은 서로 다른 책임이다.

## [sort1] 5. 폴더 구조보다 의존성 경계를 먼저 드러냈다

초기 구현에서는 UI, 제품 로직, Session, Store, Engine을 상위 폴더에서 확인할 수 있는 구조를 택했다. 다음은 그 책임을 단순화한 예시다.

```text
editor/
├── ui/        사용자 입력과 화면 표시
├── logics/    제품의 사용자 동작 처리
├── session/   여러 미디어를 다루는 작업 조율
├── stores/    제품 UI와 실행 상태
└── adapters/  제품과 공통 편집 코어의 연결
```

폴더 구조가 같아도 의존성은 다르게 얽힐 수 있다. 엔진이 UI를 직접 읽는지, 같은 문서를 여러 Store에서 독자적으로 수정하는지, 객체 생성과 연결이 어디서 이루어지는지 함께 확인해야 한다.

후속 Electron 작업에서는 창별 Store를 동기화하는 방식의 한계도 드러났다. DYNA STUDIO에서 Main Process를 문서 상태의 SSOT로 정한 이유는 [Electron 회고](/posts/electron-main-process-ssot-decision)에 별도로 정리했다.

## [sort1] 6. 확인한 변화와 적용 기준

제품의 조율 책임과 코어의 편집 규칙을 구분하고, 개인 개발한 코어를 제품 Adapter 뒤에서 재사용했다. 이 구조만의 성능 향상률이나 온보딩 시간 단축률을 측정한 것은 아니다.

- [ ] 여러 미디어를 함께 다루는 작업의 진입점을 찾을 수 있는가.
- [ ] 제품 조율 코드가 코어의 편집 규칙을 중복 구현하지 않는가.
- [ ] 엔진이 제품 UI나 특정 Store 구현에 직접 의존하지 않는가.
- [ ] 문서 변경과 프레임 단위 시각 갱신을 구분했는가.
- [ ] 폴더 이름과 실제 import 방향이 같은 책임 경계를 보여주는가.

설계를 수정하며 배운 것은 추상화의 이름만으로 경계가 생기지 않는다는 점이었다. 한 번의 사용자 동작이 어디서 시작되고, 누가 데이터를 확정하며, 어떤 결과가 화면으로 돌아오는지 설명할 수 있어야 했다.
