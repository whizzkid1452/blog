영상, 오디오, 이미지, 텍스트를 한 타임라인에서 편집할 때는 같은 변경을 여러 화면과 내보내기가 함께 해석해야 한다. 클립을 자른 결과가 타임라인에는 반영되고 미리보기에는 남아 있다면, 기능 하나의 문제가 프로젝트 전체의 정합성 문제로 이어진다.

나는 고객용 웹 에디터인 VOIX STUDIO의 초기 아키텍처와 타임라인, 저장, 내보내기 등 프론트엔드 전반을 개발했다. 이 글은 그중 **제품 UI와 편집 코어의 경계를 나누고 변경 경로를 정한 초기 설계**를 기록한다. 사내용 Electron 제품인 DYNA STUDIO의 Main Process SSOT 재설계는 [별도 회고](/posts/electron-main-process-ssot-decision)에서 다룬다.

## [sort1] 1. 기능마다 같은 편집 규칙을 다시 만들지 않기

한 번의 클립 이동은 타임라인 위치, 미리보기, 재생과 내보내기에 영향을 준다. 각 기능이 자신의 Store를 따로 고치면 같은 편집을 서로 다르게 해석할 수 있다.

그래서 개인 개발한 TypeScript 오디오 편집 라이브러리인 `daw-engine`을 제품의 편집 코어로 적용했다. 기존 글에서 `drop-ai/core`로 부르던 코어다. Session·Track·Region·Source와 편집 명령을 UI에서 분리하고, 제품 Adapter가 UI와 엔진의 연동을 맡도록 했다.

이 방식에서 중요한 것은 라이브러리 사용 자체보다 편집 규칙의 위치다. 클립을 자르고 이동하는 규칙을 제품 화면이 각각 구현하지 않고 공통 코어의 계약을 사용한다.

## [sort1] 2. 계층은 변경 이유를 기준으로 나누었다

### [sort2] 2-1. UI와 제품 흐름, 엔진의 책임

UI는 입력과 화면 표시를 맡는다. 제품 흐름을 조율하는 계층은 파일 가져오기, 저장, 내보내기처럼 여러 작업의 순서를 정한다. 엔진은 편집 규칙과 오디오 처리 계약을 제공한다.

```text
사용자 입력
→ 제품의 동작 처리
→ Adapter를 통해 편집 Command 실행
→ 확정된 편집 상태와 변경 알림
→ 타임라인·미리보기 갱신
```

엔진이 React 컴포넌트나 제품 Zustand Store를 직접 import하면 다른 제품에서도 그 의존성을 함께 준비해야 한다. 필요한 값과 콜백을 계약으로 전달하고, 제품별 연결은 Adapter에 두었다.

### [sort2] 2-2. 화면 영역과 도메인을 구분했다

처음에는 Header, Menu, Preview, Timeline처럼 화면에 보이는 영역을 기준으로 코드를 나누려 했다. 위치를 찾기는 쉬웠지만, 화면 영역만으로 편집 규칙의 소유자를 설명하기는 어려웠다.

영상·오디오·텍스트·이미지의 고유 처리와, 프로젝트 전체의 시간·재생·이력 관리를 구분해야 했다. 폴더를 나누는 기준과 상태 변경 권한을 정하는 기준도 같지 않았다. 이 구분을 실제 타임라인 구현에 맞춰 수정한 과정은 [2편](/posts/browser-multieditor-architecture-change)에서 이어진다.

## [sort1] 3. SSOT는 최종 변경 권한의 기준이다

단일 진실 공급원(SSOT)은 모든 값을 큰 Store 하나에 넣는다는 뜻이 아니다. 같은 편집 결과를 확정하는 주체를 정하고, 다른 화면은 그 결과를 읽도록 만드는 기준이다.

웹 에디터에서는 코어 Session의 편집 상태를 기준으로 제품 UI를 연결했다. 메뉴 열림이나 선택 표시 같은 UI 상태, AudioBuffer와 디코더 같은 실행 리소스는 별도로 다룬다. 이 구분이 없으면 저장할 문서와 화면을 그리기 위한 임시값이 섞인다.

Electron의 여러 창은 서로 다른 실행 환경이므로 브라우저 한 화면의 Store 구독만으로 상태가 공유되지 않는다. 이후 DYNA STUDIO에서는 문서 확정 권한을 Main Process에 두고 각 Renderer가 확정 결과를 받도록 설계했다. 웹의 Session과 Electron Main의 역할을 같은 전역 Store로 설명해서는 안 된다.

## [sort1] 4. 편집 동작은 Command 계약으로 연결했다

현재 코어는 약 70개 편집 동작을 `{ type, payload }` 형태의 Command와 도메인별 Handler로 제공한다. Zod 스키마로 실행 전 입력을 검증하고, 복합 작업은 Transaction으로 묶어 하나의 Undo/Redo 단위로 기록한다.

아래는 계약의 형태만 보여주는 예제이며 실제 Command 이름과 전체 타입 정의는 생략했다.

```ts
type MoveRegionCommand = {
  type: 'region.move';
  payload: {
    regionId: string;
    startFrame: number;
  };
};
```

UI는 수행할 동작과 입력을 전달한다. 편집 규칙과 이력 기록은 코어에서 처리한다. 이 계약 덕분에 UI·CLI·AI Agent 같은 호출 주체가 달라도 같은 편집 경계를 사용할 수 있다. 각 호출 주체가 입력 검증이나 Undo 규칙을 별도로 구현할 필요를 줄이는 구조다.

## [sort1] 5. 적용 결과와 남은 비용

개인 개발한 코어를 DYNA·VOIX STUDIO의 제품 Adapter 뒤에 적용해 브라우저와 Electron에서 편집 규칙을 재사용했다. UI와 오디오 런타임을 분리한 경계는 코어를 제품 화면 없이 테스트할 수 있는 기반이 되었다. 아키텍처 분리만의 개발 시간 단축률은 따로 측정하지 않았다.

경계를 나누면 연결 코드와 계약 관리 비용이 생긴다. 새 편집 동작을 추가할 때는 Command, Handler, 제품 Adapter와 화면 반영 경로가 같은 의미를 유지하는지 확인해야 한다. 계층 이름을 늘리는 것보다 이 경로를 추적할 수 있는지가 중요했다.

## [sort1] 6. 적용해보기

- [ ] 같은 편집 규칙이 여러 화면에 중복되어 있지 않은지 확인한다.
- [ ] 편집 상태를 확정하는 주체와 화면 캐시를 구분한다.
- [ ] 저장 문서, UI 상태, 실행 리소스의 수명을 나눈다.
- [ ] 제품과 엔진의 의존성을 Adapter에서 연결한다.
- [ ] 복합 편집의 Undo 단위와 입력 검증 경계를 함께 정한다.

초기 설계에서 얻은 기준은 폴더 모양보다 변경 권한과 계약이었다. UI를 바꾸거나 실행 환경을 옮겨도 같은 편집 규칙을 유지할 수 있어야 했다.
