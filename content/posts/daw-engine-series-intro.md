웹 브라우저에서 멀티트랙 오디오 편집기를 만든다면 어디부터 시작해야 할까요?

이 시리즈는 TypeScript로 만든 DAW(Digital Audio Workstation) 핵심 엔진 **daw-engine**을 설계하고 구현하면서 부딪힌 문제들을 기록한 글이에요. Part 1부터는 Tempo Map, Meter DSP, Automation, MIDI 파싱, Export 파이프라인, Processing Graph, Transport FSM을 차례로 다뤄요.

본격적인 코드 이야기에 앞서 전체 지도를 먼저 펼쳐 보려고 해요. DAW가 무엇인지, 오디오 편집 도메인이 일반 웹 개발과 왜 다른지, 그리고 이미 좋은 오디오 도구들이 많은데도 왜 굳이 `daw-engine`을 직접 만들게 되었는지 차근차근 짚어 볼게요.

## [sort1] 1. 미디 작곡을 하던 사람이 DAW 엔진을 만들기까지

저는 개발보다 미디 시퀀싱과 작곡을 먼저 시작했어요. 공대를 짧게 다니다 작곡으로 전공을 바꿨고, 대학원에서는 뉴미디어음악과 사운드 엔지니어링에 관심이 깊어졌죠.

그때 매일 쓰던 도구가 바로 **DAW**였어요. GarageBand, Ableton Live, Logic Pro, Cubase처럼 소리를 녹음하고, 자르고, 섞어서 하나의 음원으로 완성하는 소프트웨어예요. 개발자 입장에서 비유하자면 **음악을 만드는 IDE**에 가까워요. 오디오 파일이나 MIDI 같은 입력 소스를 받아서 트랙, 이펙트, 시간축이라는 도구를 조합해 원하는 사운드와 타임라인을 빌드하거든요.

도구를 조립하고 신호 흐름을 고쳐서 원하던 소리가 나왔을 때의 만족감이 정말 컸는데, 나중에 코딩을 처음 접했을 때도 똑같은 감각을 느꼈어요. 로직을 조립해 기능을 만들고, **복잡한 구조와 물리적 한계를 계산과 논리로 딱 맞아떨어지게 푸는 일이 작곡과 너무 닮아 있었거든요.**

그렇게 독학으로 개발을 시작해 실무 제품 코드에 뛰어들면서 자연스럽게 목표가 하나 생겼어요.

_"웹 기술로 내가 쓰던 DAW에 가까운 편집 엔진을 직접 만들어 보고 싶다."_

물론 화면에 보이는 화려한 DAW UI 전체를 혼자 다 만들려는 건 아니었어요. 화면에는 파형과 노트가 보이지만, 그 아래 엔진에서는 시간 좌표, 오디오 버퍼, 이벤트 스트림, 파라미터 곡선이 쉴 새 없이 맞물려 돌아가거든요. 이 시리즈에서 다루는 건 바로 그 **오디오 편집기의 공통 핵심 규칙만 떼어내 TypeScript 라이브러리로 분리한 'DAW Core'** 이야기예요.

## [sort1] 2. 일반 CRUD 웹 개발과는 무엇이 다를까요?

막상 오디오 편집 엔진을 설계해 보니, 데이터를 저장하고 조회해서 화면에 보여 주는 일반 CRUD 웹 서비스와는 결이 완전히 다른 문제들을 자주 마주하게 됐어요. 대표적인 특징은 다섯 가지예요.

| 특성                     | 개발할 때 왜 까다로울까요?                                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **이중 시간축**          | 오디오 장치는 Frame(같은 시점의 채널별 PCM 샘플 묶음) 단위로 움직이는데, 사람은 '13마디 2박' 같은 음악적 시간으로 생각해요. |
| **비파괴 편집**          | 원본 오디오 파일을 직접 자르지 않고, 재생 위치, 길이, 이펙트 설정만 바꿔서 실시간으로 다시 들려줘야 해요.                   |
| **실시간과 오프라인**    | 재생할 때는 낮은 지연(Latency)이 생명이고, 파일로 내보낼(Export) 때는 정확한 후처리 순서가 생명이에요.                      |
| **제각각인 상태의 수명** | 재생 상태 머신, Undo 히스토리, 음량 누적값, 이펙트 의존성 그래프가 모두 다른 주기로 변해요.                                 |
| **경계 밖의 백엔드**     | Core가 Web Audio나 네이티브 엔진을 직접 소유하지 않고, 렌더링과 재생을 명확한 계약(인터페이스)으로 위임해야 해요.           |

예를 들어 볼까요? 곡 중간에 템포가 바뀌는 순간, `beats * 60 / bpm * sampleRate` 같은 단순한 공식은 바로 깨져 버려요. 볼륨 오토메이션은 점을 저장하는 것 외에도, 점 사이를 어떻게 보간할지, 재생 중에 사용자가 노브를 돌리면 어떤 값을 우선할지 정해야 해요. MIDI 파일은 예쁜 Note 배열이 아니라 Note On/Off 이벤트가 이어진 스트림이고, 오디오 Export도 인코더 한 번 호출하는 게 아니라 `Normalize → True Peak Limit → Dither → Encode`라는 엄격한 순서를 지켜야 하죠.

각 글에서는 이 특성이 시간 변환이나 음량 측정, 편집 명령 같은 구체적인 구현 문제로 어떻게 이어지는지 살펴봐요.

## [sort1] 3. 왜 daw-engine을 직접 만들었을까요?

오디오 편집기를 실제로 개발해 보면, 소리를 재생하는 것 자체보다 그 바깥에 쌓이는 수많은 편집 규칙을 하나의 프로젝트 상태에 맞춰 어긋나지 않게 연결하는 일이 훨씬 까다로워요.

흔한 편집 시나리오 하나만 따라가 볼까요? 사용자가 음성 클립을 둘로 나누고, 뒷부분을 뒤로 옮긴 다음, 리버브 버스로 신호를 보내 마스터 믹스로 내보낸다고 해 봐요. 이 짧은 작업 뒤에서 개발자가 챙겨야 할 일은 생각보다 많아요.

- 분할된 두 클립이 원본 오디오의 어느 구간을 참조하는지 비파괴 방식으로 관리해야 해요.
- 클립을 옮긴 위치가 화면 타임라인과 오디오 재생 예약에 똑같이 반영되어야 해요.
- 사용자가 `Cmd+Z`로 분할과 이동을 되돌리면 이전 배치와 상태로 정확히 복원되어야 해요.
- 최종 익스포트(Export)를 돌릴 때도 현재 프로젝트의 클립 배치와 리버브 버스 라우팅이 그대로 적용되어야 해요.

제품을 만들 때마다 이런 프로젝트 모델, 편집 명령과 Undo/Redo 이력, 트랙과 버스 라우팅, 백엔드 동기화 구조를 매번 처음부터 짜는 건 부담이 너무 컸어요.

그래서 **화면(UI)과 오디오 실행 백엔드 사이에서 편집기의 공통 구조를 재사용할 수 있는 라이브러리**로 `daw-engine`을 만들게 되었어요. 프로젝트 상태는 `Session`이, 실행 취소 가능한 편집 이력은 `CommandHistory`가, 상태 변경과 오디오 백엔드 연결은 `AudioEngine`이 맡는 구조예요.

이 구조는 음악 제작 도구와 팟캐스트나 내레이션 편집기처럼 화면과 조작 방식이 다른 제품에서도 편집 모델을 재사용할 수 있게 해요. 사내 미디어 편집기 AnAI Media Editor에는 제품 전용 어댑터를 통해 연결했어요.

## [sort1] 4. 기존 오디오 도구들과 무엇이 다를까요?

"이미 Web Audio API나 Tone.js, wavesurfer.js 같은 좋은 도구들이 많은데, 굳이 새로 만들 필요가 있었을까?" 하는 의문이 자연스럽게 들 수 있어요.

차이를 정확히 보려면 **각 도구가 이미 잘해 주는 영역**과 **멀티트랙 편집기를 만들기 위해 개발자가 추가로 쌓아야 하는 영역**을 나눠서 봐야 해요.

| 도구              | 이미 잘 제공하는 영역                                                                                                        | 멀티트랙 편집기에서 추가로 필요한 영역                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Web Audio API** | 오디오 노드 연결, 믹싱, 이펙트 처리, 파라미터 자동화, 정밀 타이밍 재생, 오프라인 렌더링                                      | 트랙과 클립의 편집 모델, 분할과 이동 명령, Undo/Redo 같은 프로젝트 규칙 전반                            |
| **Tone.js**       | Transport 기반 음악 스케줄링, 악기와 이펙트, 자동화, 직렬 및 병렬 라우팅, 오프라인 렌더링                                    | 클립 단위 비파괴 편집, 작업 이력 관리, 트랙과 버스의 관계를 편집기 전체의 모델과 명령으로 통합하는 구조 |
| **wavesurfer.js** | 파형 표시와 재생, 플러그인을 통한 구간 표시, 볼륨 엔벌로프, 녹음, 별도 멀티트랙 확장을 통한 동기 재생                        | 클립 분할과 복제, 편집 히스토리, 센드와 버스 라우팅, 마스터 믹스 출력 같은 프로젝트 로직                |
| **daw-engine**    | 프로젝트 모델(`Session`), 비파괴 편집과 명령 이력(`CommandHistory`), 믹서와 라우팅 그래프, 백엔드 연결 경계(`AudioProvider`) | 실제 UI 화면 구성 및 오디오 재생과 녹음을 수행하는 소비 앱의 백엔드 구현                                |

조금 더 구체적으로 짚어 볼게요.

- **Web Audio API**는 브라우저 오디오 실행의 기반이에요. 이걸로 DAW를 만들 수는 있지만, 트랙과 클립을 어떻게 표현하고 편집 명령을 어떻게 되돌릴지 같은 프로젝트 규칙은 온전히 개발자 몫이에요.
- **Tone.js**는 음악적인 스케줄링과 오디오 처리를 아주 편리하게 만들어 줘요. 오프라인 렌더링과 라우팅도 지원하죠. 그래서 스케줄링이나 믹싱 자체를 `daw-engine`만의 차별점으로 보기는 어려워요. 핵심 차이는 **클립 편집, 작업 이력, 트랙과 버스의 관계를 편집기 전체의 도메인 모델과 명령으로 묶어 관리하는 범위**에 있어요.
- **wavesurfer.js**는 파형을 보여 주고 재생과 상호작용하는 데 강점이 있어요. 멀티트랙 확장도 제공하지만, 공식 문서에서도 스스로를 파형 시각화와 플레이어로 정의하듯 본격적인 클립 분할과 복제, Undo/Redo, 센드와 버스 라우팅과 믹스 출력까지 가려면 프로젝트 로직을 별도로 쌓아야 해요.

즉, `daw-engine`은 기존 오디오 기술을 대체하는 도구가 아니에요. Web Audio API나 Tone.js 같은 실행 기술 위에서 **편집 모델, 명령 이력, 라우팅, 백엔드 연결**이라는 빈칸을 채워 주는 역할을 해요. 실제 오디오 재생과 녹음은 `AudioProvider` 경계를 통해 애플리케이션의 백엔드에 연결하도록 열어 두었어요.

비파괴 편집 모델, 1,920 PPQ 시간 모델, 트랙 유형, 설치 방법과 API는 공개 저장소에서 확인할 수 있어요. [daw-engine README](https://github.com/whizzkid1452/daw-engine#readme)

도구별 실행 기능은 공식 문서에서 확인할 수 있어요. [Web Audio API 명세](https://www.w3.org/TR/webaudio-1.1/), [Tone.js 문서](https://tonejs.github.io/), [wavesurfer.js 문서](https://wavesurfer.xyz/docs/), [멀티트랙 확장 API](https://wavesurfer-multitrack.pages.dev/docs/classes/default)

## [sort1] 6. 마치며

DAW를 오래 쓰던 사람이 직접 엔진을 만들면, 처음에는 화면에 보이는 파형이나 믹서 기능부터 그대로 옮기는 데 급급하기 쉬워요. 저도 처음에는 그랬거든요.

그런데 막상 코드를 써 내려가며 파고들어 보니, 엔진의 무게중심은 기능의 개수보다 **시간, 오디오 신호, 편집 지시가 서로 어긋나지 않는 계약**에 있었어요. 좋은 DAW Core는 소리가 어긋나지 않게 흐르는 규칙을 먼저 정의하는 코드에 가까웠죠.

이 시리즈는 그 규칙을 하나씩 세워 온 기록이에요. 완성된 만능 엔진을 소개하기보다, 각 문제 앞에서 무엇을 선택했고 아직 무엇이 검증되지 않았는지 있는 그대로 남기려고 해요.

먼저 가장 기초가 되는 시간축 이야기부터 시작해 볼게요. 다음 글에서는 곡 중간에 템포가 바뀔 때 단순한 시간 변환 공식이 왜 깨지는지, 그리고 이를 구간 누적으로 어떻게 풀었는지 살펴볼게요.
