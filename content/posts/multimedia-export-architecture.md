VOIX STUDIO는 브라우저에서 영상·이미지·오디오·텍스트를 편집하고 결과물을 내보내는 고객용 멀티미디어 에디터다. 나는 웹 에디터의 초기 아키텍처와 Export 흐름을 개발하면서, 미리보기에서 본 편집 상태가 최종 파일에도 반영되도록 처리 경로를 정리했다.

핵심은 **영상 합성, 오디오 믹스다운, 인코딩과 파일 패키징을 나누고, 제품 UI와 처리 엔진 사이에 조율 계층을 두는 것**이었다. WebCodecs 경로를 기본으로 사용하고 지원되지 않는 환경에는 FFmpeg 대체 경로를 연결했다.

## [sort1] 1. 결과물 하나에 서로 다른 처리가 필요했다

Export는 인코더 호출 한 번으로 끝나지 않는다. 타임라인을 해석해 화면과 소리를 만들고, 인코딩한 결과를 재생 가능한 파일에 담아야 한다.

- 영상 합성은 각 시점의 비디오, 이미지, 텍스트를 위치·크기·투명도·순서에 맞춰 그린다.
- 오디오 믹스다운은 클립의 시간 배치와 트랙 볼륨, 패닝, 뮤트·솔로, 마스터 설정을 반영한다.
- 인코딩은 합성한 프레임과 오디오를 선택한 코덱의 데이터로 변환한다.
- Muxing은 인코딩된 영상과 오디오를 MP4 같은 컨테이너에 담는다.

미리보기와 내보내기가 서로 다른 편집 데이터를 읽거나 효과를 다르게 적용하면 결과가 달라진다. 처리 단계를 나누기 전에 두 경로가 참조하는 상태와 편집 규칙부터 맞춰야 했다.

## [sort1] 2. 브라우저 처리와 호환 경로를 함께 두었다

### [sort2] 2-1. 클라이언트에서 합성하는 이유

미디어를 서버로 전송해 합성하는 방식은 서버에 처리 자원을 집중할 수 있다. 대신 원본 업로드와 대기 시간, 서버의 인코딩 자원을 운영해야 한다.

이 제품에서는 브라우저가 로컬 미디어를 처리하는 경로를 택했다. 편집 중인 파일을 합성 서버로 다시 보내는 단계를 줄일 수 있고, 사용자의 장치에서 결과를 만들 수 있기 때문이다. 그만큼 클라이언트의 메모리, 장치 성능, 코덱 지원을 고려할 책임이 생겼다. 운영 비용이 0이 되었다는 뜻은 아니다.

### [sort2] 2-2. WebCodecs와 FFmpeg의 역할

WebCodecs는 브라우저에서 프레임과 오디오를 인코딩·디코딩하는 API다. 파일을 읽고 쓰는 컨테이너 처리까지 제공하지는 않으므로 합성, 코덱 처리, Muxing을 조합해야 한다. API의 존재와 원하는 코덱 설정의 지원 여부도 구분해야 한다.

WebCodecs 경로를 사용할 수 없는 환경에는 FFmpeg 기반 대체 경로를 연결했다. 두 경로는 같은 입력 계약을 받고, 조율 계층이 실행할 경로를 선택하도록 했다. 특정 브라우저 이름만으로 지원을 고정하지 않고 실제 실행 환경과 설정을 확인하는 기준이 필요하다.

## [sort1] 3. UI와 조율, 처리 엔진을 분리했다

한 함수에서 포맷 선택, Store 조회, 오디오 믹스다운, 영상 인코딩, 다운로드와 진행률 갱신을 모두 수행하면 오디오만 내보내는 경우에도 영상 처리와 얽히기 쉽다.

변경 이유를 기준으로 세 책임을 나누었다.

```text
UI
  포맷 선택, 실행·취소, 진행률과 오류 표시
  ↓
제품 조율 계층
  편집 상태와 미디어 수집, 처리 경로 선택, 진행 상태 전달
  ↓
처리 엔진
  영상 합성, 오디오 믹스다운, 인코딩, Muxing
```

처리 엔진은 React나 제품 Zustand Store를 직접 읽지 않는다. 조율 계층이 필요한 데이터와 진행률 콜백을 전달한다. 덕분에 제품 화면을 바꾸는 일과 처리 파이프라인을 바꾸는 일을 구분할 수 있었다.

다음 코드는 경계를 설명하기 위해 축약한 계약 예시다. 실제 제품의 전체 타입과 구현은 생략했다.

```ts
interface ExportProgress {
  stage: 'render' | 'encode' | 'mux';
  completed: number;
  total: number;
}

interface ExportRequest {
  projectId: string;
  revisionId: string;
  signal: AbortSignal;
  onProgress: (progress: ExportProgress) => void;
}
```

프로젝트와 revision은 어떤 편집 상태를 대상으로 실행하는지 식별하는 예시다. 긴 작업 중 프로젝트가 바뀌었을 때 결과를 어느 화면에 반영할지도 별도로 확인해야 한다.

## [sort1] 4. 오디오 Export와 비디오 Export의 믹스다운을 통합했다

초기 비디오 Export에는 `OfflineAudioContext`로 리전을 직접 스케줄링하는 코드가 있었다. 반면 오디오 Export는 오디오 엔진의 공통 렌더링 경로를 사용했다.

두 구현이 갈라지면서 비디오 Export의 오디오에는 트랙 볼륨·패닝·뮤트·솔로·마스터 게인이 빠질 수 있었다. 같은 타임라인을 내보내도 오디오 파일과 비디오 파일의 소리가 달라지는 문제였다.

비디오 Export도 공통 오디오 렌더링 API를 호출하도록 바꾸었다. 개인 개발한 TypeScript 라이브러리 `daw-engine`이 오디오 편집과 믹스다운을 맡고, 제품 Adapter가 멀티미디어 Export 흐름에 연결한다. 기존 글의 `drop-daw`, `drop-ai/core`는 이 편집 코어를 가리키던 이름이다.

이 변경의 결과는 두 Export 경로가 같은 믹스다운 규칙을 사용하게 된 것이다. 시간 단축이나 메모리 절감률을 별도로 측정한 결과로 해석하지 않았다.

## [sort1] 5. 썸네일 측정값과 Export 성과를 구분했다

WebCodecs와 Web Worker를 함께 사용하더라도 썸네일 생성과 Export는 작업량과 완료 기준이 다르다. 썸네일은 일부 시점의 이미지를 만들고, Export는 결과물 전체를 합성하고 인코딩한다.

[썸네일 검증 글](/posts/thumbnail-optimization-worker-verification)의 `Main busy 66% → 11%`는 100장 썸네일 생성 비교에서 나온 UI 루프 지연 대리 지표다. 이 값을 Export 중 메인 스레드 점유율 감소로 사용해서는 안 된다.

Export에서는 결과 파일의 재생 가능 여부와 화면·음향의 일치, 취소·오류 후 리소스 정리를 확인해야 한다. 제품 배포에는 내보내기 Smoke Test와 Windows·macOS·Ubuntu의 Electron E2E 검증을 적용했지만, 이것이 모든 코덱과 장치의 호환성을 증명하지는 않는다.

## [sort1] 6. 적용해보기

- [ ] 미리보기와 내보내기가 같은 확정 편집 상태를 읽는지 확인한다.
- [ ] 오디오·비디오 Export가 같은 믹스다운 규칙을 사용하는지 확인한다.
- [ ] 코덱 처리와 파일 Muxing의 책임을 구분한다.
- [ ] 기본 경로와 FFmpeg 경로가 같은 입력 계약을 받게 한다.
- [ ] 취소나 프로젝트 전환 뒤 이전 결과와 실행 리소스를 정리한다.
- [ ] 다른 작업의 벤치마크를 Export 성과로 옮겨 쓰지 않는다.

Export 구조를 나누면서 얻은 기준은 결과의 일관성이었다. 빠른 처리 경로를 추가하더라도 같은 편집 지시를 같은 결과로 해석하는 계약을 유지해야 했다.
