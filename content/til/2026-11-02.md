### 1. 개요 및 배경 (Context)

- **질문 요지** Tokens Studio 연동에 참고한 자료와 블로그 설명이 어긋나는 부분이 있는가? 실제 적용한 흐름에 맞춰 글을 고쳐 달라고 요청함.
- 디자인 시스템 글을 읽으면 디자인 토큰이 CSS 변수로 변환되고 자동으로 제품에 배포되는 것처럼 이해할 수 있었음. 당시 구성에서 어떤 형식이 만들어지고 누가 반영 여부를 판단하는지 다시 확인함.
- 토큰 원본은 색이나 간격에 이름을 붙여 공유하는 데이터임. 원본을 유지하는 방식과 앱이 최종 값을 읽는 방식에 차이가 있었음.

### 2. 핵심 내용 / 문제 해결 과정 (Core / Troubleshooting)

- **답변에서 고른 방법** 토큰의 출력 형식과 변경이 제품에 반영되는 경계를 따로 대조함. Token Transformer가 만든 JSON을 Emotion에서 읽었고, GitHub Actions는 리뷰할 PR을 생성했으므로 결과 형식과 자동화 범위를 각각 수정함.
- **Token Transformer**의 역할은 토큰 간 참조를 풀어 앱에서 읽을 수 있는 JSON을 만드는 것임. 프론트엔드는 변환된 JSON을 Emotion 테마 및 스타일에서 사용함. 설명을 두루뭉술하게 쓰면 토큰 원본과 소비 형식 사이의 변환 책임이 가려짐.
- GitHub Actions는 변환을 반복 실행하고 변경 내용을 PR로 보여 주는 역할을 함. 변환 결과를 바로 반영하면 절차는 짧지만 화면 변경을 미리 검토할 지점이 줄어듦. PR을 거치면 결과 파일의 차이를 확인할 수 있는 대신 리뷰와 머지 시간이 필요함.

    A["디자인 토큰 원본"] --> B["참조를 해석하는 Token Transformer"]

    C --> D["GitHub Actions가 만든 PR"]

- [디자인 시스템 글](/posts/design-system)에 변환 형식과 PR 경계를 반영하고 Git diff에서 문서 변경을 확인함. 실제 토큰 변경으로 CI와 제품 적용을 다시 실행한 검증은 당시 범위에 없었음.

### 3. 인사이트 및 적용점 (Takeaway & Next Action)

- 디자인 자동화는 **입력 변경, 산출물 생성, 제품 반영**의 세 시점을 기록하면 설명이 정확해짐. 파일 생성 자동화가 도입돼도 배포까지 사람이 확인해야 할 조건은 남을 수 있음.
- 다음 검증에서는 참조가 있는 토큰 하나를 바꿔 생성된 JSON, PR diff, 최종 화면의 스타일 값을 순서대로 대조할 수 있음.
