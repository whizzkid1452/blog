### 1. 개요 및 배경 (Context)

- **질문 요지** 메모리 진단을 추가한 변경을 실제로 실행해 수치를 보여 달라고 요청함. 첫 결과를 본 뒤 영상 편집 중에도 시험해 달라고 이어서 요청함.
- Electron 앱을 오래 켰을 때 메모리가 누적되는지 살피기 위한 첫 확인으로, 실제 앱의 **로그인 대기 화면**을 측정함.
- 아무 작업도 하지 않는 상태를 먼저 보면 앱이 유휴 상태에서 유지하는 기본 수준을 관찰할 수 있음. 리전 편집과 음성 생성 중에 할당되는 자원은 별도 시나리오가 필요함.

### 2. 핵심 내용 / 문제 해결 과정 (Core / Troubleshooting)

- **답변에서 고른 방법** 실제 Electron을 로그인 화면에 띄워 유휴 상태의 Main, Renderer, 전체 프로세스 지표를 함께 기록함. 이 구간에서 기본 메모리 추이와 종료 보고서의 기록 여부를 확인할 수 있었고, 편집 중 자원의 수명은 별도 부하 시험이 필요했음.
- **측정 조건** Apple M4, RAM 32 GiB, macOS 26.5.1, Electron 42.3.3에서 별도 프로필의 로그인 화면을 1회 실행함. 0~180초 동안 10초 간격으로 표본 19개를 기록했고 가비지 컬렉션은 강제하지 않았음. Main은 `process.memoryUsage().heapUsed`, 주 Renderer는 CDP의 `Runtime.getHeapUsage`를 사용함.

| 지표                         |      시작 |  180초 뒤 | 19개 표본 중앙값 |    최댓값 |
| ---------------------------- | --------: | --------: | ---------------: | --------: |
| 앱 프로세스 Working Set 합계 | 615.6 MiB | 592.9 MiB |        600.0 MiB | 615.6 MiB |
| Main JavaScript 힙           |  16.7 MiB |  14.7 MiB |         14.4 MiB |  16.9 MiB |
| 주 Renderer JavaScript 힙    |  23.2 MiB |  14.9 MiB |         14.9 MiB |  23.2 MiB |

- Working Set 합계는 Electron의 `app.getAppMetrics()`가 반환한 프로세스별 값을 더한 값이며 공유 페이지가 중복될 수 있음. 이 대기 구간에서 지속적인 증가는 관찰되지 않았음.
- **진단 보고서 확인** 10초 간격의 관찰과 별도로 앱의 30초 자동 수집을 유지함. 측정 뒤 주 Renderer를 강제 종료하자 보고서 **1개**에 자동 수집 표본 **7개**가 포함됨. 기준 브랜치와의 성능 차이는 이 시험에서 비교하지 않음.
- 전체 프로세스 합계는 앱이 유지하는 메모리의 큰 흐름을 파악하기 쉽고, 프로세스별 힙은 JavaScript 객체 관점에서 범위를 좁히는 데 적합함. 둘 다 높아지거나 한쪽만 변할 수 있으므로 같은 원인으로 해석하기 전에 함께 확인함.

### 3. 인사이트 및 적용점 (Takeaway & Next Action)

- **19회는 한 대기 구간의 표본 수**임. 독립 실행을 19번 반복한 결과로 해석하거나 영상 편집 및 장시간 누수의 결론으로 확장할 수 없음.
- 이후 편집 부하를 보려면 같은 프로젝트에서 열기, 편집, 닫기를 반복하고 각 작업 직후와 안정화 뒤의 프로세스별 수치를 대조하는 것이 적합함.
