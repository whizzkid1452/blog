## Q. server와 shared를 도메인별로 나누면 저장소도 분리된 것인가요?

A. 아니요. 이날 파일 이동, import, 진입점, 문서 경로 정리는 같은 저장소 안의 책임 구분이었어요. 프론트 저장소 생성과 API 계약 분리는 따로 계획했습니다. 폴더가 나뉘었다는 사실만으로 독립 배포나 결합도 감소까지 확인했다고 볼 수는 없습니다.

## Q. 프론트 저장소에는 어떤 기술을 쓰고 API는 어떻게 연결할 계획인가요?

A. 당시 제안은 기존 Node 미디어 서버를 유지하고 프론트의 화면, 라우팅, 요청 계층을 따로 구성하는 방향이었어요. 개발 중에는 Vite의 API 프록시를, 로컬 배포에서는 Node가 프론트 빌드를 제공하는 방식을 검토했습니다. 새 저장소와 배포를 완료한 기록은 아닙니다.

## Q. OpenAPI, Swagger, Axios, 리버스 프록시, CORS는 어떻게 정하나요?

A. 먼저 기존 엔드포인트와 JSON 응답 계약을 고정한 뒤 문서화, 클라이언트 생성을 연결하는 순서였습니다. 요청 도구를 고르는 것만으로 계약 검증이 생기지는 않아요. 프록시로 브라우저 요청 경로를 정리하더라도 백엔드의 Origin 검사와 인증, 쿠키 정책은 함께 맞춰야 합니다. 당시에도 이 항목은 설계안이었어요.

## Q. 제작 시작 API가 202를 반환하면 완료로 표시해도 되나요?

A. 아니요. 작업 접수와 완료를 나눠 표시해야 해요. 작업 ID로 진행 상태를 조회하다가 종료 상태에서 멈추는 계획이었습니다. 시작 요청을 자동 재시도하면 같은 작업이 중복될 수 있으므로 조회 재시도와 같은 정책으로 묶지 않았어요.

## Q. DAW 엔진은 편집 모델과 실제 재생을 어떻게 나누나요?

A. 세션 모델은 편집 상태를, 오디오 백엔드는 실제 버퍼, 노드, 재생 시계를 맡는 구조였어요. 명령이 모델을 변경하면 엔진이 알림을 받아 백엔드에 반영합니다. 파형, 좌표 계산 도구가 있다는 사실과 완성된 앱 화면이 있다는 사실도 구분해야 해요.

## Q. 세션 스냅샷을 저장하면 원본 오디오도 들어 있나요?

A. 당시 엔진의 기본 스냅샷은 편집 상태와 소스 참조를 담고 원본 오디오 바이트는 포함하지 않았어요. 오디오까지 묶으려면 호출자가 데이터를 제공하는 별도 경로가 필요했습니다. 자동 저장도 관련 기능을 명시적으로 시작해야 작동하는 구조였어요. 이날 확인은 코드 분석이며 실제 재생, 녹음, 내보내기를 실행한 검증은 아니었습니다.

## Q. 오디오 제작 앱은 로컬에서 어디까지 확인됐나요?

A. 당시 기록에는 웹 테스트 233개, 네이티브 CTest 13개, 브리지 회귀 시험 51개 통과와 합성 WAV 가져오기, 편집, Undo/Redo, 새로고침 복원이 있었습니다. 실제 AI 모델 호출은 0회였고 실제 소리를 듣고 평가하지도 않았어요. 로컬 기능 확인을 AI 품질, 플러그인 호환성, 서명, 출시 준비 완료로 넓힐 수는 없습니다.

## Q. GitHub Actions 비용 문제도 해결됐나요?

A. 이날 확인한 원격 실행에는 결제 실패 또는 지출 한도로 시작하지 못한 상태가 남아 있었어요. 로컬 테스트 통과와 사용량 절감 조치가 있어도 원격 실행 재개를 확인한 것은 아닙니다. 이후 계정 설정이 바뀌었는지도 이 과거 기록만으로 판단할 수 없어요.

## Q. 첫 클릭 때 정렬은 바뀌는데 화살표는 왜 그대로인가요?

A. 당시 대시보드에서는 실제 정렬 방향과 화살표 표시가 첫 클릭부터 같은 상태를 읽는지 확인하는 질문이었어요. 표의 초기 방향, 클릭 후 방향, hover 시 표시를 함께 맞춰야 합니다. 정렬 데이터가 바뀐다는 사실만으로 첫 클릭의 표시 상태까지 검증됐다고 볼 수는 없어요.

## Q. 화면만 확인하려면 dev와 dev-staging 중 무엇을 실행해야 하나요?

A. 당시 프로젝트에서 mock 연결과 실제 서버 연결을 구분해 확인해야 했어요. 실행 명령 이름만 보고 인증 우회나 mock 사용을 가정하면 안 됩니다. 화면 경로, 환경 설정, 연결 서버를 함께 확인하는 요청이었고, 개발 환경의 접근 편의와 운영 인증 정책은 구분했습니다.

## Q. DAW 라이선스 변경은 원본과 포크 중 어디에 반영됐나요?

A. 이날 대화에서는 원본 저장소에 GPL-2.0-or-later 변경을 병합했다고 확인했습니다. 포크가 따로 있다는 사실과 원본에 변경이 반영됐다는 사실은 구분해야 해요. 포크 삭제 요청은 추가 인증 대기 상태였으므로 삭제 완료로 기록하지 않았습니다. 여기서는 당시 변경 결과만 남기며 라이선스 적용 조건 전체를 설명하지 않습니다.

## Q. TIL 작성과 매일 자동 수집, 푸시는 같은 작업인가요?

A. 아니요. 날짜별 파일을 작성해 달력에 연결하는 일과 정기 실행 환경을 운영하는 일은 다릅니다. 이날 일지는 별도 워크트리에서 작성하도록 요청했지만 그 사실만으로 매일 대화 수집과 푸시 자동화가 생기는 것은 아니에요.

## Q. 현재 탭에 관계없이 일치하는 항목을 검색 드롭다운에 모두 보여 주세요.

A. 전체 탭의 후보를 먼저 찾고 작업 유형과 함께 표시하며, 선택한 결과의 탭으로 이동해 해당 제목을 검색하는 흐름으로 반영됐다는 답변을 확인했어요. 후보 목록에는 방향키, Enter, Escape 동작도 포함됐습니다. 당시 브라우저 확인은 목업 데이터를 사용했으므로 실제 서버의 전체 검색 범위까지 검증한 것으로 보지는 않았어요.

A. 10월 30일의 도메인 정리, 프론트 분리 계획, DAW 구조, 오디오 앱 로컬 검증과 CI 상태, 대시보드 정렬, 개발 실행, TIL 작성 대화를 11월 2일에 정리했습니다. 개인 계정, 비공개 URL, 로그 원문은 옮기지 않았고 실행 확인과 제안 단계의 내용을 구분했어요.

11월 2일에 같은 날짜의 로컬 메시지 기록을 추가 대조해 누락된 개발 질문을 보완했습니다. 추가 내용은 당시 답변의 요약이며, 이번 작업에서 제품 동작을 다시 실행한 결과는 아닙니다.
