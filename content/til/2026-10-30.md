이날은 **코드를 어떻게 나눌지, 지금 무엇까지 동작한다고 확인할 수 있는지**를 물었습니다. 미디어 패키징 프로그램의 폴더와 저장소 분리를 요청했고, 별도의 오디오 편집 엔진에서는 구조와 사용법을 확인했습니다. 오디오 제작 앱에서는 진행 상태를 묻는 데서 로컬 실행·검증 요청으로 이어졌습니다.

글을 정리하면서 눈에 들어온 것은 질문마다 확인해야 할 근거가 달랐다는 점입니다. 폴더 이동은 저장소 분리의 완료를, 테스트 통과는 실제 소리나 AI 품질을 보장하지 않았습니다. 아래 소제목은 당시 질문과 요청의 취지를 정리한 것이며, 원문 인용이 아닙니다.

## 1. 서버와 공유 코드를 도메인별로 나누고, 프론트엔드 저장소도 분리할 수 있을까?

미디어 패키징 프로그램에서는 **서버와 공유 모듈을 도메인별 폴더로 나눠 달라**고 요청했습니다. 도메인은 오디오·자막·검사·제작처럼 함께 이해하고 변경하는 기능 영역을 뜻합니다. 프론트엔드 저장소를 별도로 만들려는 요청도 남겼습니다.

기존 기록에서 확인한 변경은 파일 이동과 import 경로 수정, 실행 진입점과 문서 경로 갱신입니다. 이는 같은 프로그램 안에서 코드의 위치를 정리한 결과였습니다. 새 저장소 생성과 API 계약 분리까지 완료됐다는 근거는 확인하지 못했습니다.

당시에 어떤 폴더 구조를 비교했고 왜 도메인 기준을 택했는지는 질문 요약과 커밋만으로 복원할 수 없었습니다. **폴더를 나누는 요청과 저장소를 분리하는 요청은 각각 완료 상태를 확인해야 한다**는 것이 이번에 정리하며 얻은 기준입니다. 폴더 이동만으로 결합도가 낮아졌다고 평가하려면 실제 의존 방향도 더 살펴봐야 합니다.

## 2. 이 DAW 엔진은 어떤 구조이고, 앱에서는 어떻게 써야 할까?

별도의 DAW 엔진에서는 **전체 구조도와 특징, 사용법을 설명해 달라**고 요청했습니다. DAW는 소리를 녹음·편집하는 도구입니다. 확인한 저장소는 완성된 편집 화면보다는 편집 모델·명령·실행 이력·오디오 연동을 제공하는 TypeScript 라이브러리에 가까웠습니다.

구조 설명에서 구분할 수 있었던 것은 편집 상태와 실제 재생의 책임이었습니다. 세션 모델이 편집 상태를 관리하고, 명령으로 상태를 바꾸면 오디오 연동 엔진이 변경을 백엔드에 전달합니다. 앱이 연결하는 오디오 백엔드는 재생 시계와 버퍼를 관리합니다.

저장도 이름만 보고 범위를 판단할 수는 없었습니다. 세션 스냅샷은 편집 상태와 소스 참조를 담지만 **원본 오디오 바이트까지 포함하지는 않았습니다.** 오디오를 함께 묶으려면 호출자가 데이터를 제공해야 했고, 자동 저장도 관련 기능을 명시적으로 시작해야 했습니다.

이날 질문으로 확인한 범위는 코드의 구조와 연결 방식입니다. 재생·녹음·내보내기를 실행해 확인한 기록은 아니며, 전날 질문했던 플러그인 구조를 최종 채택한 것도 아닙니다. 글을 정리하며 남긴 다음 질문은 **외부 확장에 어떤 명령을 허용하고, 편집 상태를 바꿀 권한은 어디에 둘 것인가**입니다.

## 3. 진행 상태를 확인하는 데서 더 나아가, 이 컴퓨터에서 실제로 검증할 수 있을까?

별도의 오디오 제작 앱에서는 현재 진행 상태를 확인한 뒤 로컬 실행 환경과 검증을 요청했습니다. 체크리스트의 완료 표시를 읽는 것에서 테스트와 브라우저 동작을 확인하는 것으로 요청이 이어졌습니다.

기존 검증 기록에는 합성 WAV를 가져오고 파형을 표시한 뒤, 게인을 바꾸고 실행 취소·다시 실행한 과정이 남아 있습니다. 게인은 소리의 크기를 조절하는 값입니다. 새로고침 뒤 변경값이 복원되는 흐름도 확인했습니다. 반면 **오디오 출력은 비활성 상태였으므로 실제 소리를 듣고 평가한 것은 아니었습니다.**

AI 시험에서도 실행 계획과 연결 경로를 검사하는 것, 실제 모델의 응답 품질을 평가하는 것은 달랐습니다. 실제 모델 호출은 0회였고 품질 평가도 실행하지 않았습니다. 서명·공증과 사용자 검증 역시 이번 로컬 시험에 포함되지 않았습니다.

## 4. GitHub Actions의 비용 한도 문제는 해결됐을까?

로컬 검증과 별개로 **GitHub Actions의 비용 한도 문제가 해결됐는지**도 질문했습니다. CI는 변경을 원격 환경에서 자동으로 검사하는 절차입니다. 로컬에서 같은 시험을 통과했더라도 원격 실행이 다시 시작됐는지는 따로 확인해야 했습니다.

이날 조회한 최신 원격 실행 기록에는 결제 실패 또는 지출 한도로 작업을 시작하지 못한 상태가 남아 있었습니다. 중복 실행 취소와 실행 조건·시간 제한처럼 사용량을 줄이는 조치는 있었지만, 원격 실행 재개는 확인하지 못했습니다. 현재 결제 설정 자체를 확인한 것은 아니므로 이후에도 계정 상태가 그대로라고 단정할 수는 없습니다.

질문에 대한 답은 해결 완료가 아니라 **당시 확인한 실행 기록에서는 재개를 확인하지 못했다**는 상태였습니다. 다음에는 어느 커밋의 원격 작업이 실제로 시작됐는지부터 확인해야겠습니다. 이는 글을 정리하며 남긴 후속 확인 항목입니다.

## 5. TIL에는 내가 어떤 요건 때문에 고민하고 선택했는지를 남길 수 있을까?

블로그에는 대화와 접근 가능한 Work 기록을 바탕으로 공부 일지를 쓰고, 홈 달력에서 날짜별 일지로 이동할 수 있게 해 달라고 요청했습니다. 달력에는 큰 주제를 불릿으로 보여 주고, 호버하면 요약을 읽고, 날짜를 누르면 상세 내용을 볼 수 있게 하는 요구였습니다.

본문에 대해 직접 요청한 기준은 **어떤 프로젝트에서 어떤 요건 때문에 무엇을 고민하고 선택했으며, 결론은 무엇이었는지**였습니다. 따라서 일지의 중심은 구현 파일이나 전달받은 답변의 양보다 제 질문과 판단이어야 합니다. 글쓰기 컨벤션에도 이 요구를 남기도록 요청했습니다.

구현에서는 같은 날짜의 파일을 달력과 게시판이 함께 읽고, 초안·비공개 일지를 공개 경로에서 제외하도록 했습니다. 다만 화면과 일지 파일을 만드는 것, 매일 대화를 자동 수집하고 작성·푸시하는 것은 다른 범위였습니다. 이 작업으로 정기 자동화가 설정됐다고 기록할 수는 없습니다.

질문을 정리할 때도 같은 기준이 필요했습니다. **답변을 받았다는 사실과 그 제안을 제 선택으로 채택했다는 사실을 구분해야 합니다.** 이번 글 역시 당시의 질문과 확인한 내용을 연결하되, 원문이 없는 선택 이유는 보충하지 않았습니다.

## 6. PR에서 관련 작업 대화를 다시 찾을 수 있게 기록해 둘까?

이날 밤에는 PR 맨 아래에 관련 작업 대화의 실제 세션 ID를 항상 남기도록 요청했습니다. 표시 이름은 도구명 대신 **`session Id`**로 정했고, 원격 규칙과 이 컴퓨터에도 적용해 달라고 했습니다.

대화의 완료 보고에서는 규칙의 로컬 적용과 원격 푸시를 확인했습니다. 여러 대화가 같은 PR에 참여했다면 기존 ID를 유지하고 추가하는 기준도 포함됐습니다. 특정 PR의 본문을 수정한 작업까지 확인한 것은 아닙니다.

TIL에서는 질문의 맥락을 읽을 수 있게 정리하고, PR에서는 관련 대화를 다시 찾을 식별자를 남기게 됐습니다. 두 기록의 역할을 이렇게 나눠 볼 수 있다는 것은 이번 글을 정리하며 얻은 해석입니다.

## 기록의 범위

한국 시간 2026년 10월 30일의 질문과 작업을 다룹니다. **10월 31일에 질문 중심으로 다시 구성했습니다.** 블로그 구현 대화에 전달된 사용자 요청 원문과 작업 보고, PR의 세션 ID 기록을 요청한 로컬 대화를 추가로 확인했습니다.

도메인별 폴더 정리, DAW 구조, 오디오 앱의 검증과 원격 CI는 기존 10월 30일 일지의 질문·요청 요약과 검증 결과를 근거로 재구성했습니다. 이번에 그 원대화 전체나 해당 프로젝트의 시험을 다시 확인한 것은 아닙니다. 질문 요약만 있는 주제에는 당시의 동기·비교 대안·선택 이유를 새로 넣지 않았습니다.

소제목은 질문의 취지를 다듬은 문장입니다. 글을 정리하며 얻은 기준과 후속 질문은 당시의 결정과 구분했습니다. 모든 Work 대화와 하루 전체를 확인한 기록은 아니며, 비공개 원문·내부 경로·접근 정보는 본문에 옮기지 않았습니다.
