### 1. 개요 및 배경 (Context)

- **질문 요지** 대시보드를 설계하고 면접에서 설명하려면 RDB, RDBMS, SQLite, PostgreSQL, Redis를 어떻게 구분하고 어떤 기준으로 골라야 하는가?
- 제작, 업로드, 검수 상태를 한 화면에 모을 대시보드를 설계하면서 SQLite, PostgreSQL, Redis가 각각 어떤 문제에 맞는지 비교함.
- 당시 코드에는 업로드 상태용 SQLite가 있었고, 제작 상태와 이력은 다른 위치에 있었음. 데이터베이스를 처음 넣는 문제보다 **분산된 기록을 어떤 단위로 연결하고 집계할지**가 먼저였음.

### 2. 핵심 내용 / 문제 해결 과정 (Core / Troubleshooting)

- **답변에서 고른 방법** DB 이름을 먼저 정하기보다 현재 업로드 상태, 제작 기록과 화면의 집계 단위를 대조함. 이미 업로드 상태는 SQLite에 있었고, 대시보드에서는 무엇을 한 건으로 세며 누가 결과를 읽고 쓰는지가 선택을 바꾸기 때문임.
- **RDB**는 데이터를 관계로 표현하는 모델, **RDBMS**는 이를 관리하는 소프트웨어, **SQL**은 데이터를 조회하고 변경하는 언어임. SQLite와 PostgreSQL은 둘 다 관계형 모델을 제공하므로, 대시보드용 선택에서는 실행과 운영 방식의 차이가 중요함.

| 선택지     | 적합한 조건                                                   | 감수할 비용                                                                     |
| ---------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| SQLite     | 한 앱이 로컬 파일을 소유하고 배포 구성을 작게 유지할 때       | 여러 서비스에서 공유하거나 동시 쓰기가 늘면 접근 경로와 잠금 정책을 검토해야 함 |
| PostgreSQL | API와 수집 프로세스가 같은 관계형 데이터를 조회하고 갱신할 때 | 별도 서버와 접속 설정, 마이그레이션, 백업 및 복구 운영이 필요함                 |
| Redis 캐시 | 실제 측정에서 같은 결과를 반복 계산하거나 읽는 비용이 클 때   | 원본과 캐시 사이의 갱신, 무효화, 만료 규칙이 추가됨                             |

- 첫 단계에서는 **무엇을 1건으로 셀지**, **어떤 조건에서 완료로 볼지**, **어느 정도 갱신 지연을 허용할지**를 먼저 정하는 쪽으로 검토함. 회차별 건수와 회차 및 대상 언어별 건수는 다르고, 인코딩만 끝난 경우와 결과 검수까지 끝난 경우도 구분이 필요함.
- 이날은 기술별 선택 기준을 비교한 시점임. 실제 대시보드 채택과 검증은 [11월 20일 일지](/til/2026-11-20)에 이어짐.

### 3. 인사이트 및 적용점 (Takeaway & Next Action)

- 데이터베이스를 고를 때 기능 목록보다 **누가 읽고 쓰는가, 어느 저장소가 기준인가, 어떤 질문을 집계하는가**를 먼저 설명해야 함.
- 캐시가 필요한지는 대표 조회의 실행 시간과 갱신 요구사항으로 판단할 수 있음. 조회 모델 자체가 잘못되면 캐시를 두어도 잘못된 숫자가 빨리 나올 수 있음.
