## Q. 상태를 Effect로 지켜보기보다 변경이 발생하는 지점에서 처리하면 되지 않나요?

A. 직접 리뷰를 제출한 탭에서는 이미 제출 성공 콜백으로 모달을 닫고 있었어요. 남은 검토 대상은 다른 탭의 변경을 확인한 뒤 처리하는 경로였습니다. Effect를 없애고 이 탭의 클릭 이벤트만 연결하면 다른 탭에서 제출한 경우를 놓칠 수 있어요. 상태를 표시하는 일과 사건에 반응해 모달을 닫는 일을 나누어 보자는 검토였습니다.

## Q. 다른 탭의 변경 알림만으로는 어떤 값인지 모르니 다시 읽어야 하지 않나요? 재조회 실패면 닫으면 안 될 것 같아요.

A. 변경 알림의 키로 대상 저장 항목을 좁힐 수는 있지만, 유효한 리뷰가 존재하는지까지 보장되지는 않아요. 재조회에 성공하고 리뷰가 실제로 있는 것을 확인한 뒤 닫고, 실패하면 유지한다는 기준을 직접 제시했습니다. 알림 수신과 조회 성공, 모달 닫기를 각각 구분한 것이 핵심이에요. 당시에는 연결 지점을 확인하는 단계였으며 전체 수정 완료로 적지는 않았습니다.

## Q. useSyncExternalStore는 왜 쓰나요? Effect에서 상태를 갱신하면 무한 렌더링이 생겨서인가요?

A. 당시 플레이어에서는 React 밖의 컨트롤러 상태를 현재 값 읽기와 구독으로 React 렌더링에 연결하려고 사용했어요. 단순한 Effect 구독은 렌더링에서 값을 읽은 뒤 구독이 시작되기 전 변경을 놓칠 수 있다는 설명이었습니다.

Effect 안의 모든 상태 갱신이 무한 렌더링을 만드는 것은 아니에요. 갱신이 의존성을 다시 바꾸며 순환하는지가 별개의 조건입니다. 재생 버튼을 눌렀다는 요청과 실제 비디오가 재생 중이라는 사실도 구분해서 UI를 갱신해야 했어요.

## 기록의 범위

한국 시간 10월 25일의 모달 흐름 질문과 플레이어 면접 연습 중 질문을 11월 2일에 로컬 원문에서 확인했습니다. 직접 제시한 재조회 실패 처리 기준과 당시 답변을 구분했으며, 제안을 구현 완료로 바꾸지 않았어요.
